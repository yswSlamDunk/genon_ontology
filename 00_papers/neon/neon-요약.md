# NeOn 방법론 요약 — 1학년용

> 한 줄 요약: 온톨로지를 매번 처음부터 만들지 말고, **이미 있는 자원(기존 온톨로지, 분류체계, 용어집, 데이터베이스 등)을 최대한 재사용**하자. 그 방법을 **9가지 시나리오**로 정리한 방법론.

## 이 방법론이 해결하려는 문제

METHONTOLOGY(1997)는 온톨로지를 "공학적으로" 만드는 길을 열었지만, **빈 종이에서 하나의 온톨로지를 만드는 경우**만 다뤘다. 그런데 실제 회사나 프로젝트에는 이미 쓰고 있는 표준 분류, 용어 사전, 데이터베이스가 있다. 이걸 무시하고 처음부터 만들면 시간도 오래 걸리고, 다른 시스템과도 맞지 않는다.

> 비유: 요리할 때마다 밀가루부터 빻는 대신, 시판 소스와 손질된 재료를 골라 쓰고 필요한 부분만 직접 만드는 것.

## 핵심 1 — 9가지 시나리오

| # | 시나리오 | 쉽게 말하면 |
|---|---|---|
| 1 | 명세에서 구현까지 | 처음부터 만들기 (모든 경우에 **필수**) |
| 2 | 비온톨로지 자원 재사용·재공학 | 용어집·분류표·DB를 온톨로지로 바꾸기 |
| 3 | 온톨로지 재사용 | 남이 만든 온톨로지 그대로 가져다 쓰기 |
| 4 | 온톨로지 재사용·재공학 | 가져와서 고쳐 쓰기 |
| 5 | 온톨로지 재사용·병합 | 비슷한 온톨로지 여러 개를 합치기 |
| 6 | 재사용·병합·재공학 | 합친 다음 고치기 |
| 7 | 설계 패턴 재사용 | 자주 쓰는 모델링 "모범 답안" 쓰기 |
| 8 | 재구조화 | 쪼개기·잘라내기·넓히기·세분화하기 |
| 9 | 지역화 | 여러 언어로 번역하기 |

상황에 맞게 골라서 **조합**한다. 예: 시나리오 1 + 2 + 3.

## 핵심 2 — 요구사항 명세서(ORSD)와 역량 질문

만들기 전에 **ORSD**(온톨로지 요구사항 명세서)를 쓴다.

| 항목 | 예 (회사 인사 온톨로지라면) |
|---|---|
| 목적 | 결재선과 인사 발령을 자동으로 검증하려고 |
| 범위 | 직원, 직급, 직책, 조직 |
| 사용자 | 인사팀, 결재 시스템 |
| 역량 질문(CQ) | "박지훈의 결재선은?", "팀장보다 직급 높은 팀원이 있나?" |
| 사전 용어집 | CQ에 나온 단어와 등장 횟수 |

역량 질문은 **온톨로지가 반드시 답해야 하는 질문**이다. 설계의 출발점이자, 다 만든 뒤 제대로 됐는지 확인하는 시험 문제가 된다.

## 핵심 3 — 데이터베이스도 재사용 자원이다

DB를 온톨로지로 쓰는 방법은 두 가지다.

| 방법 | 쉽게 말하면 |
|---|---|
| 복사형 | DB 테이블 구조로 온톨로지를 만들고, 행을 인스턴스로 **복사**해 넣는다 |
| 매핑형 | 온톨로지와 DB 사이에 "이 컬럼은 이 속성"이라는 **연결표만** 만들고, 물어볼 때마다 DB에서 읽어 온다 |

## METHONTOLOGY와 무엇이 다른가

| | METHONTOLOGY | NeOn |
|---|---|---|
| 만드는 것 | 온톨로지 하나 | 서로 연결된 온톨로지 여러 개(네트워크) |
| 출발 | 빈 종이 | 있는 자원 먼저 찾기 |
| 데이터베이스·용어집 | 다루지 않음 | 시나리오 2로 다룸 |
| 관계 | — | 시나리오 1 안에 METHONTOLOGY가 들어 있음 |

## 기억할 것

1. NeOn은 METHONTOLOGY를 **버리는** 게 아니라 **감싸는** 방법론이다.
2. 시작은 언제나 **ORSD와 역량 질문**이다.
3. 처음부터 만들기 전에 **재사용할 자원을 먼저 찾는다**. 데이터베이스도 그 대상이다.
4. 그래도 NeOn은 여전히 **온톨로지를 만드는** 방법론이다. 데이터를 대량으로 채우고 운영하는 일이나, 그 위에 앱을 만드는 일까지 다루지는 않는다.
