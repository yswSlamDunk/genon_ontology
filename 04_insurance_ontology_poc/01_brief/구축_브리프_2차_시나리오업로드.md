# 구축 브리프 2차: 비정형 청구 서류 업로드 → 업무 시스템 반영

청구인이 쓴 청구서(docx)와 병원이 발급한 입퇴원확인서(pdf)를 Studio에 **추가 인제스천**으로 올립니다. 그 내용으로 질의·액션에서 청구를 접수해 **업무 시스템 DB에 반영되는 것**을 확인합니다.

- 작성: 2026-11-04
- **시나리오 1은 지금 구축하고, 시나리오 2는 발표 때 추가로 올려서 보여 줍니다.**
- 자료: [02_data/upload/](../02_data/upload/). 생성 스크립트: [02_data/make_scenario_upload.py](../02_data/make_scenario_upload.py)
- 모든 인물·의료기관·서류는 가상입니다.

> **실제 진행 (2026-11-04):** 아래 2절의 구축 의도·골든 커맨드 대신, 엔티티만 추가하는 최소 입력으로 진행했습니다.
> - 업로드: 문서 2개, 시스템 없음. 의도 「업로드한 청구 서류를 기존 클래스의 인스턴스로 추가한다. 스키마와 액션은 바꾸지 않는다.」, 골든 퀘스천 1개, 골든 커맨드 없음
> - 접수: 기존 `submitClaimReceipt`로 RC-0002·CL-002·EV-002 생성
> - 재적재: 시스템 4개, 의도 한 줄, 골든 퀘스천 1개(CL-002 청구인·피보험자)
> - 「첫 서류 연결」 액션은 만들지 않았습니다. 그래서 3절의 1-3 이후는 그 액션을 추가해야 진행할 수 있습니다.
> - 정리: [PoC 보고서 6장](../../03_ppt/02_보험_온톨로지_PoC/보험_청구심사_온톨로지_PoC.md)

## 0. 전체 흐름

Studio에서는 업로드한 문서가 곧바로 DB에 들어가지 않습니다(앱 코드로 확인).
- 파일은 **구축** 화면에서만 올릴 수 있습니다. 구축 에이전트는 액션을 정의하고 dry-run까지만 합니다.
- **질의·액션** 화면은 파일을 받지 않지만, 액션을 실행해 업무 시스템 API를 부릅니다.

DB를 바꾸는 것은 Studio 액션이 부른 업무 시스템 API뿐이고, DB에 직접 넣는 단계는 없습니다.

```text
① 구축(추가 인제스천): 서류 2개 업로드 → 그래프에 「미접수 서류」 2건
② 질의·액션: 기존 「청구 접수」 액션 → 접수·청구 생성              ← DB
③ 구축: 재적재
④ 질의·액션: 새 「첫 서류 연결」 액션 → 서류 등록·연결              ← DB
⑤ 구축: 재적재
⑥ 질의·액션: 서류 확인 → 평가 → 승인 또는 부지급 (기존 액션)       ← DB
```

- **확인서:** 병원 양식을 자유롭게 배치한 PDF입니다. 스캔본이 아니라 글자가 들어 있어 Studio가 OCR 없이 읽습니다.

## 2. 구축 화면 입력 (①, 시나리오 1)

| 단계 | 넣을 것 |
|---|---|
| 1 소스 | **문서:** `upload/시나리오1/`의 파일 2개. **시스템:** `ins-` 4개(새 액션 정의용). 데이터소스는 고르지 않습니다 |
| 2 대상 | `보험 청구 심사 온톨로지 (추가 인제스천)` |
| 3 의도 | 아래 구축 의도와 골든 커맨드 1개. **골든 퀘스천은 넣지 않습니다** |

골든 퀘스천을 빼는 이유는, 적재 결과를 제가 그래프에서 직접 조회해 확인할 수 있기 때문입니다. 칸이 비어 있으면 진행이 막히는 경우에는 Studio 자동 초안을 그대로 두면 됩니다.

골든 커맨드는 하나 필요합니다. 기존 액션 10개에는 **새 청구에 첫 서류를 붙이는 액션이 없습니다**. 「서류 교체」(`replaceClaimDocument`)는 교체할 기존 서류 ID를 반드시 받습니다. 접수(`submitClaimReceipt`), 서류 확인, 평가, 승인, 부지급은 기존 액션을 그대로 씁니다.

### 2.1 구축 의도

```text
기존 「보험 청구 심사 온톨로지」에 업로드한 청구 서류(청구인이 쓴 보험금 청구서 docx, 의료기관이 발급한 입퇴원확인서 pdf)를 더한다. 아직 업무 시스템에 접수되지 않은 제출 원본이며, 질의·액션에서 이 내용으로 청구를 접수하고 서류를 연결하는 데 쓴다.

적재 규칙:
- 업로드 서류는 기존 Document 클래스에 적재하고 새 클래스를 만들지 않는다. doc_id는 파일 이름 앞의 업로드 문서 번호(예: UP-S1-01), source_system은 upload, 접수 여부는 미접수로 둔다.
- storage_ref는 업로드 파일 이름, content_hash는 업로드 파일 바이트의 SHA-256을 계산해 넣는다.
- 보험금 청구서는 자유 서술이다. 본문에서 청구인, 입원한 사람, 계약번호, 청구한 보장, 사고접수번호, 의료기관 코드, 입원일, 퇴원일, 작성일을 읽어 속성으로 둔다. 사람은 기존 Claimant(display_name)와, 계약은 Policy(policy_number)와, 보장은 그 계약의 Coverage(1일 지급액)와 맞춰 청구인 번호와 보장 코드도 함께 둔다.
- 입퇴원확인서에서는 환자(식별 토큰), 의료기관 코드, 입원일, 퇴원일을 추출값(extracted_*)으로 둔다. 추출값은 확인값이 아니다. 신뢰도는 원문에 그대로 적힌 값이면 높게, 해석이 필요한 값이면 낮게 둔다.
- 청구서가 언급한 첨부 파일 이름으로 청구서와 입퇴원확인서를 잇는다.
- ClaimReceipt, InsuranceClaim, InsuranceEvent, DocumentVerification에는 업로드 내용으로 인스턴스를 만들지 않는다. 그것은 액션을 실행해 업무 시스템이 만든다.
- 기존 클래스, 인스턴스, 관계와 액션 10개는 바꾸지 않는다.

액션 1개 추가(골든 커맨드):
- InsuranceClaim을 대상으로 서류를 처음 연결하는 액션(교체 아님).
  1) ins-intake registerDocument (storage_ref, content_hash, document_type)
  2) ins-intake attachDocument (path receipt_no ← 대상 청구의 receipt_no, doc_id ← 1단계 응답 doc_id, replaces_doc_id는 보내지 않음)
  3) ins-review recordEvidenceAttached (path claim_id ← 대상 청구의 claim_id, doc_id ← 1단계 응답 doc_id)
- 보상: 2단계 revertAttachment (attachment_id ← 2단계 응답 attachment_id).
- 실행자 actor_id는 파라미터로 받는다. 파라미터 기본값에 기대지 않고, Idempotency-Key는 매핑하지 않는다. 정책 역할은 scm_operator.
```

### 2.2 골든 커맨드

```text
청구 CL-001에 새 입퇴원확인서(저장 위치 test://DC-new, 해시 hash-new)를 교체 없이 추가로 연결해 줘. 접수 담당자 intake-01.
```

구축 단계에서는 dry-run만 하므로 CL-001은 바뀌지 않습니다. 대상은 지금 그래프에 있는 청구여야 해서 CL-001을 썼습니다.

### 2.3 구축이 끝나면 제가 확인할 것

- **업로드 노드:** Document에 UP-S1-01, UP-S1-02 2건이 생겼고 미접수인지
- **채운 값:** 청구서 노드의 청구인 IP-0002, 보장 INPATIENT-DAILY-A, 해시가 1절 표와 같은지
- **원본 클래스:** ClaimReceipt, InsuranceClaim에는 노드가 늘지 않았는지
- **새 액션:** 단계 3개, 보상 1개, 인자 연결이 2.1절과 같은지
- **기존 정의:** 기존 액션 10개가 그대로인지

## 3. 질의·액션 실행 (②–⑥, 시나리오 1)

번호(RC-0002, CL-002 등)는 DB의 다음 번호로 예상한 값입니다. **각 단계 뒤에 결과를 붙여 주시면 DB를 조회해 확인하겠습니다.**

| 순서 | 화면 | 입력 | DB에 생기는 것 (예상) |
|---|---|---|---|
| 1-1 | 질의·액션 | 업로드한 보험금 청구서 UP-S1-01의 내용대로 계약 PO-001에 청구를 접수해 줘. 요청 키 REQ-UP-S1-01, 접수 담당자 intake-01. | 접수 RC-0002, 청구 CL-002 `RECEIVED`, 입원 사건 EV-002(ACC-0101) |
| 1-2 | 구축 | 등록 시스템 조회 API로 새 접수·청구·입원 사건을 다시 적재해 줘. 액션 정의는 바꾸지 마. | 없음 (그래프에 CL-002) |
| 1-3 | 질의·액션 | 청구 CL-002에 업로드한 입퇴원확인서 UP-S1-02를 첫 서류로 연결해 줘. 접수 담당자 intake-01. | 서류 DC-002 등록·연결, 서류 확인 `PENDING` |
| 1-4 | 구축 | (1-2와 같음. 서류·서류 확인 포함) | 없음 (그래프에 DC-002) |
| 1-5 | 질의·액션 | 서류 DC-002를 담당 심사자 reviewer-01이 확인 완료로 처리해 줘. 확인값은 피보험자 IP-0002, 의료기관 H-002, 입원일 2026-06-02, 퇴원일 2026-06-05이고, 근거는 원본 대조. | 서류 확인·사건 `VERIFIED` |
| 1-6 | 질의·액션 | 청구 CL-002를 담당 심사자 reviewer-01로 평가해 줘. | 지급 후보 3일·300,000원, 청구 `READY_FOR_DECISION` |
| 1-7 | 질의·액션 | 청구 CL-002를 현재 평가 기준으로 지급 승인해 줘. 담당 심사자 reviewer-01, 결정 사유는 지급 조건 충족. | 지급 지시, 청구 `APPROVED` |

- **1-1 입력:** 청구인 번호와 보장 코드는 입력하지 않습니다. 에이전트가 청구서 노드에서 읽어 기존 접수 액션의 인자를 채우는 것이 이 시나리오의 핵심입니다.
- **1-5 확인값:** 피보험자는 서류의 토큰(TKN-B)이 아니라 청구인 번호(IP-0002)로 넣습니다. 서버의 확인값 형식이 청구인 번호이고, 담당자가 추출값을 보고 사람을 확인하는 단계이기 때문입니다(명세 4.2절).
- **한도 반영:** 1-6 전에 CL-001을 먼저 지급 승인하면 B의 남은 한도가 2일이 되어 **2일·200,000원**이 나옵니다(명세 2.3절, R07).

## 4. 발표: 시나리오 2 추가

시나리오 1로 액션이 모두 갖춰져 있으므로, 발표에서는 **서류만 올리면 같은 흐름이 그대로 돈다**는 것을 보여 줍니다.

| 순서 | 화면 | 넣을 것 | 결과 |
|---|---|---|---|
| 2-0 | 구축 | 문서: `upload/시나리오2/` 2개. 시스템·골든 퀘스천·골든 커맨드 없음. 대상: 추가 인제스천. 의도: 아래 한 줄 | 그래프에 UP-S2-01, UP-S2-02 (미접수) |
| 2-1 | 질의·액션 | 1-1과 같은 문장에서 UP-S1-01 → UP-S2-01, 요청 키 REQ-UP-S2-01 | RC-0003, CL-003, EV-003(ACC-0102). 계약자 A는 청구할 수 있어 접수는 통과 |
| 2-2 – 2-4 | 구축·질의·액션 | 1-2 – 1-4와 같음 (CL-003, UP-S2-02) | DC-003 연결 |
| 2-5 | 질의·액션 | 서류 DC-003 확인 완료. 확인값 피보험자 IP-0001, 의료기관 H-004, 입원일 2026-07-10, 퇴원일 2026-07-14, 근거 원본 대조 | `VERIFIED` |
| 2-6 | 질의·액션 | 청구 CL-003 평가 | **부지급 후보**, R01 FAIL(`IDENTITY_MISMATCH`) |
| 2-7 | 질의·액션 | 청구 CL-003을 현재 평가 기준으로 부지급 결정. 사유: 입원한 사람이 피보험자가 아님 | `REJECTED` |

2-0 구축 의도:

```text
시나리오 1과 같은 적재 규칙으로 업로드한 청구 서류 2건을 기존 Document 클래스에 미접수로 더한다. 새 클래스와 새 액션은 만들지 않고, 기존 클래스·인스턴스·액션은 바꾸지 않는다.
```

시간이 모자라면 2-0과 2-1(접수)까지만 보여 주고, 2-5 – 2-7은 미리 해 둔 결과를 앱에서 보여 줘도 됩니다. 다만 미리 하면 2-0도 미리 하게 되므로 「추가」 장면이 사라집니다.

말할 수 있는 요지:
- 자유 서술 서류에서 읽은 이름과 문장을 온톨로지가 기존 청구인, 계약, 보장과 이어서 접수 인자를 채웁니다.
- 업로드한 서류는 「미접수」로만 들어오고, 사람이 승인한 액션을 거쳐야 업무 시스템에 반영됩니다.
- A는 청구서에 「제가 계약자로 가입한 보험」이라고 썼고 접수도 됩니다. 하지만 심사에서 **입원한 사람이 피보험자가 아님**이 드러나 부지급됩니다.
