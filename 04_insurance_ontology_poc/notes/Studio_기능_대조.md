# Studio 제공 기능과 서버 구현 대조

명세의 요구사항을 셋으로 나눕니다. Studio가 해 주는 것, 우리 서버가 해야 하는 것, 우리가 실제로 만든 것입니다. 목적은 서버에 불필요하게 만든 것이 있는지 가리는 것입니다.

근거는 데스크톱 앱 v0.1.1 안의 파일입니다(2026-11-03 확인).

| 근거 | 위치 (`/Applications/Ontological Studio.app/Contents/` 아래) |
|---|---|
| 액션 실행기: 계획·승인·실행·재시도·보상 | `Resources/runtime/kinetic/app/app/plans.py` |
| 호출 헤더, 멱등 키 형식 | 같은 폴더 `dispatch.py` |
| 액션 정의 형식(단계·보상·정책) | 같은 폴더 `catalog.py`, `policy.py`, `mapping.py` |

## 1. 결론

Studio는 **조율**을 맡습니다. 언제, 어떤 순서로, 누구의 승인을 받아 API를 부를지 정하고 기록합니다. 무엇을 어떻게 바꾸고 무엇을 막을지(업무 의미)는 서버가 맡습니다.

질문하신 두 가지는 둘 다 **절반만 Studio가 해 줍니다**.

- **보상:** Studio는 보상을 **언제 부를지**를 맡습니다. 실행기는 단계가 실패하면 성공한 단계를 역순으로 자동 보상합니다. 사용자가 "취소해 줘"라고 해도 같은 방식으로 되돌립니다. 구축 에이전트는 등록된 API 중에서 `cancel*`·`revert*` 같은 되돌리기 API를 골라 보상으로 짝짓습니다. 하지만 **되돌리는 API 자체는 서버에 있어야 합니다**. 없으면 그 단계는 보상 없음(`none`)으로 남고 "부분 취소만 가능"이 됩니다.
- **멱등성 키:** Studio는 키를 **만들어 보내기만** 합니다. 단계마다 `계획:대상:단계:a시도` 키를 붙입니다. 같은 키가 다시 오면 처음 결과를 돌려주는 일(중복 거르기)은 서버 몫입니다. 시스템 등록 화면에 "서비스는 Idempotency-Key 로 중복을 걸러야 합니다."라고 적혀 있습니다. Studio의 예제 서버도 이 일을 직접 합니다(`common.py`의 `once()`).

그래서 우리 구현 중 **Studio와 겹쳐서 지울 수 있는 것은 거의 없습니다**. 확실히 불필요한 것은 쓰지 않는 표 하나(`payment.idempotency_record`)입니다(4.2절). 대신 Studio의 동작에 비추어 **서버를 보완해야 할 점이 두 가지** 나왔습니다(4.4절).

## 2. Studio 실행기가 하는 일과 서버에 남는 일

| 기능 | Studio가 하는 일 | 서버가 해야 하는 일 |
|---|---|---|
| 보상 | 단계 실패 시 성공한 단계를 역순으로 자동 보상합니다. 사용자 취소(`compensate`)도 같은 방식입니다. 보상 호출에도 별도 키(`…:c`)를 붙입니다 | 되돌리는 API(`cancelReceipt`, `revertAttachment`)를 제공합니다. 되돌려도 되는 상황인지 판단합니다 |
| 멱등성 키 | 단계마다 `Idempotency-Key`를 붙입니다. 인자로 같은 헤더를 넣어도 실행기 값이 덮어씁니다 | 같은 키의 재요청을 걸러 처음 결과를 돌려줍니다. 다른 입력이면 거절합니다 |
| 같은 계획 재실행 | 같은 계획(plan)을 다시 실행하면 서버를 부르지 않고 저장된 실행 결과를 돌려줍니다(계획당 실행 하나, DB 유일 제약) | 없음 |
| 재시도 | 실패한 대상을 1단계부터 다시 부릅니다. 시도 번호가 바뀌어 **키도 바뀝니다**(`:a1` → `:a2`). 최대 3회 뒤에는 `dead`가 됩니다. 정책은 다시 평가하지 않습니다. 등록 화면의 "재시도 2번"은 게이트웨이용 값이라 데스크톱(직접 호출)에서는 실행기가 자동 재시도하지 않습니다 | 키가 바뀐 재시도도 안전해야 합니다(4.4절) |
| 권한(정책) | 역할(`roles`)과 조건식(`when`, CEL)으로 계획 때 판정하고, 실행 직전에 다시 판정합니다. 규칙이 없으면 아무도 실행하지 못합니다 | 업무 권한(담당 심사자 여부)을 확인합니다. 데스크톱은 사용자 1명(`lite-user`)에게 모든 역할을 주므로 역할로 사람을 나눌 수 없습니다 |
| 사람 승인 | 대상 수가 `confirm_threshold`를 넘으면 실행 전에 사람이 계획을 승인해야 합니다 | 없음. 명세의 A07 `ApproveClaim`(지급 결정)과는 다른 기능입니다 |
| 실행 직전 재확인 | 대상 노드를 그래프에서 다시 읽고 정책을 다시 평가합니다. 사라진 대상은 건너뜁니다 | 상태·최신성 검사. 그래프 값은 늦을 수 있고, 이 재확인은 서버 트랜잭션과 묶이지 않습니다 |
| 실행 기록 | 계획, 실행, 단계별 HTTP 결과, 보상 순서, 감사 로그(`kinetic_plans`·`kinetic_runs`·`kinetic_audit`)를 남깁니다 | 업무 이력(`action_log`)과 거절 사유를 남깁니다 |
| 결과 반영 | 성공하면 첫 단계 응답의 `status`를 대상 노드 속성에 써 넣고, 취소하면 실행 전 값으로 되돌립니다 | 응답 최상위에 `status`를 넣습니다 |
| 연결 | 인증 헤더 주입(환경변수 이름 → 값), 상태 확인(3초), 시간 제한, GET 조회(`query_system`, 쓰기는 거절) | OpenAPI 문서, `/health`, 인증 검사 |

## 4. 우리 구현 점검

### 4.1 그대로 둘 것

아래는 Studio가 대신하지 않으므로 필요합니다.

- **업무 규칙 전부:** 평가 엔진, 상태 전이, 승인 트랜잭션·잠금, 한도·중복 검사, 참조 일관성(T29)
- **지급 흐름:** 발송 대기 기록, 모의 지급 전달, 서명 콜백, 대사
- **멱등성 기록**(접수·심사): Studio 안내문이 서비스에 요구하는 일이고, 명세 8.3의 요구입니다
- **되돌리기 API**(`cancelReceipt`, `revertAttachment`): Studio 자동 보상이 부를 대상입니다
- **실행 이력**(`action_log`): Studio 기록은 Studio로 부른 호출만 담고 업무 사유가 없습니다. ActionLog는 명세의 객체 12개 중 하나이기도 합니다

Studio로 옮길 수 있었는지 살펴본 것:

- **A09 지급 요청:** 심사 서버가 안에서 지급 서버를 부릅니다. Studio의 2단계 액션으로 나눌 수도 있지만, 명세 8.3이 승인 거래와 함께 저장하는 발송 대기 기록과 별도 전달기를 요구하므로 서버 안에 둡니다.
- **A11 대사:** 응답에 따라 결과를 고르는 판단이 필요합니다. Studio 단계는 응답에 따라 갈라지지 못합니다.

### 4.2 불필요한 것

| 대상 | 이유 | 처리 제안 |
|---|---|---|
| `payment.idempotency_record` 표 (`02_data/schema/04_payment.sql`) | 지급 서버는 지급 키(`payment_key`)로만 중복을 거르고 이 표를 쓰지 않습니다. 지급 서버는 Studio가 아니라 심사 서버만 부릅니다 | 표 정의를 지웁니다 |

### 4.3 명세 요구는 아니지만 Studio 확인용으로 둔 것

| 대상 | 이유 |
|---|---|
| 시스템 인증 3종 | Studio 인증 전달을 확인하려고 두었습니다. 2026-11-03에 유지하기로 결정했습니다 |
| 모의 지급 제어 `/mock/*` | 테스트 전용입니다. OpenAPI에 노출하지 않아 Studio에는 보이지 않습니다 |

### 4.4 Studio 동작에 비추어 보완할 점

**(1) 성공한 A01·A02를 사용자가 취소하는 경우.** 구축 에이전트 지침에 따르면 "방금 한 처리를 취소해 줘" 같은 커맨드는 새 액션이 아니라 앞 액션의 보상으로 실행됩니다. 지금 서버로 그렇게 하면 데이터가 어긋납니다.

| 액션 | 취소 때 일어나는 일 | 문제 |
|---|---|---|
| A01 | 2단계(`registerClaim`)는 보상이 없어 건너뛰고, 1단계 `cancelReceipt`만 부릅니다 | 접수는 취소됐는데 청구는 남습니다. `cancelReceipt`는 청구가 있는지 보지 않습니다 |
| A02 | `revertAttachment`만 부릅니다 | 청구가 이미 승인됐어도 근거 서류 연결을 되돌립니다. `revertAttachment`는 청구 상태를 보지 않습니다 |

지금 테스트는 단계가 실패했을 때의 보상만 확인했습니다. 성공한 뒤 취소하는 경로는 확인하지 않았습니다.

제안: 두 되돌리기 API가 심사 시스템을 조회하게 합니다.
- `cancelReceipt`: 그 접수로 등록된 청구가 있으면 409로 거절합니다.
- `revertAttachment`: 청구가 승인·종결 상태면 409로 거절합니다.

이렇게 하면 실패 시 자동 보상은 그대로 동작합니다(2단계가 실패했으니 청구가 없음). 취소는 Studio에 "보상 실패"로 보이고 데이터는 어긋나지 않습니다.

**(2) 응답이 유실된 뒤 재시도하는 경우.** Studio 재시도는 키가 바뀝니다. 서버가 처리를 끝냈는데 응답이 시간 제한(5초)을 넘기면, 재시도는 서버에게 새 요청으로 보입니다.

| 액션 | 재시도 결과 |
|---|---|
| A01 | 안전합니다. 접수 요청 키(`request_key`)라는 업무 키로 중복을 거릅니다(파라미터로 받으면 재시도에도 같은 값) |
| A09 | 안전합니다. 지급 키로 거릅니다 |
| A07 등 상태를 바꾸는 액션 | 데이터는 안전합니다. 다만 이미 바뀐 상태라 409로 거절되고, Studio에는 실제로는 성공한 일이 "실패"로 보입니다 |

선택지는 두 가지입니다.
- **(가) 그대로 둡니다.** Studio 실행 결과보다 서버 상태와 `action_log`를 기준으로 봅니다.
- **(나) 키의 시도 번호(`:a<n>`)만 다른 요청을 같은 요청으로 봅니다.** Studio 키 형식에 기대는 규칙입니다.

PoC 범위에서는 (가)를 제안합니다. 가장 느린 A09도 서버 안의 지급 전달을 3초에서 끊고 `UNKNOWN`으로 응답하므로, 5초를 넘기는 경우는 드뭅니다.
