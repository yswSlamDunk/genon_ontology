# 업무 시스템 서버 설계서 (Source of Truth)

명세 1절의 네 시스템(계약, 접수, 심사, 지급)을 **HTTP 서버**로 만들어 Ontological Studio에 **시스템으로 등록**하기 위한 기준 문서입니다. 서버 코드, 실행 스크립트, Studio 등록 값은 모두 이 문서를 따릅니다. 이 문서와 코드가 다르면 이 문서를 먼저 고치고, 코드를 그에 맞춥니다.

- 작성: 2026-11-03 (1단계), 2026-11-03 개정 (2단계 추가)
- 범위:
  - **1단계, 조회:** 상태 확인, 인증, 조회 API (5절)
  - **2단계, 쓰기:** 명세 8절 Action A01–A11을 실행하는 API, 평가 엔진, 모의 지급 (7절)
- 근거: Studio 데스크톱 앱 v0.1.1에 들어 있는 실행기(kinetic-action) 코드와 예제 서버(`sample/services/`). 출처는 부록에 있습니다.

## 1. Studio가 등록된 시스템으로 하는 일

Studio는 등록된 시스템을 세 가지 용도로 씁니다. 서버가 갖춰야 할 기능은 여기서 나옵니다.

| 용도 | Studio가 하는 일 | 서버에 필요한 것 |
|---|---|---|
| 등록과 연결 테스트 | OpenAPI 문서에서 API 목록을 읽고, 상태 확인 경로를 부르고, 인증 비밀 값이 준비됐는지 봅니다 | OpenAPI 문서, `/health`, 인증 |
| 조회 | 에이전트와 화면이 **GET API**를 바로 불러 현재 값을 읽습니다. 계획과 승인 없이 실행됩니다 (`query_system`) | GET 조회 API |
| 액션 실행 | 계획 → 승인 → 실행. 단계마다 등록된 API를 부르고, 실패하면 보상 단계를 부릅니다 | 쓰기 API, 멱등성 (2단계) |

1단계 서버로 첫째와 둘째가 됩니다. 셋째는 2단계에서 쓰기 API를 추가하고 액션을 만들 때 됩니다.

## 2. 서버가 지켜야 할 규칙 (Studio 쪽 조건)

실행기 코드에서 확인한 조건입니다. 어기면 등록이나 호출이 실패합니다.

### 2.1 OpenAPI 문서

- **OpenAPI 3.x** 또는 Swagger 2.0이어야 합니다. FastAPI가 만드는 `/openapi.json`(3.1)을 그대로 씁니다. 앱 예제도 같습니다.
- **모든 API에 `operationId`가 있어야 합니다.** `operationId`가 없는 API는 목록에서 빠집니다. 이름 규칙은 영문으로 시작하고 영문, 숫자, `_ . -`만 씁니다. 이 PoC에서는 `getClaim`처럼 동사로 시작하는 camelCase로 통일합니다.
- 요청 본문은 `application/json`만 읽습니다.
- 경로 변수(`{claim_id}`)는 parameters에 같은 이름으로 있어야 합니다. FastAPI가 자동으로 맞춥니다.
- `summary`는 Studio 화면과 에이전트가 API를 고를 때 보는 설명입니다. 한국어로 짧게 씁니다.
- 등록할 때 `openapi_url`을 주면, 나중에 API를 추가한 뒤 Studio의 「새로 고침」으로 목록을 다시 읽을 수 있습니다. Studio에서 손으로 API를 추가할 수도 있습니다. 같은 `operationId`면 손으로 추가한 쪽이 이깁니다. OpenAPI에서 온 API는 Studio에서 지울 수 없고, 서버 코드를 고친 뒤 새로 고쳐야 합니다.

### 2.2 상태 확인 (`/health`)

- 연결 테스트는 `base_url + health_path`를 **GET으로 3초 안에** 부르고, 2xx면 통과입니다.
- 이 PoC의 `/health`는 인증 없이 열고, DB에 `SELECT 1`을 해서 DB가 꺼져 있으면 503을 돌려줍니다. OpenAPI 문서에는 넣지 않습니다(예제와 같음).

### 2.3 인증

- Studio는 비밀 값을 저장하지 않습니다. 등록에는 **환경변수 이름**만 적고, 실제 값은 호출할 때 실행기(kinetic-action) 프로세스의 환경변수에서 읽습니다.
- 지원 방식: 없음, API 키(헤더 또는 쿼리), Basic(`사용자:비밀번호`), Bearer, OAuth2 client credentials, 로그인 토큰.
- 환경변수가 비어 있으면 실행기는 **인증 없이** 요청을 보내고, 서버는 401을 돌려줍니다. 연결 테스트는 이 경우 `missing_env`로 알려 줍니다.
- 앱 예제처럼 **시스템마다 다른 방식**을 씁니다. 실제 회사에서 시스템마다 인증이 다르다는 가정입니다(4절).

**비밀 값 전달 문제 (미검증):** 앱 코드를 보면 실행기 프로세스의 환경은 「앱이 시작될 때의 환경 + 예제 서버 비밀 값 3개」입니다. `studio.env`의 값은 실행기에 전달되지 않습니다. 그래서 우리 서버의 비밀 값을 실행기에 넘기려면 **앱이 시작되기 전 환경에 넣어야** 합니다. macOS에서는 `launchctl setenv`로 로그인 세션 환경에 넣고 앱을 다시 시작하는 방법이 있습니다(`studio-env.sh`). 이 방법이 되는지는 등록 때 연결 테스트의 `missing_env`로 확인합니다. 안 되면 대안은 6.3절에 있습니다.

확인한 것 (2026-11-03):
- **실행기 환경:** 실행 중인 실행기 프로세스에는 `ERP_API_KEY`, `WMS_BASIC`, `CRM_TOKEN`만 있고 `INS_*`는 없습니다. 값이 아니라 환경변수 이름만 확인했습니다.
- **앱 실행 방식:** Studio 앱은 launchd(Finder, Dock)로 실행되어 있습니다(부모 PID 1).
- **launchctl 전달:** `launchctl setenv`로 넣은 시험 변수가 그 뒤 Finder 방식으로 연 앱의 환경에 들어가는 것을 확인했습니다.
- **주의:** `launchctl setenv` 값은 재부팅하면 사라집니다. 재부팅한 뒤에는 `studio-env.sh`를 다시 실행하고 앱을 다시 엽니다.

### 2.4 호출 방식

- 데스크톱 앱의 실행기는 게이트웨이 없이 `base_url`로 **직접** 부릅니다.
- 응답은 JSON입니다. 2xx는 성공, 그 밖은 실패로 기록됩니다. 실패 응답 본문도 실행 기록에 남으므로, 사유를 `{"detail": "…"}`로 담습니다.
- 쓰기 요청에는 `Idempotency-Key`(`계획:대상:단계:a시도`, 보상은 끝에 `:c`)와 `X-Kinetic-Run` 헤더가 붙습니다. 1단계 서버는 쓰기가 없으므로 받기만 하고 쓰지 않습니다.
- 요청 제한 시간은 등록 값 `timeout_ms`입니다(예제 5000).

## 3. 이 PoC의 설계 원칙

1. **시스템 하나 = 서버 하나 = 스키마 하나.** 각 서버는 자기 스키마만 읽고 씁니다. 다른 시스템의 데이터가 필요하면 **그 시스템의 API를 부릅니다**(예: 심사 서버의 평가가 계약 서버의 역할·보장을 조회). 서버끼리 테이블을 건너 읽지 않습니다.
2. **API는 각 시스템 자기 식별자를 씁니다.** 계약 서버는 `C-10001`, `PO-001`을, 접수 서버는 `IP-0001`, `RC-0001`을 씁니다. 명세 ID로 바꿔 주지 않습니다. 시스템마다 식별자가 다르다는 명세 1절의 전제를 지키고, 연결은 온톨로지가 합니다.
3. **응답 필드 이름은 DB 컬럼 이름 그대로**(snake_case)입니다. 데이터소스로 읽은 값과 API로 읽은 값을 바로 대조할 수 있습니다.
4. **조회 API는 DB를 읽기만 합니다.** 조회용 DB 연결에는 `default_transaction_read_only=on`을 걸어, 코드에 실수가 있어도 DB가 바뀌지 않게 합니다. 쓰기는 2단계 쓰기 API의 쓰기용 연결만 합니다.
5. **업무 판단은 쓰기 API 안에서만 합니다.** 평가, 상태 전이, 한도 계산은 7절의 규칙대로 서버가 합니다. 조회 API는 저장된 값을 돌려줄 뿐입니다.
6. **비밀 값은 파일 하나에만 둡니다.** `03_systems/.env.local`(권한 600)에만 있고, 문서, 로그, 채팅에 적지 않습니다.

## 4. 서버 구성과 Studio 등록 값

| 시스템 | Studio 이름 | 표시 이름 | 주소 (`base_url`) | 스키마 | 인증 | 환경변수 |
|---|---|---|---|---|---|---|
| 계약 | `ins-contract` | 계약 시스템 | `http://127.0.0.1:18101` | `contract` | API 키, 헤더 `X-API-Key` | `INS_CONTRACT_API_KEY` |
| 접수 | `ins-intake` | 접수 시스템 | `http://127.0.0.1:18102` | `intake` | Basic | `INS_INTAKE_BASIC` (`사용자:비밀번호`) |
| 심사 | `ins-review` | 심사 시스템 | `http://127.0.0.1:18103` | `review` | Bearer | `INS_REVIEW_TOKEN` |
| 지급 | `ins-payment` | 지급 시스템 | `http://127.0.0.1:18104` | `payment` | API 키, 헤더 `X-Payment-Key` | `INS_PAYMENT_API_KEY` |

네 시스템 모두 공통으로:
- 프로토콜 `rest`
- OpenAPI 주소: `base_url` + `/openapi.json`
- 상태 확인 경로 `/health`
- 제한 시간 5000ms, 재시도 2 (앱 예제와 같은 값)
- 환경 `local` 하나
- 태그 `insurance`, `poc`

- 이름 규칙: Studio 시스템 이름은 소문자, 숫자, `-`만 씁니다. 앱 예제(`sample-erp` 등)와 겹치지 않게 `ins-`로 시작합니다.
- 포트: 앱이 쓰는 274xx·278xx 대역을 피해 181xx를 씁니다. `127.0.0.1`에서만 받습니다.
- DB 계정: `ins_service`. 비밀번호는 `02_data/.env.local`의 `INS_SERVICE_PASSWORD`를 읽습니다.

## 5. 1단계 API 목록 (조회)

모든 API는 인증이 필요합니다. 없는 ID는 404, 잘못된 값은 422를 돌려줍니다. 목록 API는 `limit`(기본 100, 최대 500)을 받습니다.

### 5.1 계약 시스템 `ins-contract`

| operationId | 경로 | 돌려주는 것 |
|---|---|---|
| `getCustomer` | `GET /customers/{cust_no}` | 고객 1명 |
| `listCustomers` | `GET /customers?identity_token=` | 고객 목록. 토큰으로 동일인 찾기 |
| `getPolicy` | `GET /policies/{policy_id}` | 계약 1건 + 역할 목록 + 보장 목록 |
| `listPolicies` | `GET /policies?policy_number=` | 계약 목록. 대외 계약 번호로 찾기 |
| `getCoverage` | `GET /coverages/{coverage_id}` | 보장 버전 1건 |
| `listCoverages` | `GET /coverages?policy_number=&coverage_code=` | 보장 목록. 접수 시스템의 (계약 번호, 보장 코드)로 찾기 |

## 6. 구현과 운영

### 6.1 기술 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어, 프레임워크 | Python 3.12, FastAPI, uvicorn | 앱 예제 서버와 같은 구조. OpenAPI가 자동으로 나옵니다 |
| DB 드라이버 | psycopg 3 | 예제와 같음 |
| 실행 환경 | `uv`로 만든 `03_systems/.venv` | 앱 내부 Python에 기대지 않습니다. 앱 업데이트와 무관합니다 |

### 6.2 폴더 구성

```
03_systems/
├── 서버_설계서.md       # 이 문서 (Source of Truth)
├── README.md            # 실행 방법 요약
├── pyproject.toml       # 의존성 (uv)
├── services/
│   ├── common.py        #   DB 연결(조회·쓰기), 인증, /health, 멱등성, 거절, 다른 시스템 호출
│   ├── evaluation.py    #   평가 엔진 (R01–R07). 이 파일의 해시 = logic_hash
│   ├── contract.py      #   계약 시스템  :18101
│   ├── intake.py        #   접수 시스템  :18102
│   ├── review.py        #   심사 시스템  :18103
│   └── payment.py       #   지급 시스템  :18104 (모의)
├── run.sh               # 네 서버 시작·중지·상태 (start | stop | status | restart)
├── studio-env.sh        # 인증 비밀 값을 Studio 실행기 환경에 넣는다 (launchctl setenv)
├── check.sh, check.py   # 조회 API 확인 (B0 값)
├── scenario_test.py     # 쓰기 API 시나리오 테스트 (명세 11절 T01–T29 + A01·A02)
├── .env.local           # 비밀 값 (run.sh가 만든다, 권한 600, 공유 금지)
└── logs/                # 서버 로그
```

비밀 값은 다섯 개입니다. 시스템 인증 4개(4절)는 Studio 실행기에도 넘기고, 지급 콜백 서명 값 `INS_PAYMENT_CALLBACK_SECRET`은 지급·심사 서버만 씁니다(7.6절).

### 6.3 실행 순서

1. PostgreSQL이 켜져 있고 `insurance` DB가 B0인지 확인합니다(`02_data/reset.sh`).
2. `./run.sh start`로 네 서버를 켭니다. 처음 실행하면 의존성을 설치하고 `.env.local`을 만듭니다.
3. `./check.sh`로 네 서버가 B0 값을 돌려주는지 봅니다.
4. `./studio-env.sh`로 비밀 값 4개를 로그인 세션 환경에 넣고, **Studio 앱을 완전히 종료한 뒤 다시 엽니다.**
5. Studio 「시스템 등록」에서 4절 값으로 네 시스템을 등록하고 연결 테스트를 합니다.

서버는 자동으로 켜지지 않습니다. Studio에서 조회나 액션을 쓸 때는 `./run.sh start`로 켜 둡니다.

**4번이 안 될 때 (연결 테스트에서 `missing_env`):** 터미널에서 비밀 값을 환경에 넣고 앱 실행 파일을 직접 실행하는 방법이 있습니다. 그것도 안 되면 1단계에 한해 인증을 「없음」으로 등록하는 방법이 있습니다. 서버가 `127.0.0.1`에서만 받기 때문에 가능하지만, 실제 회사 환경과 달라지므로 결정 기록(`notes/`)에 남깁니다.

### 6.4 확인 기준 (1단계 완료 조건)

## 7. 2단계: 쓰기 API

명세 8.1절의 Action A01–A11을 실행하는 API입니다. **Studio 액션은 이 API들을 단계로 묶은 것**입니다. 구축 에이전트가 골든 커맨드를 보고 이 API 목록에서 단계를 고릅니다(7.9절). 그래서 API 하나는 한 시스템 안에서 끝나는 일만 하고, 두 시스템에 걸치는 Action은 단계 두 개로 나눕니다.

### 7.1 모든 쓰기 API의 공통 규칙

| 규칙 | 내용 | 명세 |
|---|---|---|
| 멱등성 | `Idempotency-Key` 헤더가 필수입니다. 범위는 (Action 종류, `actor_id`, 키)입니다. 같은 키와 같은 입력이면 처음 결과를 그대로 돌려주고, 같은 키에 다른 입력이면 409 `IDEMPOTENCY_CONFLICT`입니다. 기록은 각 스키마의 `idempotency_record`에 업무 변경과 **같은 트랜잭션**으로 남겨, 서버를 다시 켜도 유지됩니다. 거절된 요청은 기록하지 않습니다(조건을 고친 뒤 다시 시도할 수 있게). Studio 재시도는 시도 번호가 바뀌어 키도 바뀝니다(`…:a1` → `…:a2`). 그래도 데이터는 안전합니다. 접수는 `request_key`, 지급은 `payment_key`라는 업무 키로 중복을 거르고, 나머지는 상태 조건으로 거절하기 때문입니다. 다만 응답이 유실된 뒤의 재시도는 Studio에 실패로 보일 수 있으므로, 그때는 서버 상태와 실행 이력을 기준으로 봅니다(키 형식에 기대는 규칙은 두지 않음) | 8.3 |
| 실행자 | 본문의 `actor_id`가 필수입니다. 담당 심사자 확인 같은 권한 검사는 이 값으로 합니다. Studio 데스크톱의 사용자 토큰(`sub`)은 `lite-user` 하나뿐이어서 심사자 ID와 다릅니다. 그래서 Studio 액션은 `actor_id`를 **파라미터로 받도록**(`$params.actor_id`) 구성합니다 | 12.3 |
| revision | 본문의 `expected_revision`은 선택입니다. 주면 대상의 현재 revision과 비교하고, 다르면 409 `REVISION_CONFLICT`입니다. 필수로 두지 않은 이유: Studio는 실행 뒤 그래프 노드의 속성을 하나(`writeback_property`)만 갱신하므로, 그래프의 revision이 실제보다 뒤처질 수 있습니다. 평가의 최신성은 입력 해시로 따로 검사합니다(7.5절) | 7.4, 8.2 |
| 거절 | 업무 조건을 어기면 409와 `{"detail": {"code": "…", "message": "…"}}`를 돌려주고 업무 데이터는 바꾸지 않습니다. 없는 대상은 404, 입력 형식 오류는 422입니다 | 8.2 |
| 실행 이력 | 심사 시스템의 Action은 성공과 거절 모두 `review.action_log`에 남깁니다. 접수·지급 단계는 자기 요청 기록(`idempotency_record`)만 남기고, 업무 이력은 같은 Action의 심사 단계가 남깁니다 | 8.1 |
| 응답 | 청구를 바꾸는 API는 응답 최상위에 청구의 `status`를 넣습니다. Studio는 첫 단계 응답의 `status`를 대상 노드에 다시 써 넣습니다(`writeback_property`) | — |
| 시각 | 변경 시각은 시간대가 있는 시각(`timestamptz`)으로, 업무 날짜는 `Asia/Seoul` 달력 날짜로 다룹니다 | 2.3 |

### 7.4 평가 엔진 (A04)

평가 코드는 `services/evaluation.py` 한 파일에 둡니다. 이 파일의 SHA-256이 평가 로직 해시(`logic_hash`)입니다. `02_data/reset.sh`가 B0를 넣을 때 이 값을 `RV-001`에 채웁니다.

**입력 스냅샷** — 심사 서버가 평가 시점에 모읍니다.

| 입력 | 어디서 |
|---|---|
| 청구, 사건, 증빙 확인값, 규칙 버전, 같은 사건·같은 한도 키의 지급 지시 | 심사 DB |
| 계약 역할, 보장 조건 | 계약 API (`getPolicy`) |
| 접수에 현재 연결된 서류(유형·해시) | 접수 API (`getReceipt`) |
| 사건 주체와 계약 고객의 동일인 판정 | 접수 API `getClaimant`의 `identity_token` → 계약 API `listCustomers` |

**규칙** (명세 7.2절, 결과는 `PASS` / `FAIL` / `UNKNOWN`)

| 규칙 | 판정 | 사유 코드 |
|---|---|---|
| R01 `IDENTITY_MATCH` | 입원일에 유효한 피보험자 역할의 고객과 사건 주체의 고객이 같으면 PASS, 다르면 FAIL. 사건 사실 미확인, 고객 매핑 없음, 피보험자 역할 없음은 UNKNOWN. 단 입원일이 보장 기간 밖이면 그 날짜의 역할이 없는 것이 당연하므로 계약의 피보험자 역할 전체로 판정합니다(보장 밖은 R02가 FAIL로 잡음, T05) | `IDENTITY_MISMATCH` / `UNCONFIRMED_FACT` |
| R02 `COVERAGE_PERIOD` | 입원일이 `[보장 시작, 보장 종료)` 안이고 퇴원일 ≤ 보장 종료면 PASS. 입원일이 밖이면 FAIL. 입원일은 안인데 퇴원일이 넘으면 UNKNOWN | `OUTSIDE_COVERAGE` / `PERIOD_CROSSING` |
| R03 `WAITING_PERIOD` | 입원일 ≥ 보장 시작 + 대기 일수면 PASS, 아니면 FAIL | `WAITING_NOT_MET` |
| R04 `EVIDENCE_COMPLETE` | 규칙이 요구하는 서류 유형마다, 현재 연결된 서류 중 `VERIFIED`가 하나 이상이고 그 확인값(사람·의료기관·입원일·퇴원일)이 사건과 같으면 PASS. 없으면 UNKNOWN(누락), 다르거나 사건이 `CONFLICT`면 UNKNOWN(충돌) | `MISSING_DOCUMENT` / `FACT_CONFLICT` |
| R05 `POSITIVE_STAY` | 퇴원일 > 입원일 PASS, 같으면 FAIL, 역전이면 UNKNOWN | `ZERO_STAY` / `INVALID_DATES` |
| R06 `DUPLICATE_CLEAR` | 같은 사건·같은 보장의 **다른 청구**가 승인·지급 상태이거나 유효한 지급 지시를 가지면 UNKNOWN, 없으면 PASS | `DUPLICATE_REVIEW` |
| R07 `LIMIT_AVAILABLE` | 잔여 일수 = max(0, 최대 일수 − 지급 일수 − 다른 청구 예약 일수) > 0 이면 PASS, 0이면 FAIL | `LIMIT_EXHAUSTED` |

사건 사실이 확인되지 않았으면(`UNVERIFIED`) 날짜가 필요한 R01·R02·R03·R05는 UNKNOWN `UNCONFIRMED_FACT`입니다. 한도 키는 (계약, 보장, 피보험자 고객, `benefit_period_key`)이고, 지급 일수는 `PAID`, 예약 일수는 `RESERVED`·`REQUESTED`·`UNKNOWN`·`FAILED`의 `reserved_days` 합입니다(명세 5.3절).

**집계** (명세 7.3절 순서)
1. `INVALID_DATES`, `FACT_CONFLICT`, `PERIOD_CROSSING`, `DUPLICATE_REVIEW`, `DEPENDENCY_UNAVAILABLE`가 하나라도 있으면 `MANUAL_REVIEW`입니다. `UNCONFIRMED_FACT`도 여기에 들어가는데, 예외가 있습니다. 서류 누락(`MISSING_DOCUMENT`)이 함께 있고 미확인 원인이 사건 사실 미확인뿐이면, 서류 보완으로 해소될 수 있으므로 넣지 않습니다.
2. 그다음 `MISSING_DOCUMENT`가 있으면 `NEED_INFO`입니다.
3. 그다음 FAIL이 있으면 `NOT_PAYABLE_CANDIDATE`입니다. 인정 일수와 금액은 0입니다.
4. 모두 PASS면 `PAYABLE_CANDIDATE`입니다. 인정 일수 = min(입원 일수, 잔여 일수), 금액 = 인정 일수 × 일당입니다.
5. 1과 2는 인정 일수와 금액이 `null`입니다(0과 구분).

**결과 기록**
- 평가 `AS-…`를 새로 만들고 사용 증빙(문서 ID·해시)을 함께 남깁니다. 이전 평가는 그대로 둡니다.
- 청구의 `current_assessment_id`를 바꿉니다.
- 사유 코드마다 업무를 만듭니다. 같은 (청구, 유형, 사유, 관련 ID)의 미해결 업무가 있으면 새로 만들지 않습니다.

| 사유 코드 | 업무 유형 |
|---|---|
| `MISSING_DOCUMENT` | `EVIDENCE_REQUEST` |
| `FACT_CONFLICT`, `UNCONFIRMED_FACT` | `FACT_REVIEW` |
| `INVALID_DATES`, `DEPENDENCY_UNAVAILABLE` | `DATA_REPAIR` |
| `PERIOD_CROSSING` | `PERIOD_REVIEW` |
| `DUPLICATE_REVIEW` | `DUPLICATE_REVIEW` |

- 청구 상태:
  - `PAYABLE_CANDIDATE`·`NOT_PAYABLE_CANDIDATE`이고 미해결 업무가 0건이면 `READY_FOR_DECISION`
  - `NEED_INFO`면 `NEED_INFO`
  - 그 밖은 `UNDER_REVIEW`
  - 평가가 미해결 업무를 닫지는 않습니다(명세 9.1절).

**입력 해시 (`input_hash`)**
- 판단에 영향을 주는 값만 정렬·정규화해 SHA-256을 냅니다.
  - 들어가는 값: 청구의 계약·보장·사건 연결, 보장 조건, 규칙 버전과 해시, 역할, 사건 사실, 동일인 매핑, 연결 서류와 확인값, 같은 사건·같은 한도 키의 지급 지시(ID·상태·일수), 미해결 업무
  - 빠지는 값: 청구 상태, `current_assessment_id`, revision, 시각
- 전체 스냅샷(revision 포함)은 `input_snapshot`에 감사용으로 남깁니다(명세 7.4절).

**평가 보류** — 규칙 버전을 찾지 못하거나 계약·접수 시스템을 조회하지 못하면 평가를 만들지 않습니다. 이때 `DATA_REPAIR` 업무(`DEPENDENCY_UNAVAILABLE`)를 만들고 청구를 `UNDER_REVIEW`로 두며, 응답은 `{"result": "HELD"}`입니다(명세 T15 「운영 중 조회 불능이면 평가 보류」).

### 7.6 지급 흐름 (A09–A11, 명세 8.3·9.2절)

```
A09 requestPayment (심사)
  ├ [트랜잭션] 지급 지시 RESERVED 또는 FAILED → REQUESTED, 전송 대기 기록(payment_outbox) PENDING
  └ [트랜잭션 뒤] 지급 시스템 submitPaymentRequest 호출 (같은 지급 키, 제한 3초)
       ├ 응답 PAID / FAILED → A10과 같은 처리로 결과 반영
       ├ 응답 REQUESTED     → REQUESTED 유지 (나중에 콜백이나 A11)
       └ 시간 초과·연결 실패 → UNKNOWN (새 지급 지시를 만들지 않음)
A10 recordPaymentResult (지급 연계 → 심사, 서명 확인)
  REQUESTED·UNKNOWN → PAID(청구도 PAID) / FAILED / UNKNOWN
  PAID에 같은 거래 ID가 다시 오면 기존 결과 반환, 다른 결과면 덮어쓰지 않고 거절 이력 (T24)
A11 reconcilePayment (심사 → 지급 조회)
  UNKNOWN·REQUESTED에서 지급 시스템을 지급 키로 조회
  ├ PAID / FAILED → 반영
  ├ REQUESTED     → 유지
  └ 기록 없음     → FAILED (지급 시스템이 받은 적 없음 = 미지급 확인, NOT_RECEIVED)
```

- **재시도:** `FAILED`에서 A09를 다시 하면 같은 지급 지시, 같은 지급 키로 보냅니다(T25). 지급 시스템은 지급 키가 같으면 새 요청을 만들지 않고 `attempt_count`만 올립니다. 이미 `PAID`인 키는 다시 지급하지 않고 기존 결과를 돌려줍니다.
- **한도:** `FAILED`에서도 한도 예약은 유지합니다(명세 8.3절).
- **서명:** A10 요청은 Bearer 인증 대신 `X-Payment-Signature` 헤더로 확인합니다. 값은 본문의 HMAC-SHA256이고, 비밀 값은 `INS_PAYMENT_CALLBACK_SECRET`입니다. 그래서 A10은 Studio 액션으로 쓰지 않습니다.

### 7.7 모의 지급 제어 (테스트 전용)

지급 시스템이 어떤 결과를 낼지 테스트에서 정하는 API입니다. OpenAPI 문서에 넣지 않으므로 Studio에는 보이지 않습니다. 인증은 지급 시스템과 같습니다.

| 경로 | 하는 일 |
|---|---|
| `POST /mock/outcomes` `{"outcomes": ["FAILED", "PAID"]}` | 다음 요청들의 결과를 순서대로 정함. 비어 있으면 `PAID`. `TIMEOUT`은 요청을 받아 두고(`REQUESTED`) 응답하지 않음, `LOST_RESPONSE`는 `PAID`로 처리하고 응답하지 않음 |
| `POST /mock/payment-requests/{request_no}/settle` `{"status": "PAID"}` | 받아 둔 요청의 결과를 나중에 확정 |
| `POST /mock/payment-requests/{request_no}/callback` | 현재 결과를 서명해 심사 시스템 A10으로 보냄. 두 번 부르면 중복 콜백(T24) |

### 7.9 Studio 액션 구성 참고 (구축 에이전트용)

액션의 대상은 **그래프에 적재된 인스턴스**여야 합니다(가상 노드 불가). 대상 클래스와 인자 연결 예시는 다음과 같습니다. 구축 에이전트가 실제 정의를 만들 때 참고합니다.

| Action | 대상 클래스 (`$this`) | 주요 인자 |
|---|---|---|
| A01 | 계약(또는 청구인) | 접수 내용은 `$params`. 2단계 `body.receipt_no` ← `$steps.<1단계>.response.receipt_no` |
| A02 | 청구 | 1단계 `path.receipt_no` ← `$this.receipt_no`, 보상 `path.attachment_id` ← `$steps.<1단계>.response.attachment_id` |
| A03 | 증빙 문서 | `path.doc_id` ← `$this.doc_id`, 확인값은 `$params` |
| A04, A05, A07, A08 | 청구 | `path.claim_id` ← `$this.claim_id`, A07·A08 `body.assessment_id` ← `$this.current_assessment_id` |
| A06 | 심사 업무 | `path.task_id` ← `$this.task_id` |
| A09, A11 | 지급 지시 | `path.payment_order_id` ← `$this.payment_order_id` |

모든 액션에서 `body.actor_id` ← `$params.actor_id`입니다(7.1).

`Idempotency-Key`는 OpenAPI에 필수 헤더로 보이지만 인자로 연결할 필요가 없습니다. 실행기가 단계마다 `계획:대상:단계:a시도` 키를 붙이고, 인자 매핑으로 같은 헤더를 넣더라도 실행기 값이 덮어씁니다(`dispatch.py`의 헤더 병합 순서).
