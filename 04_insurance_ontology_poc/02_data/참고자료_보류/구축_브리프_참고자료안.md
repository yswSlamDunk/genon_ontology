# 구축 브리프 2차: 문서로 추가 인제스천

1차로 구축한 「보험 청구 심사 온톨로지」에 **업로드 문서 4개**를 더하는 구축입니다. Studio에서는 이것을 **추가 인제스천**이라고 부릅니다. 구축 화면 「2 대상」의 목록에 `보험 청구 심사 온톨로지 (추가 인제스천)`으로 나옵니다.

목적은 청구 심사 앱에서 지금은 코드로만 보이는 값에 **이름, 근거, 다음 할 일**을 붙여 시연하는 것입니다.

| 앱에서 지금 | 이 자료를 더하면 |
|---|---|
| 의료기관 `H-001` | 가상한빛병원(병원, 서울특별시, 입원 진료 가능) |
| 규칙 R03 충족 | 근거: 약관 제6조(대기 기간) 본문 |
| 평가 사유 `MISSING_DOCUMENT` | 「필수 서류 누락」, 생기는 업무 「서류 보완」, 다음 업무 「보완 요청 → 서류 연결 → 확인 → 업무 해결 → 재평가」 |
| 청구 상태 `READY_FOR_DECISION` | 업무 지침의 「지금 할 일」: 승인 전 확인 4가지 → 지급 승인 또는 부지급 |

- 작성: 2026-11-04
- 자료 위치: [02_data/upload/](../02_data/upload/) (생성 스크립트 [02_data/make_upload.py](../02_data/make_upload.py))
- 모든 자료는 가상입니다. 각 문서 첫 줄과 「설명」 시트에 그렇게 적었습니다.

## 1. 업로드 자료

확장자 두 종류에 각 두 개입니다. 네 자료 모두 업무 시스템(DB)에는 없는 **참고 지식**이라, 시스템이 원본인 데이터(계약, 청구, 서류, 지급)와 겹치거나 충돌하지 않습니다.

| 파일 | 형식 | 내용 | 기존 온톨로지와 잇는 키 | 에이전트 처리 방식 (지침의 패턴) |
|---|---|---|---|---|
| `TEST-TERMS-A-1.0_입원일당A_약관.docx` | Word | 가상 약관 4장 14조와 부칙. 제4조–제9조, 제11조 끝에 「관련 심사 규칙: R0x」 | 약관 코드 `TEST-TERMS-A-1.0` = RuleSetVersion의 `clause_reference`, 규칙 R01–R07 | A: 문서 구조(장-조) → 노드 |
| `입원일당_청구심사_업무지침_v1.0.docx` | Word | 담당자별 업무, 청구 상태별 처리, 평가 결과별 조치, 승인 전 확인, 유의 사항 | 청구 상태(`RECEIVED` 등), 평가 결과(`PAYABLE_CANDIDATE` 등), 액션 A01–A11 | A·B: 구조 + 내용 |
| `의료기관_목록.xlsx` | Excel | 가상 의료기관 5곳(H-001–H-005): 기관명, 종별, 지역, 병상 수, 입원 진료 여부 | `provider_code` = 입원 사건·접수·서류 확인값의 의료기관 코드 | C: 표 → 노드 |
| `심사_사유코드표.xlsx` | Excel | 사유 코드 12개(관련 규칙, 판정, 결과 영향, 생기는 업무, 약관 조항, 안내, 다음 업무)와 심사 업무 유형 5개 | `reason_code`, `task_type` = 평가의 사유 코드, 심사 업무의 유형 | C: 표 → 노드 |

내용은 명세(2.3절 상품 규칙, 5.4절 사유 코드, 7장 평가, 8–9장 액션·상태)와 평가 엔진(`03_systems/services/evaluation.py`)의 실제 코드 값에 맞췄습니다. 약관 조항은 평가 규칙 R01–R07과 하나씩 대응하고, 새 규칙을 만들지 않았습니다.

## 2. 먼저 알아 둘 제약

앱의 구축 에이전트 지침(`skills/ontology-build/SKILL.md` 「스키마 그룹 관리」)에 이렇게 적혀 있습니다.

> `[대상 스키마]` 가 지정된 경우: 해당 스키마의 기존 클래스만 사용하여 엔티티를 생성하고, 새로운 클래스를 추가하지 마세요.

이 네 자료는 기존 17개 클래스에 들어갈 자리가 없습니다(의료기관, 약관 조항, 사유 코드, 업무 지침 모두 새 개념). 그래서 구축 의도에 **새 클래스 추가를 명시적으로 요청**했습니다(3.1절).

| 에이전트 반응 | 대응 |
|---|---|
| 새 클래스를 추가해 진행 | 그대로 진행 |
| "기존 클래스만 써야 한다"며 묻거나 멈춤 | 「이번 추가 인제스천에서는 구축 의도에 적은 새 클래스 추가를 허용한다. 기존 클래스·액션은 바꾸지 않는다」라고 답합니다 |
| 끝내 기존 클래스에 억지로 끼워 넣음(예: 의료기관을 InsuranceEvent 속성으로) | 중단하고 「2 대상」을 새 스키마(예: `보험 심사 참고자료`)로 바꿔 다시 구축합니다. 앱에서는 두 스키마의 클래스를 코드 값으로 이어 씁니다 |

## 3. 구축 화면 입력

| 단계 | 넣을 것 |
|---|---|
| 1 소스 | **문서**: `02_data/upload/`의 파일 4개를 끌어다 놓습니다. 데이터소스·시스템은 고르지 않습니다(기존 인스턴스는 이미 그래프에 있음) |
| 2 대상 | `보험 청구 심사 온톨로지 (추가 인제스천)` |
| 3 의도 | 아래 구축 의도, 골든 퀘스천 10개(`golden_questions_2차.txt`를 「파일에서 불러오기」), 골든 커맨드는 비워 둠 |

「의도」로 넘어가면 에이전트가 문서를 읽고 **초안**을 써 줍니다. 초안은 지우고 아래 내용으로 바꿉니다.

### 3.1 구축 의도

```text
기존 「보험 청구 심사 온톨로지」에 심사 참고 자료 네 가지를 더한다. 심사 담당자가 청구 화면에서 의료기관 정보, 판단 근거가 되는 약관 조항, 평가 사유의 뜻과 다음 할 일을 함께 보려고 쓴다.

이번 추가 인제스천에서는 아래 새 클래스를 추가하고 기존 클래스와 잇는 것을 요청한다. 기존 클래스·속성·인스턴스·관계·액션은 바꾸거나 지우지 않는다.
- 의료기관 목록(xlsx) → 의료기관(Provider). 키는 provider_code. 기존 InsuranceEvent, ClaimReceipt, DocumentVerification의 provider_code와 같은 값이다.
- 약관(docx) → 약관(Terms)과 조항(TermsArticle). 장-조 계층을 살리고, 조항의 「관련 심사 규칙」(R01–R07)을 조항 속성으로 둔다. 약관 코드 TEST-TERMS-A-1.0은 RuleSetVersion의 clause_reference와 같은 값이다.
- 사유 코드표(xlsx) → 사유 코드(ReasonCode)와 심사 업무 유형(ReviewTaskType). 사유 코드는 근거 약관 조항과 생기는 업무 유형에 잇는다. 이 코드는 기존 Assessment의 reason_codes, ReviewTask의 reason_code·task_type과 같은 값이다.
- 업무 지침(docx) → 업무 지침(Guideline)과 절(GuidelineSection). 청구 상태(RECEIVED, NEED_INFO, UNDER_REVIEW, READY_FOR_DECISION, APPROVED, PAID, REJECTED)와 평가 결과(PAYABLE_CANDIDATE, NOT_PAYABLE_CANDIDATE, NEED_INFO, MANUAL_REVIEW)별 조치를 찾을 수 있게 한다.

모든 자료는 가상이다. 참고 정보일 뿐이고, 지급 판단은 기존 심사 기준(RV-001)과 업무 시스템이 한다.
```

### 3.2 골든 퀘스천

1–6은 1차와 같은 질문입니다(기존 답이 그대로 나오는지 회귀 확인). 7–10이 새 자료를 쓰는 질문입니다.

| 번호 | 질문 | 쓰는 자료 |
|---|---|---|
| GQ1–GQ6 | 1차 브리프와 같음 | 기존 |
| GQ7 | 청구 CL-001의 입원 의료기관은 어디이고(기관명, 종별, 지역), 입원 진료를 하는 기관인가요? | 의료기관 목록 + 기존 입원 사건 |
| GQ8 | 심사 기준 RV-001의 규칙 R03(대기 기간)과 R07(지급 한도)은 약관 TEST-TERMS-A-1.0의 몇 조에 근거하고, 조항 내용은 무엇인가요? | 약관 + 기존 규칙 버전 |
| GQ9 | 사유 코드 MISSING_DOCUMENT가 나오면 어떤 심사 업무가 생기고, 담당자는 어떤 순서로 처리해야 하나요? 근거 약관 조항도 알려 주세요. | 사유 코드표 + 약관 |

## 4. 기대 답 (검수용)

| 번호 | 기대 답 |
|---|---|
| GQ1–GQ6 | 1차와 같음([구축_브리프_1차.md](구축_브리프_1차.md) 4절). 단, 1차 구축 뒤에 액션을 실행했다면 GQ5·GQ6의 상태와 한도 값이 바뀌었을 수 있습니다 |
| GQ7 | H-001 가상한빛병원, 병원, 서울특별시 가상구, 입원 진료 Y(병상 120) |
| GQ8 | R03 → 제6조(대기 기간): 보장 시작일로부터 30일이 지난 날 이후 입원에 지급, 입원일 ≥ 시작일 + 30일, 예: 2026-01-31 종료. R07 → 제8조(지급 한도): 보장 기간에 피보험자별 최대 5일, 남은 일수 = 5일 − 지급 일수 − 다른 청구 예약 일수, 결정 시점에 다시 확인 |
| GQ9 | 업무 EVIDENCE_REQUEST(서류 보완). 순서: 보완 요청(A05) → 서류 연결(A02) → 서류 확인(A03) → 업무 해결(A06) → 재평가(A04). 근거 제11조(청구 서류). 평가 결과는 NEED_INFO |
| GQ10 | 확인 4가지: 근거 평가가 현재 평가인지, 열린 심사 업무 0건, 받을 사람이 수익자(피보험자)인지, 한도는 승인 시 시스템이 재확인(평가 뒤 입력이 바뀌면 STALE_ASSESSMENT). 그다음 지급 후보면 지급 승인(A07), 부지급 후보면 부지급 결정(A08) |

검수할 때 같이 볼 것:
- **새 클래스와 기존 인스턴스의 연결:** H-001 의료기관 노드가 기존 입원 사건 EV-001과 실제로 연결됐는지(관계 또는 같은 키 값). 연결이 없으면 앱에서 이어 붙일 수 없습니다.
- **기존 정의 보존:** 기존 17개 클래스, 액션 10개(version 2)가 그대로인지. 구축이 끝나면 제가 그래프에서 대조합니다.
- **사유 코드 표기:** 사유 코드 노드의 코드 값이 평가 엔진이 쓰는 값(예: `MISSING_DOCUMENT`)과 철자까지 같은지.

## 5. 앱 수정 요청 (구축이 끝난 뒤)

기존 코드 앱 「청구 심사 화면」을 열고, 대화로 고치는 입력창에 넣습니다. `@` 뒤 클래스 이름은 **에이전트가 실제로 만든 이름**을 골라 칩으로 넣습니다.

```text
새로 적재한 참고 자료를 이 화면에 붙여 줘.
1. 사람·사건 영역: 입원 의료기관을 @Provider 에서 provider_code로 찾아 기관명, 종별, 지역, 입원 진료 여부를 보여 줘. 목록에 없는 코드면 "의료기관 목록에 없음"으로.
2. 계약·보장 영역: 규칙 R01–R07 판정마다 근거 약관 조항(@TermsArticle 의 조 번호와 제목)을 달고, 누르면 조항 본문을 펼쳐 줘.
3. 평가 영역: 평가의 사유 코드마다 @ReasonCode 의 사유 이름, 담당자 안내, 다음 업무를 보여 주고, 열린 심사 업무마다 업무 유형의 해결 방법을 보여 줘. 사유 코드가 없으면 이 영역은 "사유 없음"으로.
4. 맨 위 심사 상태 옆에 @GuidelineSection 에서 지금 청구 상태에 해당하는 「지금 할 일」을 한 줄로 보여 줘.
```

## 6. 시연 순서

| 장면 | 할 일 | 보여 줄 것 |
|---|---|---|
| 1. 전 | 앱에서 CL-001을 엽니다 | 의료기관이 `H-001` 코드로만, 규칙 판정에 근거 없음 |
| 2. 자료 추가 | 구축 화면에서 문서 4개를 올려 추가 인제스천 | 에이전트가 약관을 장-조로, 표를 행 단위로 읽어 적재. GQ7–GQ10 답 |
| 3. 후 | 5절 요청으로 앱을 고친 뒤 CL-001을 다시 엽니다 | 가상한빛병원, 규칙마다 약관 조항, 상태 옆 「지금 할 일」 |
| 4. 사유 코드가 나오는 청구 (선택) | 질의·액션에서 1차 GC1로 새 청구를 접수(H-003, 서류 없음) → 그래프 재적재 → 새 청구 평가 → 재적재 | 새 청구(CL-002 예상)가 NEED_INFO, 사유 `MISSING_DOCUMENT`, 「필수 서류 누락 → 보완 요청부터」, 가상새솔종합병원 |

장면 4는 실제로 DB를 바꾸고 재적재가 두 번 필요합니다. B0의 CL-001은 모든 규칙을 충족해 사유 코드가 나오지 않으므로, 사유 코드 안내를 보여 주려면 이 장면이 필요합니다. 시연 전에 미리 한 번 해 두고, 시연에서는 결과 화면만 보여 주는 것을 권합니다.
