# 구축 브리프 2차: 청구 시나리오 업로드 → 업무 시스템 반영

보험금 청구 서류를 Studio에 **업로드**하고, 그 내용으로 청구를 접수해 **업무 시스템 DB에 반영되는 것**을 확인합니다. 시나리오는 2개이고, 시나리오마다 Word 1개와 Excel 1개입니다.

- 작성: 2026-11-04
- 자료: [02_data/upload/](../02_data/upload/), 생성 스크립트 [02_data/make_scenario_upload.py](../02_data/make_scenario_upload.py)
- 모든 인물·의료기관·서류는 가상입니다.

## 0. 전체 흐름: 문서가 DB까지 가는 길

Studio에서는 업로드한 문서가 곧바로 DB에 들어가지 않습니다. 앱 코드에서 확인한 사실은 다음과 같습니다.

| 화면 | 파일 업로드 | 할 수 있는 일 |
|---|---|---|
| 온톨로지 구축 | 됨 (`allowsFiles: true`) | 문서를 읽어 **그래프에 적재**. 액션은 정의·dry-run까지만, 실행하지 않음 |
| 질의·액션 | 안 됨 (`allowsFiles: false`) | 그래프를 읽고 **액션을 실행**. 액션이 업무 시스템 API를 불러 **DB를 바꿈** |

그래서 아래 순서로 진행합니다. DB에 직접 넣는 단계는 없습니다. DB 변경은 모두 Studio 액션 → 업무 시스템 API로만 일어납니다.

```text
① 구축: 서류 4개 업로드 (추가 인제스천)
     → 그래프에 「미접수 제출 서류」 노드 4개 + 「청구서대로 접수」 액션 1개
② 질의·액션: "업로드한 청구서대로 접수해 줘"
     → 접수 시스템: 접수·서류 등록·연결  /  심사 시스템: 청구 등록   ← DB 반영
③ 구축: 재적재 (새 청구·서류를 그래프로)
④ 질의·액션: 서류 확인 → 평가 → 승인 또는 부지급                    ← DB 반영
⑤ 앱: 새 청구 2건을 엽니다
```

### 2.1 구축 의도

```text
기존 「보험 청구 심사 온톨로지」에 업로드한 청구 시나리오 자료(시나리오 1·2의 청구 서류 docx와 접수 자료 xlsx)를 더한다. 이 자료는 아직 업무 시스템에 접수되지 않은 제출 원본이다. 업로드한 서류의 내용으로 질의·액션에서 청구를 접수해 업무 시스템에 반영하려고 쓴다.

적재 규칙:
- 업로드 자료는 기존 Document(서류 원문) 클래스에 적재하고 새 클래스를 만들지 않는다. doc_id는 업로드 문서 번호(UP-S1-01, UP-S1-02, UP-S2-01, UP-S2-02), source_system은 upload, 접수 여부는 미접수로 둔다.
- 보험금 청구서(UP-S1-01, UP-S2-01) 노드에는 접수 자료 xlsx 「청구접수」 시트의 값(request_key, policy_number, coverage_code, submitter_no, patient_no, accident_no, provider_code, admission_date, discharge_date, intake_actor_id)과, 첨부된 입퇴원확인서의 storage_ref·content_hash를 속성으로 둔다.
- 입퇴원확인서(UP-S1-02, UP-S2-02) 노드에는 「제출서류」 시트의 storage_ref, content_hash, 추출값(extracted_*)과 신뢰도를 둔다. 추출값은 확인값이 아니다.
- 청구서와 입퇴원확인서는 request_key로 짝을 짓고, 청구인·입원한 사람은 기존 Claimant(청구인 번호)와, 계약은 기존 Policy(policy_number)와 잇는다.
- ClaimReceipt, InsuranceClaim, InsuranceEvent, DocumentVerification 같은 업무 시스템 원본 클래스에는 업로드 내용으로 인스턴스를 만들지 않는다. 그것은 액션을 실행해 업무 시스템이 만든다.
- 기존 클래스·인스턴스·관계와 액션 10개는 바꾸지 않는다.

업무 실행(골든 커맨드):
- 보험금 청구서 노드를 대상으로, 그 노드의 속성값으로 다음 다섯 단계를 실행한다.
  1) ins-intake createReceipt
  2) ins-review registerClaim (receipt_no ← 1단계 응답 receipt_no)
  3) ins-intake registerDocument (첨부 입퇴원확인서의 storage_ref·content_hash, document_type은 HOSPITALIZATION_CERTIFICATE)
  4) ins-intake attachDocument (path receipt_no ← 1단계 응답 receipt_no, doc_id ← 3단계 응답 doc_id)
  5) ins-review recordEvidenceAttached (path claim_id ← 2단계 응답 claim_id, doc_id ← 3단계 응답 doc_id)
- 보상: 1단계 cancelReceipt(receipt_no ← 1단계 응답), 4단계 revertAttachment(attachment_id ← 4단계 응답 attachment_id).
- 실행자 actor_id는 파라미터로 받는다(접수 담당자 intake-01). 파라미터 기본값에 기대지 않고, Idempotency-Key는 매핑하지 않는다. 정책 역할은 scm_operator.
```

업로드한 보험금 청구서 UP-S1-01의 내용대로 청구를 접수하고, 첨부된 입퇴원확인서를 그 청구에 연결해 줘. 접수 담당자 intake-01.

## 4. 앱 시연 (⑤)

④까지 마치고 한 번 더 재적재한 뒤 「청구 심사 화면」을 엽니다.

| 청구 | 보여 줄 것 |
|---|---|
| CL-002 | 업로드한 서류에서 온 접수, B 본인 청구, 지급 후보 금액(한도 반영 여부), 승인 후 지급 지시 |
| CL-003 | 청구자·입원자 A가 **계약자이지 피보험자가 아님**, R01 FAIL, 부지급 |
| CL-001 | 비교 대상. B의 첫 입원, 한도 사용 |

말할 수 있는 요지:
- 업로드한 서류가 그래프에 「미접수 서류」로 먼저 들어오고, 사람이 승인한 액션을 거쳐서만 업무 시스템에 접수됩니다.
- 서류의 추출값은 담당자가 확인(A03)해야 확인값이 됩니다.
- 같은 사람이 시스템마다 다른 번호(IP-0001 / C-10001)를 갖지만, 온톨로지가 같은 사람으로 이어 계약상 역할을 판정합니다.

## 5. 주의

- **새 클래스:** 업로드 자료를 기존 Document 클래스에 넣도록 해서 새 클래스가 필요 없게 했습니다. 추가 인제스천은 기존 클래스만 쓰는 것이 Studio 지침(`SKILL.md`)이라 그에 맞춘 것입니다. 에이전트가 청구서용 속성(request_key 등)을 Document에 더하는 것은 이 규칙과 충돌하지 않는 것으로 보지만, 결과를 확인합니다.
- **재적재:** 액션 뒤 재적재는 1차 구축 때 에이전트가 남긴 절차입니다. 액션 대상이 그래프에 적재된 복사본이라 필요한 수작업입니다.
- **자동 보상의 한계:** 2단계(청구 등록)가 성공한 뒤 3–5단계가 실패하면, 자동 보상 중 1단계 접수 취소(`cancelReceipt`)는 서버가 거절합니다. 청구가 있는 접수는 취소하지 않도록 서버를 만들었기 때문입니다(설계서 7.3절). 이때 청구는 남고 서류만 연결되지 않습니다. 같은 커맨드를 다시 실행해도 청구 등록 단계가 `ALREADY_REGISTERED`로 거절되고, 기존 「서류 교체」 액션은 교체할 서류가 있어야 합니다. 이런 일이 생기면 알려 주세요. 서류만 붙이는 방법을 따로 정하겠습니다.
- **되돌리기:** 모든 실행은 DB를 바꿉니다. 처음 상태로 돌리려면 `02_data/reset.sh`(B0) 뒤 그래프 재적재가 필요하고, 업로드 노드는 그래프에 그대로 남습니다.
- **보관한 자료:** 처음에 만든 참고 자료(약관, 업무 지침, 의료기관 목록, 사유 코드표)는 [02_data/참고자료_보류/](../02_data/참고자료_보류/)로 옮겨 두었습니다.
