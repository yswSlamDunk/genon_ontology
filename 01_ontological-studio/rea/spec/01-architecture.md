# 01. 아키텍처

## 1. 원본 구조 요약 [원본]
- 데스크톱 셸 1개가 하위 프로세스 9개를 띄움: 관계형 DB, Bolt 게이트웨이(네이티브), 포털 서버(Node), 분석 백엔드(Python), 검색 MCP 서버(Python), 액션 실행기(Python), 예제 업무 서비스 3개(Python).
- 저장소가 흩어져 있음: PostgreSQL(그래프·인스턴스·패브릭), SQLite 2개(온톨로지 정의·대화 / 액션 실행기), **앱 패키지 폴더**(대시보드), 데이터 폴더(코드 앱·작업 공간).
- 모든 서버가 127.0.0.1에 인증 없이 열려 있고, 같은 DB 슈퍼유저 계정을 공유.
- 근거: 분석 `common/A1-shell/design.md`, `A2-storage`, `A3-agent-mcp`, 각 메뉴 `design.md`.

### 2.1 구성 요소
| 구성 | 책임 | 원본 대응 |
|---|---|---|
| **데스크톱 셸** | 창·탭(원본 UX 유지), 하위 프로세스 감독(시작 순서·준비 확인·고아 정리·역순 종료), 로컬 게이트웨이, 앱 오리진, 네이티브 승인 창, OS 키체인 | 셸 + 로컬 웹 오리진 (A1) |
| **코어 서비스** | 아래 모듈들을 **한 프로세스**로. 모듈 경계는 코드 패키지로 유지(나중에 분리 가능) | 분석 백엔드 + 검색 MCP + 액션 실행기 + 패브릭 브리지 + 포털 서버 |
| ├ Ontology | 메타모델 CRUD, 검증, 변경 제안·이력, 발행(컴파일) | M1 스키마·발행, 포털 스키마 디자이너 |
| ├ Object | Object/Link 질의, Object set, 객체 식별·병합, 검색(벡터 포함) | 그래프 질의, 엔티티 해석 |
| ├ Action | 계획(dry-run)·승인·실행·보상·감사, 시스템 레지스트리 | 액션 실행기 (M2, M7) |
| ├ Data | 데이터소스 연결, 카탈로그, 백킹 데이터 미리보기, 동기화(색인) 작업 | 패브릭 브리지 (M3) |
| ├ Agent | 에이전트 선택, 모드별 도구, CLI 실행기, 내장 에이전트, MCP(내부·외부) | A3 |
| ├ Quality | 추출 게이트, 검수 대기열, 점검 | M6 |
| └ Apps | 대시보드 명세·위젯, 코드 앱 수명 주기, SDK 토큰 | M5 |
| **PostgreSQL 16** | 메타·런타임·감사 데이터 + 그래프 엔진 호스트 + FDW로 원천 연결 | 같음 (단, SQLite 2개를 PG로 통합) |
| **그래프 엔진** | Cypher 실행, 가상 노드(원천 읽기), 물리 노드, 시점 조회, 감사 | 원본 엔진 재사용 여부 [결정 대기 D-02] |
| **예제 업무 서비스** | 튜토리얼 재현용(erp·wms·crm). 선택 설치 | 같음 |

**원본 대비 단순화**: 하위 프로세스 9개 → **4개**(PG, Bolt 게이트웨이(재사용 시), 코어, 예제 서비스 묶음 1개). 포털은 별도 서버가 아니라 메인 UI의 한 화면(F4)이 되고 코어 API를 쓴다.

## 3. 저장소 설계 [제안]
**PostgreSQL 하나에 스키마로 나눈다**(원본의 SQLite·앱 폴더 저장을 없앰 — 백업·트랜잭션·데이터 폴더 격리 일관성).

| DB / 스키마 | 내용 |
|---|---|
| `workbench.meta` | 온톨로지 메타모델(02 문서의 모든 정의), 버전·제안·이력 |
| `workbench.runtime` | 대화·세션·메시지, 액션 계획·실행·단계·보상, 시스템 레지스트리, 대시보드 명세, 코드 앱 메타, 품질 대기열·판정, 동기화 작업 |
| `workbench.audit` | 감사 로그(누가·무엇을·언제·근거) — 추가만 가능 |
| `workbench.secret_ref` | 비밀 **참조**만(실제 값은 OS 키체인) |
| 그래프 (엔진 내부) | 발행된 객체 모델의 그래프 표현: 가상 타입·링크, 물리(색인) 객체, 발행 레지스트리 |
| 원천 연결 (FDW 스키마) | 데이터소스별 외부 테이블 (엔진/PG가 관리) |
| `sample` (선택) | 예제 업무 DB |

파일 저장(데이터 폴더): 업로드 문서, 대화별 작업 공간, 코드 앱 소스, 로그, 포트 파일. **앱 패키지 폴더에는 쓰지 않는다**(원본 결함 수정).

### 3.1 데이터 폴더
원본 A1 설계와 같은 구조·규칙(환경 변수로 위치 지정, 폴더당 인스턴스 1개, 끈끈한 포트, 단계 완료 표식, 고아 정리)을 유지한다. 차이: 비밀값 파일 대신 키체인, SQLite 파일 없음, 대시보드 폴더가 데이터 폴더 안.

## 4. 통신과 API
- UI ↔ 코어: REST(JSON) `/api/v1/...` + 스트리밍은 SSE. OpenAPI 문서를 코어가 생성 → 프런트·SDK 타입의 원천.
- **Object API (OSDK식)** [제안]: 발행된 온톨로지에서 자동 도출되는 엔드포인트 — `GET /api/v1/objects/{objectType}`(필터·정렬·페이지), `GET …/{pk}`, `GET …/{pk}/links/{linkType}`, `POST /api/v1/object-sets/query`(Object set DSL), `POST /api/v1/actions/{actionType}/plan|apply`. 대시보드·코드 앱·에이전트 도구·외부 MCP가 모두 이 API를 쓴다(원본처럼 각자 Cypher/SQL을 직접 만들지 않음).
- 에이전트 ↔ 코어: MCP(streamable HTTP), 모드별 엔드포인트, **턴별 일회용 토큰** 필수 (04 문서).
- 외부 AI 클라이언트 ↔ 코어: MCP, 사용자가 설정에서 켜고 발급한 토큰으로만(기본 꺼짐).
- 코어 ↔ 업무 시스템: Action 모듈만 호출. 시스템별 인증 정보는 키체인 참조.
- 코어 ↔ LLM: 설정된 공급자(OpenAI 호환 / Anthropic 등). 원본처럼 일부 기능이 다른 공급자를 몰래 직접 부르지 않도록 **LLM 호출은 Agent 모듈의 단일 클라이언트**를 거친다(원본 M6 결함 수정).

## 5. 부팅·종료
원본 순서를 따르되 단순화: 데이터 폴더·키체인 준비 → 고아 정리 → 포트 → PG 시작(첫 실행: 초기화·메타 스키마 마이그레이션·예제) → 그래프 엔진(·Bolt) → 코어(마이그레이션, 발행 모델 적재) → 예제 서비스(선택) → 게이트웨이 → UI. 진행 단계 표시·부팅 시간 기록·역순 종료·고아 정리 규칙은 원본 A1과 같다.

## 7. 관측성
- 로그: 구성 요소별 파일(원본과 같은 위치·형식) + 코어의 구조화 로그(JSON, 요청 id).
- 감사: 쓰기·발행·승인·실행·에이전트 도구 호출을 `audit`에 기록(actor = 사람/에이전트/시스템을 구분 — 원본은 에이전트 승인이 사람과 같게 기록되는 문제).
- 상태 API: 원본 `/app/status`와 같은 정보(단계, 시간, 포트, PID) — 토큰 필요.

## 8. 확장성 경계
