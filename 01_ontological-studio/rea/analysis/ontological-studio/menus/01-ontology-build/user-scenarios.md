## S1. 구축 탭 열고 구성 보기
- **목적:** 구축 화면의 영역과 기존 예제 온톨로지를 확인한다.
- **단계:** 홈에서 「온톨로지 구축」 카드를 누른다.
- **기대 결과:**
  - 왼쪽 레일(온톨로지 구축·질의·액션·대시보드·품질 검수·데이터소스·시스템 등록·Ontological Portal), 그 옆 「온톨로지 구축」 워크스페이스(설명 문구 「문서를 분석하고 스키마, 엔티티, 관계를 생성하는 작업 모드입니다.」, 「+」 새 대화, 구축 대화 목록 — 각 행에 스키마 이름 배지·제목·날짜·× 삭제), 아래 파일 패널, 맨 아래 「초기화」.
  - 가운데: 대화가 비어 있으면 **구축 브리프**(3단계 「소스 · 대상 · 의도」), 대화가 있으면 대화창.
  - 오른쪽: 「온톨로지 그래프」 패널, 탭 「그래프 · 정보 · 배포 · 검수(배지=확인 필요+보류 건수)」. 그래프 탭에 예제 스키마 지도(클래스 7, 관계 6).
- **기록할 것:** 첫 로딩 요청 순서(`/api/sessions`, `/api/sessions/default/messages?mode=…`, `/api/files`, `/api/neo4j/status`, `/api/schema`, `/api/graph?limit=0`, `/api/schemas`, `/api/graph?limit=200`, `/api/datasources`, `/api/act/systems`)와 응답 형식, 화면 캡처.

## S2. 브리프 1단계 「소스」 — 문서 업로드·데이터소스·시스템 선택
- **목적:** 구축 재료를 고른다.
- **단계:**
  1. 「+ 파일 업로드 (드래그 앤 드롭 가능)」에 실습 문서를 끌어 놓는다.
  2. (선택) 데이터소스 칩(`crm`/`erp`/`wms`)을 눌러 고르고, 펼쳐진 스키마 칩을 고른다.
  3. (선택) 「시스템 (서비스)」 칩(`sample-erp` 등, `API n` 표시)을 고른다.
- **기대 결과:**
  - 업로드 칩에 파일 이름·크기. 단계 표시에 요약(`문서 1개 · erp · 시스템 1개`).
  - 아무것도 안 고르면 안내 「문서·데이터소스·시스템 중 1개 이상 선택하세요.」
  - 데이터 패브릭에 못 닿으면 「데이터 패브릭에 연결되지 않아 데이터소스를 선택할 수 없습니다. 문서만으로 진행합니다.」
  - 소스가 바뀌면 약 0.9초 뒤 **브리프 초안 요청**이 자동으로 나간다(S4).
  - 소스 조합이 바뀔 때마다 **권장 전략** 요청(`/api/build-strategy/recommend`)이 나간다.
- **기록할 것:** 업로드 요청(multipart `files`, `session_id`)과 응답, 사용자 데이터 폴더 `sandbox/sessions/<세션>/uploads/`와 `sandbox/uploads/`에 같은 파일이 생기는지.

## S3. 브리프 2단계 「대상」 — 새 스키마 또는 추가 인제스천
- **단계:** 「새 스키마 생성」을 고르고 이름 `협력사 품질 온톨로지` 입력. (변형) 목록에서 「공급망 운영 (예제) (추가 인제스천)」 선택.
- **기대 결과:**
  - 안내 「기존 스키마를 고르면 그 스키마의 클래스만 사용해 추가 인제스천합니다. 이름을 비워 두면 구축 의도에 맞춰 새로 만듭니다.」
  - 기존 스키마를 고르면 그 스키마의 구축 의도·골든 퀘스천·골든 커맨드가 3단계에 채워진다(예제: 질문 3, 커맨드 4).
  - 단계 요약: `새 스키마 「협력사 품질 온톨로지」` 또는 `공급망 운영 (예제) (추가)`.

## S4. 브리프 3단계 「의도」 — 에이전트 초안, 골든 퀘스천·커맨드 (튜토리얼 11·12)
- **목적:** 구축 의도와 골든 퀘스천(필수), 골든 커맨드(선택)를 확정한다.
- **단계:**
  1. 「의도」로 넘어가 초안이 채워지기를 기다린다(튜토리얼 실측 약 50초).
  2. 골든 퀘스천을 하나 추가: `납땜 불량이 난 부품은 어느 완제품에 들어가고, 그 협력사의 담당자는 누구인가?`
  3. (선택) 「파일에서 불러오기」로 한 줄 한 질문 텍스트 파일을 넣는다. 「초안 다시 생성」.
  4. (선택) 골든 커맨드 추가.
- **기대 결과:**
  - 초안 생성 중: 「에이전트가 소스를 살펴보고 초안을 만드는 중입니다. 그동안 직접 입력해도 됩니다.」
  - 완료: 「아래는 에이전트 초안입니다. 그대로 쓰지 말고 고쳐 주세요.」, 의도·질문 칸에 「에이전트 초안」 배지, 질문마다 「근거: <테이블.컬럼 또는 문서>」.
  - 사용자가 이미 쓴 칸은 덮어쓰지 않고 안내 「직접 입력한 항목은 그대로 두었습니다 — 구축 의도 · Golden Question.」 초안 칸을 고치면 배지가 사라진다.
  - 실패: 「초안을 만들지 못했습니다 — 직접 입력해서 그대로 진행할 수 있습니다.」 + 오류(예: 「에이전트가 초안 형식(ontology_brief_draft)을 반환하지 않았습니다.」, 404면 「초안 생성 경로를 찾지 못했습니다 (404)…」).
  - 「권장 전략」 상자: 추천 전략 이름·이유, 쓸 수 없는 전략과 사유, 「권장은 강제가 아닙니다…」.
  - 의도와 질문 1개 이상이 있어야 「이 브리프로 구축 시작」이 켜진다. 아니면 「구축 의도와 Golden Question을 최소 1개 입력하면 구축을 시작할 수 있습니다.」
- **기록할 것:** `POST /api/build-brief/draft` 요청·응답(`intent`, `questions[{question,evidence}]`, `note`, `error`), 초안 에이전트 CLI 명령줄(brief_draft 브리지), 소요 시간.

## S5. 구축 시작 — 대화창 스트리밍 (튜토리얼 12 3단계)
- **단계:** 「이 브리프로 구축 시작」을 누른다. 진행 중 대화창에 「범위를 Supplier, Component만으로 좁혀」를 입력해 ➤로 보낸다(끼어들기). (변형) 「중단」.
- **기대 결과:**
  - 사용자 말풍선 「구축 의도와 Golden Question을 기준으로 온톨로지 구축 시작」(입력란이 비었을 때), 상태 문구 `온톨로지 구축 에이전트를 시작합니다... (N개 Golden Question)`.
  - 도구 칩이 흐름: 칩 종류 `ONTOLOGICAL`(스키마·그래프 도구) / `DATA`(데이터소스 도구) / `TOOL`, 한국어 한 줄 설명(예 「클래스 'Supplier' 를 생성합니다」), 「실행 중...」 → ✓, 「입력 보기」·「결과 보기」.
  - 스키마 그룹이 만들어지면 세션에 스키마 이름이 붙고(목록 배지), 스키마·그래프 도구가 끝날 때마다 오른쪽 그래프가 갱신된다.
  - 같은 이름의 클래스가 이미 있으면 에이전트가 병합/분리를 묻는다(튜토리얼 — 「분리」로 답함).
  - 끼어들기: 「작업 중 지시」 표시, 상태 「사용자 지시를 반영해 방향을 바꿉니다...」 (Claude Code만 전달됨).
  - 중단: 「[중단됨] "계속해"를 입력하면 이어서 진행합니다.」
  - 끝: 진행 상황 4단계 완료(Phase 1 스키마 설계 / Phase 2 소스 파싱 + 적재 / Phase 3 검증 / Phase 4 검수), 출력 파일 버튼(`_schema_design.json`, `_parsed_*.json`, `_search_hints.json` 등). 실측 약 6분.
- **기록할 것:** `/api/stream` 쿼리(`prompt`, `session_id`, `mode=build`, `build_context` JSON)와 SSE 이벤트 순서·필드, 에이전트에 간 라벨 블록 프롬프트(로그 `effective_prompt`), 그래프·SQLite 변화(전후 비교).

## S6. 구축 보고서와 골든 퀘스천 검수 → 피드백 반영 재구축
- **단계:**
  1. 보고서 카드 「Golden Question 검수」에서 질문마다 「맞다」/「틀리다」를 누른다.
  2. 「틀리다」 질문에 부족한 점을 적고 「피드백 반영 요청」.
- **기대 결과:**
  - 카드: 「이 구축 결과가 각 Golden Question에 답할 수 있는지 확인해 주세요.」, 질문·답 초안·상태(답변 가능 / 부분적으로 답변 가능 / 아직 답변 어려움)·신뢰도(높음/보통/낮음).
  - 「틀리다」가 하나 이상이고 모두 피드백이 있어야 버튼이 켜진다.
  - 반영 요청: 사용자 말풍선 「Golden Question 검토 피드백 반영 요청」, 같은 세션에서 build 턴이 다시 돌고 프롬프트에 `[검토 피드백]` 블록.
  - 보고서 아래 검수 현황 줄 「🙋 확인이 필요한 내용 N건 · 🗂️ 보류 M건 — 사람이 판단해야 지식 지도에 들어갑니다.」 + 「검수 탭에서 보기」(오른쪽 검수 탭으로 전환).
- **기록할 것:** `done.build_report` 형식(`intent, summary, next_action, golden_questions[{question,answer,status,confidence}], golden_commands[], quality{…}`), 피드백 턴의 `build_context.review_feedback`.

## S7. 만들어진 온톨로지 보기·고치기 (튜토리얼 12 4단계)
- **단계:**
  1. 그래프 탭: 「스키마」/「엔티티」 전환, 배치(Force (CoSE)·Circle·Concentric·Tree·Grid), 이름 검색, 노드 펼치기.
  2. 정보 탭: 스키마 선택, 클래스 ✎ 편집(이름·설명·속성 이름/타입 string·integer·float·boolean·date·list), 「+ 클래스 추가」, 「+ 관계 추가」, 삭제.
- **기대 결과:**
  - 정보 탭 「온톨로지 스키마」: 클래스별 인스턴스 수, 가상 클래스는 「가상」 배지(툴팁 데이터소스/테이블), 속성 줄(타입, `← 원천 컬럼`, PII, `*`).
  - 클래스 삭제 확인: 「클래스 X 을(를) 삭제하시겠습니까?\n\n⚠ 이 클래스의 엔티티 N개와 관련 관계 타입도 함께 삭제됩니다.」
  - 이름 바꾸기는 모든 스키마 그룹의 정의와 그래프 라벨을 함께 바꾼다.
  - 스키마 메뉴: 「엔티티 삭제」(정의 보존), 「스키마 복원 (Neo4j)」(현재는 개수만 돌려줌), 「이 온톨로지로 대시보드를 자동 구성합니다」(M5로 이동).
- **기록할 것:** `PUT /api/schema/classes`(rename 포함), `PUT /api/schema/relationships`, 삭제 요청, 그래프 라벨 변화.

## S8. 발행 — 대화로 「발행해 줘」 (튜토리얼 12 5단계)
- **단계:** 구축 대화창에 `발행해 줘` 입력.
- **기대 결과:**
  - 화면에 발행 버튼은 없다. 에이전트가 발행 도구를 부르고 반영 결과(클래스·관계·behavior·액션 수, 제약)를 보고(실측 약 50초).
  - 발행 후 질의·액션 탭에서 같은 골든 퀘스천에 답(SC-100, 김민수 대리)과 근거.
  - 발행 전 질의하면 「발행된 온톨로지가 없다」(FAQ).
- **기록할 것:** 발행 후 `ontology` 그래프의 `_OntologyModel`/`_OntologyClass`/`_OntologyRelationship`/`_OntologyBinding`/`_OntologyBehavior` 노드와 `ont_pub_*` 제약, 실행기 카탈로그 갱신 호출.

## S9. 골든 커맨드로 액션 만들기 (튜토리얼 15)
- **단계:**
  1. 새 대화 → 소스: 시스템 `sample-erp`만 선택.
  2. 대상: 「공급망 운영 (예제)」(추가 인제스천).
  3. 의도의 Golden Command에 `한빛정밀의 미결 발주를 모두 보류해 줘 (사유: 단가 재협상)` (또는 새 액션이 생기는 `납기가 늦어지는 발주의 품목을 산 고객에게 지연 안내를 보내 줘`).
  4. 「이 브리프로 구축 시작」.
- **기대 결과:**
  - 프롬프트에 `[연결 시스템]`, `[실행 역할]`(`scm_operator`), `[골든 커맨드]`; 문서·데이터소스가 없으면 `[인스턴스 원천] 등록 시스템의 조회 API (system_query)`.
  - 에이전트가 시스템 목록 → API 목록 탐색 → 액션 생성(단계·보상·정책) → 발행 → dry-run. 이미 같은 일을 하는 액션이 있으면 「기존 액션으로 충족」 보고.
  - 보고서 「Golden Command」 표(커맨드 · 액션 `Class.action` · 단계 `a → b` · 검증 「✓ dry-run」/「미검증」). 취소형 커맨드는 「보상(역순)」. 검증 여부는 저장소 기록으로 정해진다.
  - 실측 약 4분 반. 실행·승인은 일어나지 않는다.
- **기록할 것:** 생성된 액션 정의(정책·단계·보상·`golden_command`·`verified_at`), dry-run plan 요약, 발행물의 액션 노드.

## S10. 테이블 구조로 바로 생성 (화면 기능, LLM 불필요)
- **단계:** 소스에서 데이터소스+스키마(예 `erp`/`erp`) 선택 → 「테이블 구조로 바로 생성」 상자에서 대상 고르고 「미리보기」 → 「이대로 생성」.
- **기대 결과:** 미리보기 「이 계획으로 생성하면 아래 클래스와 관계가 만들어집니다.」 + 클래스/테이블/속성/키, 관계/출발/도착 표. 생성 후 「생성 완료 — 클래스 N개, 관계 M개. 가상 클래스로 바인딩되어 바로 조회할 수 있습니다.」 카탈로그가 비면 오류 「카탈로그에 'erp' / 'erp' 테이블이 없습니다. 데이터 패브릭에서 메타데이터 추출을 먼저 실행하세요.」
- **주의:** 이 패키지에서 카탈로그 그래프가 있는지 불명(모르는 점) — 오류가 기대 결과일 수 있음.

## S11. 클래스-데이터소스 바인딩과 behavior (정보 탭 ⛁ 「데이터 연결」)
- **단계:** 정보 탭에서 클래스의 ⛁ → 「바인딩」 탭: 데이터소스·스키마·테이블 선택, 샘플 행, 컬럼→속성 매핑(포함·속성명·타입·키·PII), 기본 조회조건, 라벨 속성 → 저장. 「동작(Behavior)」 탭: 이름·설명·대응 Golden Question·파라미터·SQL 템플릿 → 「테스트 실행」/「저장」.
- **기대 결과:** 「저장했습니다.」(패브릭 불통이면 「…컬럼 검증은 건너뛰었습니다」), behavior 저장 시 「저장했습니다. (실제 실행으로 검증됨)」 또는 「(기본값이 없어 실행 검증은 건너뛰었습니다)」. 클래스가 「가상」으로 바뀜.
- **주의(정적 분석):** behavior 실행은 원천 직접 SQL 경로를 쓰는데, 이 패키지의 패브릭 브리지는 임의 SQL을 501로 거절한다 → 테스트 실행·검증이 「실행 실패 (HTTP 501)」일 가능성이 높다. 실행 기록에서 확인.

## S12. 액션 편집기로 직접 만들기·dry-run (정보 탭 ⛁ → 「액션」 탭, 튜토리얼에 없음)
- **단계:** 예제 `Shipment`의 ⛁ → 「액션」: 칩 `expediteShipment v1` 눌러 보기 → 「+ 새 액션」으로 이름·설명·단계(시스템·Operation·인자 매핑·보상)·파라미터(JSON Schema)·정책·효과·승인 임계치·대상 상한·키 속성·성공 시 기록할 속성 입력 → 「저장」 → 「Dry-run (발행된 정의 기준)」에서 조건(속성·연산자·값)·파라미터 → 「계획 만들기 (dry-run)」.
- **기대 결과:**
  - Operation을 고르면 인자 줄이 그 API의 path/query/header/body 필드로 자동 채워지고 기본값 제안(`path.*`=`$this.$key`, `reason`=`$params.reason`, `requestedBy`=`$actor.sub`; 보상은 `reason`=`$cancel.reason`, `status`=`$before.status` 등).
  - 저장: 「저장했습니다 (vN). 발행하면 실행기에 반영됩니다.」 + 경고(시스템/operation 없음, 보상 없는 단계, 정책 없음).
  - 발행 전 dry-run: 「실행기가 이 액션을 모릅니다 — 스키마를 발행했는지 확인하세요.」
  - 발행된 액션 dry-run: 실행 계획 카드(허용/거부 건수, 사람 승인 필요, 대상 표, 호출 미리보기) — 카드에 「승인」·「실행」 버튼이 있다(M2 경계, notes 참조).
  - 실행기 불통: 「kinetic-action 에 닿지 못했습니다 (<url>). 정의는 저장되지만 시스템·operation 목록과 dry-run 은 쓸 수 없습니다.」
- **기록할 것:** `PUT /api/schema/classes/{c}/actions/{a}` 요청·응답(`action`, `warnings`, `version`), `POST /api/act/plans` 응답.
- **주의:** 카드에서 「승인」·「실행」을 누르면 예제 업무 DB가 실제로 바뀐다. 이 시나리오에서는 누르지 않는다.

## S13. 문서+데이터소스 — 역바인딩 (전략 1, 정보 탭 패널)
- **사전:** 문서로 클래스를 만든 스키마가 선택돼 있고 브리프에 데이터소스 스키마가 골라져 있음.
- **단계:** 정보 탭 「문서 엔티티 → 데이터소스 역바인딩」 → 「미리보기」 → 판정(자동/검토필요/충돌/매칭없음)별 후보 선택 → 「확정 바인딩」.
- **기대 결과:** 「미리보기입니다. 아직 저장되지 않았습니다.」, 결과 「바인딩 N개 완료.」「확인이 필요해 건너뛴 항목 K개.」「미바인딩 U개는 그대로 남습니다.」 충돌 안내 「충돌 — 테이블 A 을 X 가 함께 지목했습니다. 어느 쪽인지 고르지 않으면 바인딩하지 않습니다.」

## S14. 인과 가설 검토 (전략 2, 정보 탭 패널)
- **단계:** 「인과 가설 검토」 → 「발견 실행」 → 가설마다 승인/거부/방향반전 → 「관계로 승격」.
- **기대 결과:** 이 패키지에는 통계 서비스가 없어 권장 전략에 「통계 서비스에 연결할 수 없습니다」가 뜨고 발견이 실패할 것으로 추정. 동작하면 「가설 N건. 승인 전에는 관계가 되지 않습니다.」, 승격 후 「관계 N개 승격.」

## S15. 검수 탭 (구축 화면 안의 품질 검수 요약 — M6와 공유)
- **단계:** 오른쪽 「검수」 탭 → 온톨로지 선택 → 「🙋 확인하기」/「🗂️ 보류함」.

## S16. 배포 탭 (개발 → 운영 릴리스, 튜토리얼에 없음)
- **단계:** 오른쪽 「배포」 탭 → 개발/운영 스키마 버전·변경 이력 확인 → 「패키지 만들기」 → 「계획 보기」 → 「운영에 적용」.
- **기대 결과:** 개발 쪽은 포털 관리 API에서 스키마 버전·이력. 운영 쪽은 기본 설정에 운영 DB가 없어 오류 표시(추정). 패키지 만들기는 성공할 수 있으나 적용은 실패할 것으로 추정.
- **기록할 것:** `/api/release/overview` 응답, 패키지 파일 저장 위치.

## S17. 대화 관리와 초기화
- **단계:** 「+」 새 대화, 다른 대화 선택, × 삭제, 파일 패널에서 파일 열기/삭제, 「초기화」에서 「샌드박스 파일시스템」·「Ontological 데이터」 체크 → 「선택 항목 초기화」.
- **기대 결과:**
  - 새 대화 제목 「새 대화」 → 첫 메시지 후 앞 30자로 바뀜. 대화 전환 시 그 대화의 메시지·파일·스키마 필터 복원.
  - 초기화 확인 「다음 항목이 초기화됩니다:\n- 샌드박스 파일시스템\n- Ontological 데이터\n\n정말 초기화하시겠습니까?」. 「Ontological 데이터」는 `ontology` 그래프 **전체**를 지운다(예제 인스턴스·발행물 포함).
- **주의:** 「Ontological 데이터」 초기화는 되돌릴 수 없고 질의·액션·앱이 모두 영향을 받는다. 스냅샷 후에만.

## 튜토리얼에 없어 확인한 것 (정적 분석 결과)
- 오른쪽 패널 4탭(그래프·정보·배포·검수)은 「질의·액션」 화면에서도 똑같이 보인다(같은 레이아웃). 따라서 정보 탭의 액션 편집기는 질의·액션 탭에서도 열린다.
- 화면에 발행 버튼은 없지만 HTTP 발행 API는 있다(`POST /api/schema/{id}/publish`, 화면 미사용).
- 문서 OCR·청크 인덱싱 모듈은 들어 있지만 구축 흐름에 연결돼 있지 않다(전처리 이벤트를 내는 코드가 없음). 문서는 에이전트가 직접 파일로 읽고 파서를 작성한다.
- 그래프 탭의 「자연어로 질문」은 OpenAI API 키를 직접 쓴다 — CLI 에이전트만 있으면 「LLM 호출 실패」.
