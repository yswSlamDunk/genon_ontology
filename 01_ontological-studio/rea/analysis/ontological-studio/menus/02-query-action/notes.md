# M2 질의·액션 — 메모 (보안·품질·다른 대상·열린 질문)

## 1. 보안 질문에 대한 답: 에이전트가 사람 승인 없이 승인·실행할 수 있는가 (A3 제기)

**결론: 설계(도구·토큰) 수준에서는 분리돼 있으나, 프로세스 수준에서는 우회가 가능한 조건이 모두 갖춰져 있다. 실제 우회는 실행 검증하지 않았다(추정).**

관찰(코드 확인):
- 에이전트 도구 표면 3곳(백엔드 브리지 act, 내장 act, 실행기 MCP) 어디에도 승인 도구가 없다.
- 에이전트 도구는 `KINETIC_AGENT_TOKEN`(sub `lite-agent`, roles `[scm_operator]`)을 쓴다. 실행기 승인은 `kinetic_approver`를 요구 → 도구 경로로는 403.
- 화면 승인은 백엔드 `POST /api/act/plans/{id}/approve` → `KINETIC_STUDIO_TOKEN`(sub `lite-user`, roles `kinetic_admin, kinetic_approver, scm_operator`).
- 실행은 작성자만. 에이전트 계획 = 에이전트만 실행, 승인 필요면 승인 후에만.
- **실행기에 직무 분리가 없다** — 승인자가 작성자와 같아도, 누구든 approver 역할만 있으면 승인.
- **Studio 백엔드에 인증이 없다**(127.0.0.1, CORS `*`). 백엔드 승인 프록시를 부르는 아무 로컬 프로세스나 `lite-user`로 승인된다.
- CLI 에이전트(Claude Code `bypassPermissions` / Codex `--dangerously-bypass-approvals-and-sandbox`)는 백엔드 환경 전체를 상속: `KINETIC_STUDIO_TOKEN`, `KINETIC_URL`, `BACKEND_PORT`, `NEO4J_PASSWORD`(PG 슈퍼유저). 브리지 MCP URL에도 백엔드 포트가 있다.
- 사용자 데이터 폴더의 `secrets.json`(0600, 같은 OS 사용자)에 토큰 서명 개인키(`kineticKey`)·PG 비밀번호가 있다. 에이전트 작업 폴더는 그 하위(`sandbox/sessions/<id>`).
- 코드 앱 경로의 "브라우저에서만 승인" 검사는 `Sec-Fetch-Mode` 헤더 **존재 여부**뿐(curl로 위조 가능), 그리고 Studio 백엔드 직접 경로에는 그 검사조차 없다.

추정(실행 검증 안 함):
- 에이전트가 셸로 (a) `curl -X POST http://127.0.0.1:$BACKEND_PORT/api/act/plans/<id>/approve`, (b) 실행기 REST approve를 `$KINETIC_STUDIO_TOKEN`으로, (c) 개인키로 approver 토큰 발급 — 어느 것으로든 자기 계획을 승인한 뒤 `execute_plan` 도구로 실행 가능. 더 나아가 화면 토큰으로 계획·승인·실행을 모두 할 수도 있다.
- 감사 기록은 `approve / actor_sub=lite-user`로 남아 사람 승인과 구별 불가.
- 유일한 방어는 스킬 지시문의 "승인을 우회하지 않습니다". 프롬프트 주입(예: 업무 시스템 응답·그래프 속성에 심은 지시문)에 취약할 수 있다.
- 내장 에이전트(deepagents)의 act 모드에는 셸 도구가 없어 이 경로는 없다(단 build 모드 `execute`는 같은 환경의 호스트 셸).
- 브라우저발: CORS `*`라 다른 웹 페이지도 백엔드 승인 프록시를 부를 수 있으나 plan id(무작위 16 hex)와 포트를 알아야 해 현실성 낮음.

권고는 design.md §9.3.

## 2. 튜토리얼·문서와 0.1.1 차이
- 13장 "예제 온톨로지의 골든 퀘스천·골든 커맨드가 예시로 나옵니다" — 0.1.1은 화면에 **고정된 예시 4개**(온톨로지와 무관).
- 13장 "문서를 끌어다 놓으면(📎) 대화에 첨부" — 0.1.1 act 모드는 `allowsFiles:false`(첨부 꺼짐). 구축 화면에서만 첨부.
- 16장 "만료 — 지나면 같은 조건으로 다시 계획" — 자동이 아니라 에이전트가 `plan_expired`를 받고 재계획(지시문 규칙).
- 액션 실행기 연결 실패 힌트 문구가 "kinetic-action(8030)과 api-gateway(9000)"를 말하지만 0.1.1은 게이트웨이 없이 동적 포트(M7과 같은 낡은 문구).
- 스킬 예시(설비·점검 모드·MES/CMMS/APS)는 예제 공급망 도메인과 다르다(지시문 일반 예).

## 3. 품질 관찰
- 대화 삭제/초기화가 act 모드의 내장 에이전트 체크포인트를 지우지 않는다(build·answer만). CLI 세션 기억은 지운다.
- 계획 만료는 조회할 때만 `expired`로 바뀐다 — 카드가 「승인 대기」로 남아 있다가 승인 누르면 409.
- 실행기 REST에 반려(reject)·재시도(retry)·run 목록·감사 조회가 있지만 Studio 화면에는 없다. 감사 로그를 볼 화면이 없다.
- 되쓰기 값이 "첫 단계 응답의 status 또는 done"이라 액션에 따라 의미 없는 값이 그래프에 쓰일 수 있다(모르는 점).
- 예시 버튼 문구가 예제 데이터에 고정돼 있어 다른 온톨로지에서는 엉뚱하다.

## 4. 다른 대상 메모
- M5: 대시보드·코드 앱 버튼은 같은 `/api/act/*` 프록시를 쓰고 작성자 = 화면 신원이라 카드에서 바로 실행 가능(채팅과 달리 에이전트 "실행해" 불필요). 코드 앱 가드는 헤더 존재 검사뿐.
- M1: 구축 중 골든 커맨드 드라이런은 에이전트 토큰으로 계획(정책 판정이 실제 실행 주체 기준) — 그 계획들도 실행기 DB·감사에 남는다(확인 필요).
- A3: answer/act 브리지 도구 목록의 "검색 서버 기동 경쟁" 문제는 act에도 그대로 적용.
- M7: 실행기 MCP는 DNS 리바인딩 보호를 끄고 Bearer 필수.

## 5. 열린 질문 (사용자 결정)
- 새 구현에서 원본의 "공용 화면 신원 + 무인증 백엔드" 모델을 재현할지, 사람 승인 증거(일회용 토큰·네이티브 확인)를 추가할지.
- §1의 우회 가능성을 4단계에서 실제로 시험할지(분석용 폴더, 예제 시스템만 영향). 시험한다면 최소 확인: CLI 자식 프로세스 환경 변수 목록.
