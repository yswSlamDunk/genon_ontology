# M7 시스템 등록 — 메모 (다른 대상·보안·품질·열린 질문)

## 1. 비밀 값 공급 — studio.env 경로가 없음 (중요)
- 튜토리얼 14: "여러분이 등록하는 시스템의 비밀 값은 `studio.env`에 `ERP_API_KEY=...`처럼 적어 두면 됩니다."
- 0.1.1 코드: 셸이 내장 kinetic-action을 띄울 때 환경 = 앱 프로세스 환경 + 예제 비밀 3개(`ERP_API_KEY`, `WMS_BASIC`, `CRM_TOKEN`) + `KINETIC_*` 설정. `studio.env` 읽기는 Studio 백엔드 환경 조립에만 쓰이고 실행기에는 쓰이지 않는다. 실행기는 `PYTHON_DOTENV_DISABLED=1`, cwd=userData라 스스로 .env를 읽지도 않는다. 비밀 해석·연결 테스트의 `missing_env`는 실행기 `os.environ`만 본다.
- 결론(정적 분석): **studio.env로는 등록 시스템의 비밀을 공급할 수 없다.** 유일한 우회는 앱을 띄우는 셸(터미널)에 환경 변수를 export한 뒤 실행(Finder 실행은 불가). A3/M8 분석 결과와 일치. 4단계에서 실측 확인.

## 2. 튜토리얼·문서와 0.1.1 불일치
- 헬스 404/405 → 「연결됨 · 경고」 주황 `~`: 0.1.1 번들에 없음. 3xx 이상 모두 실패.
- 헬스 경로 비우기: 비우면 `/health`로 대체(튜토리얼은 활성 주소 자체 점검이라 함). Petstore 연습이 튜토리얼대로 통과하지 않을 가능성.
- `studio.env.example`: "kinetic-action은 이 패키지에 들어 있지 않다" — 0.1.1은 내장.
- 화면 안내 "게이트웨이가 …": 0.1.1은 게이트웨이 없이 실행기 직접 호출.
- 정책 「재시도」: 직접 모드 호출에서 시스템별 retries 미적용.

## 3. 보안·품질 관찰
- 같은 이름으로 「+ 시스템 등록」 하면 경고 없이 기존 등록을 덮어씀.
- 사용 중 시스템 삭제 허용(사후 경고만). 예제 시스템은 재시작 시 다시 등록됨.
- 실행기→업무 시스템 호출에 내부 비밀 헤더(`X-Kinetic-Internal`)가 함께 전송됨 — 사용자가 등록한 외부 시스템에도 실행기 내부 비밀이 노출될 수 있음(코드상, 확인 필요).
- 스펙 URL은 실행기가 서버 측에서 가져온다(10초) — 로컬 앱이라 영향 작지만 임의 URL 요청 경로.
- 화면 신원은 공용 토큰 하나(관리자·승인자). 로그인 없음 → 화면을 쓰는 누구나 레지스트리 쓰기 가능(로컬 전제).
- 토큰은 부팅 시 30일짜리로 발급. 30일 이상 연속 실행 시 만료 가능.
- 예제 서비스 멱등 캐시가 메모리 — 재시작 뒤 같은 Idempotency-Key 재전송은 중복 처리될 수 있음.
- 실행기 상태 조회를 페이지에서 1회 캐시 → 부팅 직후 연 탭은 새로고침 전까지 "닿지 못했습니다" 배너가 남을 수 있음.
- 등록 본문에 timeout_ms가 없으면 실행기 기본 10000ms(화면 기본 5000과 다름).

## 4. 다른 대상 메모
- M1: 구축 「소스」 단계와 액션 편집기가 시스템 목록·operation 목록 사용. 에이전트 도구 system_list/system_operations/system_query, 액션 생성 시 operation 존재 확인(실행기 불통이면 경고만).
- M2: 계획 시 시스템 실행 가능성·operation 존재 확인, 조회 API(GET 전용), Idempotency-Key 형식, 직접 모드 인증 주입. 실행기 MCP의 query_system 도구.
- A1: `/kinetic-idp/jwks.json`, 실행기 미가동 대체 응답, 부팅 시 repoint→register 순서는 A1 설계와 일치.
