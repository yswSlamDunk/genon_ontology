# 액션의 권한 검사 (Permission checks for Actions)

- 원문: https://www.palantir.com/docs/foundry/object-edits/permission-checks/
- 사이드바 위치: Ontology architecture > Object edits and materializations > Permission checks for Actions

이 페이지는 사용자가 액션(Action)을 적용해 객체를 만들거나 수정, 삭제하거나 링크를 만들고 지울 때, Foundry가 어떤 권한(permission)을 검사하는지 설명합니다. 특히 객체 하나의 속성이 여러 데이터소스에서 오는 경우에는 사용자가 객체의 일부만 볼 수 있으므로, 작업 종류별로 검사 규칙이 다릅니다.

액션을 적용할 때의 권한 검사는 [단일 데이터소스 객체](#edits-of-single-datasource-objects)를 편집하는지, [다중 데이터소스 객체](#edits-of-multi-datasource-objects)를 편집하는지에 따라 달라집니다.

<a id="edits-of-single-datasource-objects"></a>
## 단일 데이터소스 객체의 편집 (Edits of single-datasource objects)

객체 타입이 단일 데이터소스로 뒷받침된다면, 액션은 다음 조건을 만족하는 한 사용자가 객체를 편집하도록 허용합니다.

* 사용자가 객체를 보거나 불러올 수 있어야 합니다(자세한 내용은 [객체 권한(Object Permissioning)](../02_object-permissioning/01_overview.md) 섹션 참고). **그리고**
* 사용자가 액션에 정의된 [제출 조건(submission criteria)](../../02_define-ontologies/03_action-types/08_submission-criteria.md#submission-criteria)을 통과해야 합니다.

새 객체를 만들 때는 사용자가 객체 타입의 입력 데이터소스를 볼 수 있어야 합니다. 사용자가 입력 데이터소스에 접근 권한이 없으면 액션 실행은 실패합니다.

<a id="edits-of-multi-datasource-objects"></a>
## 다중 데이터소스 객체의 편집 (Edits of multi-datasource objects)

객체 타입은 [둘 이상의 데이터소스](../02_object-permissioning/06_multi-datasource-objects.md)에서 오는 속성을 가질 수 있습니다. 이 경우 사용자는 주어진 객체에 대해 다음과 같이 서로 다른 수준의 접근 권한을 가질 수 있습니다.

* 사용자가 객체 전체를 볼 수 있습니다. 예를 들어 모든 데이터소스와 그 데이터소스의 모든 행에 접근할 수 있는 경우입니다.
* 사용자가 데이터소스의 일부만 볼 수 있습니다. 예를 들어 일부 데이터소스의 모든 행에는 접근할 수 있지만 나머지 데이터소스의 행에는 하나도 접근할 수 없는 경우입니다.
* 사용자가 데이터소스 일부의 행 일부만 볼 수 있습니다. 예를 들어 어떤 행들에 대해서는 객체 전체에, 어떤 행들에 대해서는 객체 일부에 접근할 수 있고, 나머지 행들에 대해서는 객체에 접근할 수 없는 경우입니다.

객체 타입에 데이터소스가 여러 개 있으면 액션을 적용할 때의 권한 검사가 더 복잡해집니다. (단일 데이터소스 객체처럼) 객체를 편집하려면 객체 전체를 볼 수 있어야 한다는 제약을 강제하면 지나치게 제한적일 수 있기 때문입니다.

**설명**: 다중 데이터소스 객체는 기본 키가 같은 행들을 여러 데이터셋에서 모아 하나의 객체로 만든 것입니다. 예를 들어 Employee 객체 타입이 `employees_public`(이름, 부서)과 `employees_hr`(연봉) 두 데이터소스로 뒷받침되고, 일반 직원은 `employees_public`만 볼 수 있다고 합시다. 이 직원에게 Employee 객체는 연봉 속성이 빠진 채 보입니다. 아래 규칙들은 이런 부분 접근 상태에서 무엇을 허용할지 정합니다.

객체에 적용할 수 있는 액션의 종류별로 다음 권한 규칙이 구현되어 있습니다.

<a id="create-object"></a>
### 객체 생성 (Create object)

시나리오: 주어진 객체가 데이터소스 `D[i..k, m..n]`에 존재합니다. 사용자는 `D[i..k]`에 있는 속성 값만 설정해 객체를 생성합니다.

사용자가 `D[i..k]`의 백킹 데이터소스(backing datasource)를 볼 수 없으면 객체를 생성할 수 없습니다. `D[m..n]`에 대해서는 권한을 검사하지 않습니다. `D[m..n]`의 값은 기본값 `null`이 됩니다.

`D[i..k]` 중 어느 것이든 과거에 그 객체를 포함하고 있었다면(지금은 삭제된 것으로 표시되어 있더라도), 사용자가 객체를 다시 생성하려면 `D[i..k]` 전부에서 그 행 또는 객체를 볼 수 있는 권한이 있어야 합니다.

**설명**: `D[i..k, m..n]` 표기는 객체를 뒷받침하는 데이터소스 목록을 두 그룹으로 나눈 것입니다. `D[i..k]`는 이번 액션이 값을 쓰는 데이터소스들, `D[m..n]`은 이번 액션이 건드리지 않는 나머지 데이터소스들입니다. 위 Employee 예시라면 일반 직원이 이름과 부서만 넣어 객체를 생성할 수 있고, 연봉은 `null`로 남습니다.

<a id="edit-or-modify-object"></a>
### 객체 편집 또는 수정 (Edit or modify object)

시나리오: 객체가 데이터소스 `D[i..k, m..n]`에 존재합니다. 사용자는 `D[i..k]`에 매핑된 속성을 편집합니다.

사용자가 `D[i..k]`에 있는 속성의 기존 값을 볼 수 있다면 속성을 편집할 수 있습니다. `D[m..n]`에 매핑된 속성에 대해서는 권한을 검사하지 않습니다.

검증(validation) 중에는 `D[m..n]`이 `null`로 보입니다. `null` 값을 가진 상태로 검증을 통과하면 사용자는 액션을 적용할 수 있습니다.

**설명**: 액션의 제출 조건이 `D[m..n]` 쪽 속성을 참조한다면, 그 속성을 볼 수 없는 사용자에게는 값이 `null`로 평가된다는 뜻입니다. 예를 들어 "연봉이 null이 아니어야 함" 같은 조건은 HR 데이터소스를 볼 수 없는 사용자에게 항상 실패합니다.

<a id="delete-object"></a>
### 객체 삭제 (Delete object)

시나리오: 객체가 데이터소스 `D[i..k, m..n]`에 존재합니다.

사용자가 객체 전체(즉, `D[i..k, m..n]`에서 오는 모든 속성)를 볼 수 없으면 객체를 삭제할 수 없습니다.

<a id="create-link"></a>
### 링크 생성 (Create link)

시나리오: object1은 데이터소스 `D1[i..k]`에 존재하고 object2는 데이터소스 `D2[m..n]`에 존재합니다.

사용자가 object1과 object2를 각각 데이터소스 `D1[i..k]`와 `D2[m..n]` 중 어느 하나에서든 불러올 수 있다면 링크를 생성할 수 있습니다. 개별 속성이나 데이터소스에 대해서는 권한을 검사하지 않습니다.

<a id="delete-link"></a>
### 링크 삭제 (Delete link)

시나리오: object1은 데이터소스 `D1[i..k]`에 존재하고 object2는 데이터소스 `D2[m..n]`에 존재합니다.

사용자가 object1과 object2를 각각 데이터소스 `D1[i..k]`와 `D2[m..n]` 중 어느 하나에서든 불러올 수 있다면 링크를 삭제할 수 있습니다. 개별 속성이나 데이터소스에 대해서는 권한을 검사하지 않습니다.

> **중간 요약**: 다중 데이터소스 객체에서 생성과 수정은 값을 쓰는 데이터소스에 대한 권한만 검사하고 나머지는 `null`로 취급합니다. 삭제는 객체 전체를 볼 수 있어야 하며, 링크 생성과 삭제는 양쪽 객체를 어느 데이터소스에서든 불러올 수 있으면 허용됩니다.

## 정리

- 단일 데이터소스 객체는 객체를 볼 수 있고 제출 조건을 통과하면 편집할 수 있으며, 생성에는 입력 데이터소스 열람 권한이 필요합니다.
- 다중 데이터소스 객체의 생성과 수정은 해당 액션이 쓰는 데이터소스 권한만 검사하고, 보이지 않는 쪽 속성은 `null`이 됩니다.
- 삭제된 객체를 다시 만들려면 관련 데이터소스 전부에서 그 행을 볼 수 있어야 합니다.
- 객체 삭제는 가장 엄격해서 객체 전체를 볼 수 있어야 하고, 링크 생성과 삭제는 가장 느슨해서 양쪽 객체를 불러올 수만 있으면 됩니다.
