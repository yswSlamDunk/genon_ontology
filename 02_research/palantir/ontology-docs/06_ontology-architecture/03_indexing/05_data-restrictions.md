# 데이터 제약 (Data restrictions)

- 원문: https://www.palantir.com/docs/foundry/object-indexing/data-restrictions/
- 사이드바 위치: Ontology architecture > Indexing > Data restrictions

이 페이지는 Object Storage v2(OSv2)가 데이터를 온톨로지에 인덱싱(indexing)할 때 검사하는 제약 조건을 정리합니다. 기본 키(primary key)의 유일성과 허용 타입, 속성(property) 타입 일관성, 허용되지 않는 값, 속성 크기 한도가 포함됩니다. 인덱싱이 실패했을 때 원인을 찾거나, 처음부터 실패하지 않을 데이터를 설계할 때 참고하는 페이지입니다.

Object Storage v2(OSv2)는 온톨로지에 들어가는 데이터의 품질을 보장하고, 더 결정적인(deterministic) 동작을 제공하고, 플랫폼 전반의 가독성을 높이기 위해 데이터 제약을 적용합니다. 이 제약은 인덱싱 중에 검증됩니다. 배치 데이터소스로 뒷받침되는 객체 타입에서는 위반이 있으면 인덱싱 작업이 실패합니다. 스트리밍 데이터소스로 뒷받침되는 객체 타입에서는 이 제약을 위반하는 레코드가 버려집니다.

**설명**: 인덱싱은 데이터셋의 행을 온톨로지 객체로 바꾸어 빠르게 검색하고 조회할 수 있는 저장소에 적재하는 과정입니다. 배치(batch)는 데이터셋 전체를 한 번에 처리하므로 잘못된 행이 하나라도 있으면 작업 전체를 실패시켜 알리고, 스트리밍은 레코드가 계속 흘러 들어오므로 잘못된 레코드만 건너뛰는 방식으로 처리한다는 차이가 있습니다.

<a id="primary-keys-and-uniqueness"></a>
## 기본 키와 유일성 (Primary keys and uniqueness)

OSv2는 데이터소스에 대해 객체 기본 키가 유일하도록 강제합니다. 한 트랜잭션 안에 중복된 기본 키가 있으면 인덱싱이 실패하고 오류가 발생합니다. 여러 트랜잭션에 걸쳐 중복된 기본 키가 있으면 나중 트랜잭션의 버전이 사용됩니다.

OSv2는 온톨로지 모델링 모범 사례를 장려하기 위해 일부 데이터 타입을 기본 키로 쓰지 못하게 합니다. 다음 타입은 기본 키로 사용할 수 **없습니다**.

* Geopoint
* Geoshapes
* Arrays
* 시계열 속성(Time series properties)
* 실수 타입(decimal, double, float)

**설명**: 트랜잭션은 데이터셋에 데이터를 한 번 기록하는 단위입니다. 예를 들어 첫 트랜잭션에 `(id=7, status=open)`, 다음 트랜잭션에 `(id=7, status=closed)`가 들어오면 나중 값인 `closed`가 객체 7의 값이 됩니다. 하지만 한 트랜잭션 안에 `id=7` 행이 두 개 있으면 어느 쪽이 맞는지 정할 수 없으므로 실패합니다. 실수 타입이 금지되는 이유는 일반적으로 `0.1 + 0.2`가 정확히 `0.3`이 되지 않는 것처럼 부동소수점 값은 같은 값인지 비교하기가 불안정해서 식별자로 부적합하기 때문입니다.

> **중간 요약**: 한 트랜잭션 안의 중복 기본 키는 인덱싱 실패를, 트랜잭션 간 중복은 나중 값 우선을 낳습니다. 지리 타입, 배열, 시계열, 실수 타입은 기본 키로 쓸 수 없습니다.

<a id="property-type-restrictions"></a>
## 속성 타입 제약 (Property type restrictions)

* OSv2는 매 동기화마다 데이터소스 스키마와 객체 타입 스키마 사이의 데이터 타입 일관성을 강제합니다. 속성에 호환되지 않는 데이터 타입이 있으면 빌드가 실패합니다.
* 기존 속성의 기본 타입(base type)을 바꿀 때(예: `Double`에서 `Integer`로), 그 속성의 모든 기존 값은 대상 타입과 엄격하게 호환되어야 합니다. 새 타입과 호환되지 않는 값(Integer로 바꿀 때의 소수, 또는 통화 기호 등)이 데이터에 하나라도 있으면 `A property could not be cast to the new type` 같은 오류와 함께 마이그레이션이 실패합니다. 호환되지 않는 값이 있으면 스키마 마이그레이션은 진행되지 않으며, 마이그레이션 과정에서 이런 값을 자동으로 정리하거나 강제 변환하지 않습니다.
* OSv2는 속성 값으로 `NaN`이나 `±infinity`를 허용하지 않습니다.
* OSv2에서는 빈 문자열이 허용되지 않습니다. OSv1에서는 빈 문자열이 별다른 알림 없이 null로 변환되었습니다.
* `Lat, Long`은 괄호 없이 쉼표로 구분된 문자열이어야 합니다(예: `-29.123, 150.982`).
* OSv2는 중첩 배열을 가진 속성을 허용하지 않습니다.
* OSv2는 배열 데이터 타입 속성의 배열 안에 null 요소가 있는 것을 허용하지 않습니다.
* OSv2는 제한 뷰(restricted view) 데이터소스의 세분화 권한 정책에서, 부정되는 필드가 컬렉션이고 **비어 있지 않음(non-empty)** 제약이 있는 경우에 `Not` 조건을 지원합니다. 이는 Ontology Manager에서 해당 속성을 **required**(필수)로 표시하여 설정할 수 있습니다.
* OSv2는 geopoint 속성에 대해 더 엄격한 검증을 합니다.

**설명**: 몇 가지를 예시 값으로 보면 다음과 같습니다. `price` 열에 `12.5`가 있는데 타입을 `Integer`로 바꾸려 하면 실패하므로, 먼저 파이프라인에서 값을 반올림하는 등 정리해야 합니다. 배열 속성 `tags = ["a", null, "b"]`는 허용되지 않고 `["a", "b"]`처럼 null을 제거해야 합니다. 중첩 배열 `[[1,2],[3]]`도 허용되지 않습니다. 빈 문자열 `""`은 OSv1처럼 자동으로 null로 바뀌지 않으므로, 의도가 "값 없음"이라면 데이터 단계에서 null로 바꿔 두어야 합니다.

> **중간 요약**: OSv2는 스키마 타입 일치를 매번 검사하고, 타입 변경 시 호환되지 않는 값이 있으면 자동 변환 없이 실패합니다. `NaN`, 무한대, 빈 문자열, 중첩 배열, 배열 안의 null은 허용되지 않으며 좌표 문자열 형식과 geopoint 검증도 엄격합니다.

<a id="property-size-limits"></a>
## 속성 크기 한도 (Property size limits)

OSv2는 안정적인 인덱싱 성능과 안정성을 보장하기 위해 개별 속성에 크기 한도를 적용합니다. 이 한도는 큰 속성 값을 처리할 때 생길 수 있는 직렬화 제약과 메모리 압박 문제를 다룹니다.

| 속성 타입 | 최대 크기 |
| ------------- | ------------ |
| 문자열 속성 | 12 MB |
| 배열 속성 | 100,000개 요소 |

이 한도를 넘는 속성이 있으면 인덱싱 작업이 실패합니다. 이 한도는 우선 배치 데이터소스로 뒷받침되는 객체 타입에 적용되며, 앞으로 스트리밍 데이터소스를 가진 객체 타입에도 비슷한 한도가 적용될 예정입니다.

<a id="recommendations-for-large-data"></a>
### 큰 데이터에 대한 권장 사항 (Recommendations for large data)

* **큰 문자열 속성:** 12 MB를 넘는 데이터를 저장해야 한다면 대신 [미디어 참조 속성](../../02_define-ontologies/02_object-and-link-types/03_properties/09_base-types.md#media-references)을 사용하세요. 미디어 참조를 사용하면 인덱싱 성능에 영향을 주지 않고 큰 파일이나 바이너리 콘텐츠를 객체에 연결할 수 있습니다.
* **큰 배열:** 100,000개 요소를 넘는 관계를 모델링해야 한다면 배열 속성 대신 [링크 타입](../../02_define-ontologies/02_object-and-link-types/06_link-types/02_create-link-type.md)을 사용하는 것을 고려하세요. 링크는 객체 사이의 관계를 표현하는 더 확장성 있고 질의하기 좋은 방법을 제공합니다.

**설명**: 배열 대신 링크를 쓰라는 권장은 관계형 데이터베이스에서 한 열에 ID 목록을 문자열로 몰아넣는 대신 별도의 관계 테이블(외래 키)을 두는 정규화 원칙과 같은 방향입니다. 예를 들어 `Warehouse` 객체에 담긴 상품 ID 20만 개를 배열 속성으로 두는 대신, `Product` 객체마다 `warehouse_id`를 두고 링크로 연결하면 크기 한도에 걸리지 않고 "이 창고의 상품" 같은 질의도 쉬워집니다.

> **중간 요약**: 문자열 속성은 12 MB, 배열 속성은 10만 개 요소가 한도이며 넘으면 인덱싱이 실패합니다. 큰 콘텐츠는 미디어 참조로, 큰 관계는 링크 타입으로 모델링합니다.

## 정리

- OSv2는 인덱싱 중에 데이터 제약을 검증하며, 위반 시 배치는 작업 실패, 스트리밍은 해당 레코드 폐기로 처리합니다.
- 기본 키는 트랜잭션 안에서 유일해야 하며, 지리 타입, 배열, 시계열, 실수 타입은 기본 키가 될 수 없습니다.
- 스키마 타입 일관성을 매번 검사하고, 타입 변경 시 비호환 값을 자동 변환하지 않습니다.
- `NaN`, 무한대, 빈 문자열, 중첩 배열, 배열 내 null은 금지됩니다.
- 문자열 12 MB, 배열 10만 요소 한도를 넘는 데이터는 미디어 참조나 링크 타입으로 바꿔 모델링합니다.
