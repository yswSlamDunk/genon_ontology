# 온톨로지 시나리오 개요 (Overview)

- 원문: https://www.palantir.com/docs/foundry/ontology/overview-ontology-scenario/
- 사이드바 위치: Ontology scenarios > Overview

이 페이지는 온톨로지 시나리오(Ontology scenario)가 무엇인지, 어떤 용도에 쓰는지, 그리고 수명, 자동 리베이스, 함수 실행, 제한 사항 같은 기본 동작을 소개합니다. 시나리오는 실제 운영 데이터를 건드리지 않고 "만약 ~라면(what-if)" 상황을 시험해 볼 수 있는 격리된 작업 공간이므로, 의사 결정 시뮬레이션이나 에이전트 평가를 이해하는 출발점이 됩니다.

<a id="common-use-cases"></a><a id="scenarios-beta"></a>
## 시나리오 [베타] (Scenarios [Beta])

**참고**: 베타(Beta). 온톨로지 시나리오는 개발 단계 중 [베타](https://www.palantir.com/docs/foundry/platform-overview/development-life-cycle/) 단계에 있으며, 사용 중인 환경(enrollment)에서는 제공되지 않을 수 있습니다. 활발히 개발되는 동안 기능이 바뀔 수 있습니다. 시나리오에 대한 접근을 요청하려면 Palantir 지원팀에 문의하세요.

온톨로지 시나리오를 사용하면 객체와 모델(model)이라는 온톨로지 개념을 이용해 "만약 ~라면(what-if)" 분석을 만들고 비교할 수 있습니다. 시나리오는 본질적으로 온톨로지 데이터 위에 편집(edit)을 적용하는 샌드박스이며, 이 편집은 하나 이상의 액션을 적용해서 생성됩니다.

**설명**: 샌드박스(sandbox)는 실제 환경과 분리되어, 그 안에서 바꾼 내용이 바깥에 영향을 주지 않는 격리된 실행 공간을 말합니다. 예를 들어 Warehouse 객체의 `stock` 값이 실제로 100일 때, 시나리오 안에서 "주문 처리" 액션을 실행해 `stock`을 60으로 바꿔도 실제 온톨로지의 값은 여전히 100입니다. 시나리오 안에서 객체를 읽으면 60, 시나리오 밖에서 읽으면 100이 보입니다.

<a id="common-use-cases"></a><a id="time-to-live"></a>
## 일반적인 사용 사례 (Common use cases)

다음 워크플로에는 온톨로지 시나리오 사용을 권장합니다.

* **What-if 분석:** 온톨로지의 격리된 포크(fork)를 만들어, 실제 데이터에 영향을 주지 않고 데이터나 시스템의 변경을 시뮬레이션합니다.
* **비즈니스 로직 시뮬레이션:** 액션과 함수(function)를 적용해 비즈니스 프로세스를 시뮬레이션하거나, 운영상 변경을 확정(commit)하기 전에 그 영향을 평가합니다.
* **에이전트 평가 및 예측:** 서로 다른 입력 파라미터로 에이전트를 테스트해 결과를 비교하고 예측을 다듬습니다.
* **비교 분석:** 여러 시나리오를 나란히 만들어 최적의 결정을 찾거나 서로 다른 전략 간의 절충점(trade-off)을 이해합니다.

**주의**: 시나리오는 데이터 버전 관리 도구가 아닙니다. 과거 특정 시점의 온톨로지 스냅샷을 제공할 수 없으며, 그런 목적으로 사용해서는 안 됩니다.

> **중간 요약**: 시나리오는 실제 데이터 위에 액션으로 만든 편집을 격리해 적용하는 샌드박스로, what-if 분석, 비즈니스 로직 시뮬레이션, 에이전트 평가, 전략 비교에 씁니다. 과거 시점 스냅샷 용도로는 쓸 수 없습니다.

<a id="auto-rebasing"></a><a id="time-to-live"></a>
## 수명 (Time to live)

스토리지 비용을 관리하기 위해 시나리오의 기본 수명은 31일입니다. 31일이 지나면 시나리오는 그 시나리오에 적용된 모든 편집, 그리고 이를 뒷받침하는 영속(persisted) 시나리오 객체와 함께 자동으로 삭제됩니다. 영속 시나리오의 경우 [사용자 지정 만료 시간을 설정](03_persisted-scenario.md#configure-scenario-object-type)해 시나리오 수명을 줄이거나 늘릴 수 있습니다.

**설명**: Time to live(TTL)는 데이터가 생성된 뒤 자동 삭제되기까지 유지되는 시간을 뜻하는 일반적인 용어입니다. 캐시나 Redis 키의 만료 시간과 같은 개념입니다.

<a id="auto-rebasing"></a><a id="global-branching-vs-ontology-scenarios"></a>
## 자동 리베이스 (Auto-rebasing)

시나리오는 10분마다 메인(main) 브랜치 또는 글로벌(global) 브랜치 위로 자동 리베이스됩니다. 리베이스 기능을 통해 기반 온톨로지의 최신 변경 사항을 활성 시나리오에 반영할 수 있으므로, 시나리오가 데이터의 최신 상태와 동기화된 상태로 유지됩니다.

**설명**: 리베이스(rebase)는 Git에서 온 용어로, 내 변경 사항을 기준(base)의 최신 상태 위에 다시 얹는 작업입니다. 예를 들어 시나리오를 만든 뒤 실제 온톨로지에서 Warehouse의 `stock`이 100에서 120으로 바뀌었다면, 다음 리베이스 때 시나리오는 이 120을 새 기준으로 받아들이고 그 위에 시나리오의 편집을 다시 적용합니다.

<a id="global-branching-vs-ontology-scenarios"></a><a id="govern-actions-by-execution-context"></a>
## 글로벌 브랜칭과 온톨로지 시나리오 비교 (Global Branching vs. Ontology scenarios)

[글로벌 브랜칭(Global branching)](https://www.palantir.com/docs/foundry/global-branching/overview/)은 빌더(builder)가 Palantir 플랫폼에서 엔드투엔드 워크플로를 개발하고 테스트하는 데 쓰는 도구입니다. 이런 워크플로는 실제 운영 환경에서 실행하기에는 영향이 너무 클 수 있습니다. 반면 온톨로지 시나리오는 이런 워크플로의 사용자(사람과 에이전트)가 메인 온톨로지 데이터를 방해하지 않고 온톨로지에 편집을 적용할 수 있는 샌드박스를 제공합니다. 사용자는 여러 시나리오를 만들고 비교할 수 있으며, 편집 내용을 메인 온톨로지 데이터에 병합(merge)할 수 있습니다.

**설명**: 정리하면 글로벌 브랜칭은 개발자가 스키마, 파이프라인, 애플리케이션 같은 "만드는 쪽"의 변경을 시험하는 도구이고, 시나리오는 완성된 애플리케이션의 최종 사용자가 "데이터 값"에 대한 가정을 시험하는 도구입니다.

<a id="functions-on-a-scenario"></a><a id="govern-actions-by-execution-context"></a>
## 실행 컨텍스트로 액션 통제하기 (Govern actions by execution context)

[액션 제출 조건(submission criteria)](../02_define-ontologies/03_action-types/08_submission-criteria.md#execution-context)은 시나리오 안에서 실행된 액션과 메인 온톨로지를 대상으로 실행된 액션을 구분할 수 있습니다. 이 안전장치 덕분에 계획 담당자(planner)와 에이전트는 시나리오의 격리된 샌드박스에서 액션을 테스트할 때 더 느슨한 제출 조건을 사용할 수 있으며, 그렇다고 해서 그 액션을 메인 온톨로지에 적용할 권한까지 얻지는 않습니다. 승인된 시나리오 편집을 메인 온톨로지에 적용하는 것은 [병합 액션(merge action)](04_merge-scenario.md#configure-the-merge-action)의 제출 조건을 통해 별도로 통제됩니다.

**설명**: 예를 들어 "재고 이동" 액션의 제출 조건을 "실행 컨텍스트가 시나리오이면 누구나 허용, 메인 온톨로지이면 물류 관리자만 허용"으로 설정할 수 있습니다. 그러면 일반 사용자나 에이전트는 시나리오 안에서 마음껏 시험하고, 그 결과를 실제 데이터에 반영하는 병합 단계에서만 더 엄격한 검사를 받습니다.

<a id="functions-on-a-scenario"></a><a id="limitations"></a>
## 시나리오에서의 함수 (Functions on a scenario)

AIP Logic 함수를 제외한 모든 함수는 그대로 시나리오에서 실행할 수 있습니다. 함수가 온톨로지를 읽으면 시나리오 상의 온톨로지 상태를 읽습니다. 함수가 온톨로지 편집을 수행하면 그 편집은 시나리오에 적용됩니다. 시나리오에서 AIP Logic 함수를 사용하려면 해당 함수와 그 함수가 호출하는 모든 중첩 Logic 함수에 대해 [스테이지드 쓰기(staged writes)](https://www.palantir.com/docs/foundry/logic/staged-writes/)를 활성화하세요.

<a id="limitations"></a>
## 제한 사항 (Limitations)

시나리오를 사용해 워크플로를 구축할 때는 다음 제한 사항을 고려하세요.

* 시나리오 병합은 액션을 사용하므로, 시나리오를 병합할 때 [액션 적용 한도](../02_define-ontologies/03_action-types/17_scale-property-limits.md)가 적용됩니다.
* 시나리오는 10분마다 기반 위로 자동 리베이스됩니다.
* 시나리오를 원할 때 리베이스하거나 리베이스 간격을 설정할 수는 없습니다.

> **중간 요약**: 시나리오는 31일 뒤 자동 삭제되고(영속 시나리오는 조정 가능), 10분마다 자동 리베이스됩니다. 제출 조건으로 시나리오 안과 메인 온톨로지에서의 액션 실행을 구분해 통제할 수 있고, 함수는 AIP Logic을 제외하면 시나리오에서 그대로 실행됩니다.

## 정리

- 온톨로지 시나리오는 실제 온톨로지 데이터 위에 액션으로 만든 편집을 격리해 적용하는 베타 기능의 샌드박스입니다.
- what-if 분석, 비즈니스 로직 시뮬레이션, 에이전트 평가, 여러 전략 비교에 쓰며, 과거 시점 스냅샷 용도는 아닙니다.
- 기본 수명은 31일이고, 10분마다 자동 리베이스되며 리베이스 시점이나 간격은 바꿀 수 없습니다.
- 글로벌 브랜칭은 빌더의 개발용, 시나리오는 사용자(사람과 에이전트)의 데이터 편집 시험용입니다.
- 제출 조건의 실행 컨텍스트로 시나리오 안과 밖의 액션 권한을 다르게 줄 수 있으며, 병합은 별도의 병합 액션으로 통제합니다.
