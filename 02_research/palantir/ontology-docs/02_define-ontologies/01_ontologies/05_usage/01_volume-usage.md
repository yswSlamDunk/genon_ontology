# 온톨로지 볼륨 (Ontology volume)

- 원문: https://www.palantir.com/docs/foundry/ontologies/volume-usage/
- 사이드바 위치: Define Ontologies > Ontologies > Usage > Ontology volume

이 페이지는 온톨로지가 차지하는 저장 용량, 즉 온톨로지 볼륨(Ontology volume)을 어떻게 측정하고 무엇이 그 크기를 키우며 어떻게 관리하는지 설명합니다. 온톨로지 데이터는 빠른 조회를 위해 인덱싱되어 저장되므로 원본 데이터셋보다 클 수 있고, 이는 플랫폼 사용량(비용)과 직결됩니다.

Foundry의 온톨로지는 빠른 접근을 위한 저장 계층(storage layer)으로, 객체 정의를 대화형 데이터에 연결해 쿼리, 링크, 시나리오, 액션에 사용할 수 있게 합니다. Foundry 온톨로지의 데이터는 빠른 접근과 여러 편집자의 동시 안전 편집을 위해 인덱싱됩니다. 온톨로지 볼륨은 인덱싱된 객체 집합(object set)과 그들 사이 링크의 전체 크기를 나타내는 척도입니다. 온톨로지 볼륨은 평균 지표로, 순간 측정값의 단위는 GB이지만 한 달 동안 측정할 때는 GB-Month 단위를 가집니다.

**설명**: 인덱스(index)는 데이터를 빨리 찾기 위해 원본과 별도로 만들어 두는 자료구조입니다. 데이터베이스에서 `CREATE INDEX`로 B-트리 인덱스를 만들면 조회는 빨라지지만 디스크 공간을 더 쓰는 것과 같은 원리로, 온톨로지도 객체를 빠르게 검색하고 수정할 수 있도록 별도의 인덱스 저장소에 데이터를 적재하며, 그 크기가 온톨로지 볼륨입니다.

<a id="measuring-ontology-volume"></a>
## 온톨로지 볼륨 측정 (Measuring Ontology volume)

온톨로지 볼륨은 객체 타입을 뒷받침하는 인덱스의 크기를 측정해 기록됩니다. 각 객체 타입에는 일정 수의 객체가 있고, 객체마다 일정 수의 속성(property)이 있습니다. 각 속성의 크기는 임의적입니다. 인덱스 전체 크기는 해당 객체 타입의 모든 객체에 대해 인덱싱된 각 속성의 크기를 합산해 계산합니다.

온톨로지 데이터는 압축할 수 없고, 온톨로지 인덱싱은 더 빠른 쿼리를 위해 추가 저장 공간이 필요하기 때문에, 온톨로지 볼륨이 데이터셋 볼륨보다 클 수 있습니다.

Foundry 플랫폼은 매시간 객체별 온톨로지 볼륨 측정값을 기록합니다. 시간에 걸친 온톨로지 볼륨을 측정할 때는 해당 기간의 모든 시간별 측정값을 평균합니다. 한 달력 월 동안 평균을 내면 *GB-Month* 단위가 됩니다.

**설명**: GB-Month 계산 예시입니다. 한 달(30일) 중 앞의 15일은 볼륨이 10GB, 뒤의 15일은 20GB였다면 시간별 측정값의 평균은 15GB이고, 그 달의 사용량은 15 GB-Month입니다. 순간 최대치가 아니라 평균이므로, 잠깐 커졌다가 줄어든 볼륨은 그 기간만큼만 반영됩니다.

> **중간 요약**: 온톨로지 볼륨은 객체 타입별로 모든 객체의 인덱싱된 속성 크기를 합한 값이며, 매시간 측정한 값을 월 단위로 평균해 GB-Month로 표시합니다. 압축이 안 되고 인덱스용 공간이 추가되므로 데이터셋보다 클 수 있습니다.

<a id="investigating-ontology-volume-usage"></a>
## 온톨로지 볼륨 사용량 조사 (Investigating Ontology volume usage)

객체는 객체의 모든 관리와 모니터링을 위한 허브인 Ontology Manager에서 관리합니다. Ontology Manager에서 사용자는 어떤 데이터셋을 객체로 만들지, 이 객체에 어떤 타입의 속성을 붙일지, 객체 타입 사이에 어떤 링크 집합을 정의할지 구성할 수 있습니다.

객체와 해당 링크 타입의 전체 온톨로지 볼륨은 Resource Management Application에 표시됩니다.

<a id="factors-that-drive-ontology-volume"></a>
## 온톨로지 볼륨을 좌우하는 요인 (Factors that drive Ontology volume)

온톨로지 볼륨은 사실상 온톨로지에 있는 모든 객체(속성과 링크 포함)의 크기를 나타내는 척도입니다. 다음 두 가지가 전체 볼륨을 좌우하는 주요 요인입니다.

* **객체 타입별 객체 수와 크기**
  * 데이터셋으로 온톨로지 객체 타입을 만들면, 그 데이터셋의 행마다 객체 하나가 인덱싱됩니다. 따라서 데이터셋의 행 수와 해당 객체 타입의 객체 수는 1:1로 연결됩니다.
  * 또한 열이 더 많거나 더 많은 데이터(예: 자유 텍스트 필드)를 담은 데이터셋은 각 열이 속성으로 변환되기 때문에 개별 객체가 더 커질 수 있습니다.
* **조인 테이블을 사용할 때 객체 사이 링크의 수**
  * 다대다(many-to-many) 관계에서는 온톨로지가 기본 키(primary key)를 기준으로 객체 사이의 모든 링크를 정의하는 조인 테이블을 정의하도록 요구합니다. 이 테이블은 온톨로지에서 객체와 함께 인덱싱되며 온톨로지 볼륨을 사용합니다.
  * 일반적으로 룩업 테이블(look-up table)은 레코드당 크기가 일정하며, 정의된 링크 수에 비례해 볼륨이 선형으로 증가합니다.

**설명**: 다대다 관계의 예로 Student와 Course를 생각해 봅시다. 학생 한 명은 여러 강의를 듣고 강의 하나에는 여러 학생이 있으므로, `(student_id, course_id)` 두 열만 가진 조인 테이블 `enrollments`가 필요합니다. 학생 1,000명이 각각 5개 강의를 듣는다면 이 테이블은 5,000행이 되고, 이 5,000개의 링크 레코드도 인덱싱되어 볼륨에 포함됩니다. 레코드 하나의 크기는 키 두 개로 거의 일정하므로, 링크 수가 두 배가 되면 볼륨도 대략 두 배가 됩니다.

> **중간 요약**: 볼륨을 키우는 주된 요인은 객체 수(데이터셋 행 수와 1:1), 객체 하나의 크기(열 수와 긴 텍스트), 그리고 다대다 링크를 위한 조인 테이블의 레코드 수입니다.

<a id="managing-ontology-volume"></a>
## 온톨로지 볼륨 관리 (Managing Ontology volume)

온톨로지는 운영 용도와 쿼리를 위한 빠른 접근 백엔드로 설계되었습니다. 일반적으로 온톨로지는 더 큰 데이터 자산으로부터 합성된, 고도로 정제된 데이터와 함께 사용하는 것이 가장 좋습니다. 따라서 온톨로지 볼륨은 Foundry 변환 프레임워크(transformation framework)에 있는 원시(raw) 데이터와 중간(intermediate) 데이터의 전체 크기보다 작아야 합니다.

온톨로지 볼륨 사용량을 관리하려면 온톨로지에 정의된 객체 타입 수와 객체 타입별 객체 수, 객체별 속성 수에 주의를 기울이십시오. 전반적으로 온톨로지 볼륨 사용량을 관리하는 가장 좋은 방법은 객체 수, 속성 수, 속성 크기를 이해하고 의도적으로 관리하는 것입니다.

**설명**: 예를 들어 원시 로그 데이터셋이 수십억 행이라면 그대로 객체 타입으로 만들기보다, 파이프라인에서 일별, 장비별로 집계한 정제 데이터셋을 만들어 그것을 객체 타입으로 매핑하는 편이 볼륨 관리에 유리합니다. 업무 화면에서 쓰지 않는 열(긴 원문 텍스트 등)은 속성으로 만들지 않는 것도 같은 맥락입니다.

> **중간 요약**: 온톨로지에는 원시 데이터 전체가 아니라 정제된 데이터를 올리는 것이 원칙이며, 객체 타입 수, 객체 수, 속성 수와 크기를 의도적으로 관리해야 합니다.

## 정리

- 온톨로지 볼륨은 인덱싱된 객체와 링크의 전체 크기이며, 매시간 측정값을 평균해 GB-Month로 집계합니다.
- 압축 불가와 인덱스 추가 공간 때문에 같은 데이터라도 데이터셋보다 볼륨이 클 수 있습니다.
- 객체 수(행 수), 객체 크기(열 수와 텍스트 크기), 다대다 링크의 조인 테이블 레코드 수가 볼륨을 좌우합니다.
- 사용량은 Resource Management Application에서 확인하고, 정제된 데이터만 올리고 불필요한 속성을 줄이는 방식으로 관리합니다.
