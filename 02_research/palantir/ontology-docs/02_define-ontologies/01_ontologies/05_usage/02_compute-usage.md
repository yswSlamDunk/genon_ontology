# 온톨로지 인덱싱 컴퓨트 (Ontology indexing compute)

- 원문: https://www.palantir.com/docs/foundry/ontologies/compute-usage/
- 사이드바 위치: Define Ontologies > Ontologies > Usage > Ontology indexing compute

이 페이지는 데이터셋의 데이터를 온톨로지 인덱스로 변환하는 작업, 즉 온톨로지 인덱싱(Ontology indexing)이 얼마만큼의 계산 자원(compute)을 쓰는지, 그 사용량을 무엇이 좌우하고 어떻게 줄일 수 있는지 설명합니다. 볼륨 페이지가 "저장 공간"을 다룬다면, 이 페이지는 그 저장 공간을 채우는 "처리 비용"을 다룹니다.

Foundry의 온톨로지는 객체를 빠른 접근에 최적화된 저장 형식인 온톨로지 인덱스(Ontology index)에 저장합니다. Foundry 데이터셋의 데이터는 크기와 형식이 제각각일 수 있으므로, 데이터셋의 데이터를 온톨로지 인덱스에 저장할 수 있도록 준비하는 데이터 변환이 필요합니다. 이 과정을 *온톨로지 인덱싱*이라고 하며, 임의 크기의 데이터셋과 객체에 적용할 수 있습니다. 온톨로지 인덱싱의 처리 비용은 컴퓨트 초(compute-seconds) 단위로 측정합니다. 이 문서는 온톨로지 인덱싱이 컴퓨트를 어떻게 사용하는지, 그리고 컴퓨트 사용량을 어떻게 관리하는지 설명합니다.

<a id="measuring-compute-usage-from-ontology-indexing"></a>
## 온톨로지 인덱싱의 컴퓨트 사용량 측정 (Measuring compute usage from Ontology indexing)

온톨로지 인덱싱은 병렬화된 Spark 백엔드를 사용해 임의로 큰 데이터 집합을 읽고 온톨로지 형식으로 변환합니다. 인덱싱 작업(job) 하나를 실행하는 데 쓰이는 컴퓨트 양은 계산 자원(드라이버와 익스큐터)의 양과 인덱싱 작업 자체의 전체 경과 시간(wall-clock duration)에 따라 정해집니다.

Spark 사용량이 컴퓨트 초로 어떻게 환산되는지는 [사용량 유형(Usage Types)](https://www.palantir.com/docs/foundry/resource-management/usage-types/) 문서를 참고하십시오. 아래에서 [온톨로지 인덱싱이 사용하는 컴퓨트 초 계산 예시](#example-indexing-compute-calculation)를 볼 수 있습니다.

**설명**: Spark는 큰 데이터를 여러 컴퓨터에서 나누어 처리하는 분산 처리 엔진입니다. 드라이버(driver)는 작업을 쪼개고 조율하는 프로세스 하나이고, 익스큐터(executor)는 쪼개진 조각을 실제로 처리하는 작업자 프로세스들입니다. 경과 시간(wall-clock)은 CPU가 실제로 바빴던 시간이 아니라 작업 시작부터 끝까지 벽시계로 잰 시간이므로, 자원을 잡아 둔 채 기다린 시간도 포함됩니다.

<a id="investigating-usage-from-ontology-indexing"></a>
## 온톨로지 인덱싱 사용량 조사 (Investigating usage from Ontology Indexing)

온톨로지 인덱싱 작업은 Foundry의 Builds 애플리케이션에 표시되며, 인덱싱 대상 객체에 연결되어 있습니다. 온톨로지 인덱싱 작업은 Spark 작업이므로 병렬화된 배치 컴퓨트(parallelized batch compute)로 분류됩니다. 따라서 Code Repositories 변환(transform)이나 Contour 쿼리처럼 같은 백엔드를 쓰는 다른 작업과 같은 방식으로 측정할 수 있습니다.

인덱싱 작업은 무엇이 실행을 일으키는지에 따라 분류할 수 있습니다.

* *온톨로지 인덱싱 작업(Ontology indexing jobs)*은 데이터셋을 온톨로지 백엔드로 인덱싱합니다. 이 컴퓨트는 데이터셋으로부터 인덱싱된 객체를 만드는 데 쓰입니다.
* *온톨로지 내보내기 작업(Ontology export jobs)*은 온톨로지에서 직접 이루어진 편집(edit)을 Foundry 변환 프레임워크의 데이터셋에 영구 저장합니다. 내보내기 작업은 일반적으로 전체 객체 집합의 엄격한 부분집합인 편집만 다루므로, 전체 인덱싱 작업보다 작은 경향이 있습니다.

**설명**: 두 작업은 데이터가 흐르는 방향이 반대입니다. 인덱싱은 데이터셋에서 온톨로지 방향(읽어 들이기), 내보내기는 사용자가 액션으로 바꾼 값을 온톨로지에서 데이터셋 방향(써 내보내기)입니다. 예를 들어 Flight 객체 10만 개 중 오늘 50개만 상태가 바뀌었다면 내보내기 작업은 그 50개 편집만 처리합니다.

> **중간 요약**: 인덱싱은 Spark 작업이므로 드라이버와 익스큐터 자원량, 그리고 실행 시간으로 컴퓨트 초가 정해집니다. 작업은 Builds 애플리케이션에서 볼 수 있고, 데이터셋을 읽어 오는 인덱싱 작업과 편집을 데이터셋으로 내보내는 내보내기 작업으로 나뉩니다.

<a id="drivers-of-usage-for-ontology-indexing"></a>
## 온톨로지 인덱싱 사용량을 좌우하는 요인 (Drivers of usage for Ontology indexing)

온톨로지 인덱싱 작업은 인덱싱할 모든 데이터를 읽어서, 온톨로지 백엔드가 빠르게 저장하고 검색하고 편집할 수 있는 형식으로 변환해야 합니다.

데이터를 읽고 인덱싱할 때의 컴퓨트 사용량은 다음 요인으로 결정됩니다.

* **객체별 레코드 수(Number of records per object)**
  * 인덱싱되는 데이터셋의 레코드 수가 늘면 객체 수도 늘어납니다. 객체 하나를 인덱싱하는 데 일정량의 연산이 필요하므로, 객체 수가 늘면 인덱싱에 쓰이는 컴퓨트도 늘어납니다.
* **객체별 속성 수(Number of properties per object)**
  * 각 객체의 각 속성(property)은 인덱싱 작업이 개별적으로 분석한 뒤 객체 인덱스에 기록해야 합니다. 분석하고 인덱싱할 속성이 많을수록 더 많은 컴퓨트가 쓰입니다.
* **각 속성의 크기(Size of each property)**
  * 어떤 속성은 다른 속성보다 훨씬 큽니다. 예를 들어 내용이 많은 텍스트 속성은 단순한 숫자 속성보다 분석에 더 많은 공간과 컴퓨트가 필요합니다. 더 크고 복잡한 속성 타입을 가진 객체는 인덱싱에 더 많은 컴퓨트가 필요합니다.

인덱싱 빈도(frequency)도 온톨로지 업데이트에 쓰이는 컴퓨트 양에 큰 역할을 합니다. 업스트림 데이터셋에 설정된 스케줄은 객체의 자동 재인덱싱(auto-reindex)을 일으킵니다. 객체를 최신 상태로 유지하는 데 따르는 사용량을 검토할 때는 그 객체와 업스트림 데이터셋의 업데이트 스케줄을 함께 고려하십시오.

**설명**: 대략적으로 한 번의 인덱싱 비용은 "객체 수 x 속성 수 x 속성 크기"에 비례하고, 전체 비용은 여기에 실행 횟수를 곱한 것입니다. 예를 들어 업스트림 데이터셋이 매시간 다시 빌드되도록 스케줄되어 있으면 하루 24번 재인덱싱이 일어나므로, 하루 한 번으로 충분한 업무라면 스케줄만 바꿔도 인덱싱 비용이 크게 줄어듭니다.

> **중간 요약**: 인덱싱 비용은 레코드(객체) 수, 객체당 속성 수, 속성 크기에 따라 커지며, 업스트림 데이터셋 스케줄이 정하는 재인덱싱 빈도가 전체 사용량을 크게 좌우합니다.

<a id="managing-ontology-indexing-compute"></a>
## 온톨로지 인덱싱 컴퓨트 관리 (Managing Ontology indexing compute)

온톨로지 인덱싱 작업은 컴퓨트 사용량을 줄이도록 최적화할 수 있습니다. 가장 먼저 할 수 있는 가장 간단한 최적화는 인덱스의 입력 데이터 크기를 줄여 작업 완료에 필요한 일의 양을 줄이는 것입니다. 가능한 경우 다음을 수행합니다.

* 입력 레코드 수 관리
* 객체별 속성 수 관리
* 객체별 각 속성의 크기 관리

또 다른 최적화 방법은 온톨로지 인덱싱 작업이 체인지로그(changelog) 전략으로 인덱싱하도록 구성하는 것입니다. 체인지로그 인덱싱은 실행 전에 작업을 기존 객체와 비교함으로써, 인덱싱 작업마다 생성하거나 업데이트해야 하는 객체 수를 크게 줄입니다. 체인지로그 인덱싱은 더 많은 구성과 업데이트 전략 준수가 필요하지만, 몇 자릿수(orders-of-magnitude) 수준의 성능과 효율 향상을 가져올 수 있습니다.

**설명**: 전체 재인덱싱은 매번 테이블 전체를 지우고 다시 넣는 방식이고, 체인지로그 인덱싱은 추가, 수정, 삭제된 행만 반영하는 증분(incremental) 방식입니다. 100만 행 중 하루에 1,000행만 바뀐다면 처리 대상이 1,000분의 1로 줄어드는 셈이므로 "몇 자릿수" 개선이 가능합니다. 대신 데이터 파이프라인이 변경 내역을 정해진 규칙에 맞게 만들어 주어야 합니다.

> **중간 요약**: 입력 레코드 수, 속성 수, 속성 크기를 줄이는 것이 가장 간단한 최적화이고, 변경분만 처리하는 체인지로그 인덱싱은 구성이 더 필요하지만 효과가 매우 큽니다.

<a id="example-indexing-compute-calculation"></a>
## 인덱싱 컴퓨트 계산 예시 (Example indexing compute calculation)

인덱싱 작업은 병렬화된 Spark 작업 형태이며 Builds 애플리케이션에서 볼 수 있습니다. 다음은 인덱싱 작업의 예시입니다. 온톨로지 인덱싱 작업은 작업 크기에 따라 드라이버와 익스큐터의 크기를 자동으로 선택합니다.

```
Driver:
    num_vcpu: 1
    GiB_RAM: 6
Executors:
    num_vcpu: 1
    GiB_RAM: 4
    num_executors: 2
Total Runtime: 10 seconds

Calculation: 

driver_compute_seconds = max(num_vcpu, GiB_RAM / 7.5) * runtime_in_seconds
                       = max(1vcpu, 6GiB / 7.5) * 10sec
                       = 1 * 10 = 10 compute-seconds

executor_compute_seconds = max(num_vcpu, GiB_RAM / 7.5) * num_executors * runtime_in_seconds
                         = max(1vcpu, 4GiB / 7.5) * 2executors * 10sec
                         = 1 * 2 * 10 = 20 compute-seconds

total_compute_seconds = driver_commpute_seconds + exeucutor_compute_seconds
                      = 10 compute-seconds + 20 compute-seconds
                      = 30 compute-seconds

```

**설명**: 이 계산은 다음 순서로 이루어집니다.

1. 프로세스 하나의 "크기"는 `max(vCPU 수, 메모리 GiB / 7.5)`입니다. 즉 메모리 7.5GiB를 vCPU 1개와 같은 값으로 환산해, CPU와 메모리 중 더 큰 쪽을 기준으로 삼습니다. 드라이버는 6/7.5 = 0.8이므로 vCPU 1이 더 커서 크기는 1입니다. 익스큐터도 4/7.5 = 약 0.53이므로 크기는 1입니다.
2. 드라이버: 크기 1 x 10초 = 10 컴퓨트 초입니다.
3. 익스큐터: 크기 1 x 2개 x 10초 = 20 컴퓨트 초입니다.
4. 합계는 30 컴퓨트 초입니다.

만약 익스큐터의 메모리가 15GiB였다면 15/7.5 = 2가 vCPU 1보다 크므로 익스큐터 크기는 2가 되고, 익스큐터 컴퓨트는 2 x 2 x 10 = 40 컴퓨트 초가 됩니다. 원문 코드의 `commpute`, `exeucutor`는 원문의 오타이며 그대로 두었습니다.

## 정리

- 온톨로지 인덱싱은 데이터셋 데이터를 온톨로지 인덱스 형식으로 변환하는 Spark 작업이며, 비용은 컴퓨트 초로 측정합니다.
- 컴퓨트 초는 드라이버와 익스큐터 각각 `max(vCPU, GiB/7.5) x 개수 x 실행 시간`을 더해 계산합니다.
- 작업은 Builds 애플리케이션에서 확인하며, 인덱싱 작업(데이터셋에서 온톨로지로)과 내보내기 작업(편집을 데이터셋으로)으로 나뉩니다.
- 사용량은 레코드 수, 속성 수, 속성 크기, 재인덱싱 빈도가 좌우하며, 입력 축소와 체인지로그 인덱싱으로 줄일 수 있습니다.
