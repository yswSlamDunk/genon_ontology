# 온톨로지 브랜치 [레거시] (Ontology branches [Legacy])

- 원문: https://www.palantir.com/docs/foundry/ontologies/ontology-branches-legacy/
- 사이드바 위치: Define Ontologies > Ontologies > Branching the ontology > Ontology branches [Legacy]

이 페이지는 전역 브랜치(global branch)가 도입되기 전에 쓰이던 방식, 즉 온톨로지 전용 브랜치와 제안(proposal)으로 온톨로지를 변경하는 방법을 설명합니다. 이 기능은 단계적으로 종료되는 중이지만, 아직 이 방식을 쓰는 환경이 있고 이후의 전역 브랜치 개념을 이해하는 바탕이 되므로 흐름(브랜치 생성, 리뷰 요청, 리뷰, 병합)을 알아 둘 가치가 있습니다.

**주의**: 온톨로지 브랜치(이전 이름은 온톨로지 제안(ontology proposals))는 단계적으로 종료(sunset)되고 있습니다. Global Branching이 활성화된 환경(enrollment)에서는 더 이상 온톨로지 브랜치를 만들 수 없습니다. 대신 [전역 브랜치(global branches)](01_branching-ontology.md)를 사용해 온톨로지를 수정하십시오. 전역 브랜치에서는 데이터소스 브랜칭, 지원되는 애플리케이션에서 다운스트림 변경 테스트, 데이터와 온톨로지 수정을 하나의 통합된 워크플로에서 관리하기 등 확장된 기능을 사용할 수 있습니다.

온톨로지 브랜치를 사용하면 온톨로지의 `Main` 버전을 기반으로 하는 브랜치 위에서 온톨로지를 변경할 수 있습니다. 이 과정은 모든 수정 사항이 메인 온톨로지에 반영되기 전에 검토와 승인을 거치도록 보장합니다.

브랜치를 만들려면 해당 리소스가 들어 있는 프로젝트에 대한 편집자(editor) 권한이 필요합니다.

<a id="definitions"></a>
## 정의 (Definitions)

* **브랜치(Branch):** 온톨로지의 *브랜치*는 메인 버전에서 파생된, 그 온톨로지의 별도 버전입니다. 메인 브랜치에 영향을 주지 않고 실험하고 변경할 수 있도록 설계되었습니다. 이를 통해 사용자는 온톨로지 조정 사항을 격리된 환경에서 테스트하고 다듬은 뒤 메인 브랜치에 다시 병합(merge)할 수 있습니다.

* **제안(Proposal):** *제안*은 버전 관리 시스템의 Pull Request에 해당하는 것으로, 온톨로지 브랜치에 맞게 특화된 것입니다. 제안은 브랜치와 함께 자동으로 생성되며, 리뷰, 이름, 메인 브랜치로 병합될 변경 사항에 대한 설명 같은 메타데이터를 담습니다. 제안은 별도 브랜치에서 이루어진 변경을 메인 온톨로지에 통합하기 전에 검토하고 승인하는 메커니즘 역할을 합니다.

**설명**: Git을 써 봤다면 그대로 대응됩니다. `git checkout -b feature`로 만든 브랜치에서 커밋을 쌓고, GitHub에서 Pull Request를 열어 리뷰어의 승인을 받은 뒤 `main`에 병합하는 흐름입니다. 여기서는 소스 코드 대신 객체 타입, 링크 타입, 액션 타입 같은 온톨로지 정의가 변경 대상이고, Pull Request 역할을 하는 것이 제안입니다.

> **중간 요약**: 브랜치는 메인 온톨로지에서 갈라져 나온 격리된 작업 공간이고, 제안은 그 브랜치의 변경을 검토하고 승인받기 위한 Pull Request 역할의 메타데이터 묶음입니다.

<a id="ontology-branching-workflow"></a>
## 온톨로지 브랜칭 워크플로 (Ontology branching workflow)

일반적인 온톨로지 브랜칭 워크플로는 다섯 단계로 이루어집니다.

1. [브랜치 만들기](#1-create-your-branch)
2. [리뷰를 위해 제안 준비하기](#2-prepare-your-proposal-for-review)
3. [리뷰 요청하기](#3-request-a-review)
4. [제안 리뷰하기](#4-review-the-proposal)
5. [제안 릴리스하기](#5-release-the-proposal)

각 단계는 이어지는 섹션에서 설명합니다.

<a id="1-create-your-branch"></a><a id="create-your-branch"></a>
### 1. 브랜치 만들기 (Create your branch)

**Create Branch**를 선택해 대화상자를 열고, 제안의 제목과 설명을 정해 브랜치를 만들 수 있습니다.

또는 이미 제안에 포함하고 싶은 온톨로지 변경 사항이 있다면, 저장(save)을 선택한 뒤 저장 대화상자에서 **Propose your changes**(변경 사항 제안) 토글을 켤 수 있습니다.

![변경 사항 제안하기.](https://www.palantir.com/docs/resources/foundry/ontologies/propose-changes.png)

온톨로지의 메인 브랜치에 있고 변경 사항이 없다면, 브랜치 선택 컴포넌트를 골라 새 브랜치 이름을 입력하는 방법으로도 브랜치를 만들 수 있습니다.

제안 브랜치는 메인 온톨로지 구성(configuration)에서만 만들 수 있습니다. 다른 제안을 기반으로 새 브랜치를 만들 수는 없습니다.

브랜치에 있는 동안에는 작업 공간 인터페이스 위쪽에 있는 브랜치 탐색 상단 바가 현재 브랜치를 보여 줍니다.

![브랜치 탐색 상단 바.](https://www.palantir.com/docs/resources/foundry/ontologies/topbar.png)

**설명**: "다른 제안을 기반으로 새 브랜치를 만들 수 없다"는 것은 브랜치 구조가 한 단계뿐이라는 뜻입니다. Git에서는 `feature-a`에서 다시 `feature-a-sub`를 따는 것이 가능하지만, 레거시 온톨로지 브랜치에서는 모든 브랜치가 반드시 Main에서 직접 갈라져야 합니다.

<a id="2-prepare-your-proposal-for-review"></a><a id="prepare-your-proposal-for-review"></a>
### 2. 리뷰를 위해 제안 준비하기 (Prepare your proposal for review)

이 시점에는 제안을 어떻게 만들었는지에 따라 브랜치에 이미 일부 변경 사항이 있을 수 있습니다. 브랜치에 있는 동안 온톨로지 리소스를 계속 변경할 수 있으며, 생성과 삭제도 할 수 있습니다.

수정된 온톨로지 엔터티 하나하나는 제안 안에서 별도의 **Task**(작업)가 되며, 리뷰 대상으로 제공됩니다.

[온톨로지 역할(Ontology roles)](../../../06_ontology-architecture/02_object-permissioning/03_ontology-permissions-legacy.md#ontology-roles)을 사용하도록 마이그레이션된 리소스의 경우, 뷰어(viewer)도 제안 안에서 리소스를 변경할 수 있습니다. 리소스가 데이터소스 파생 권한(datasource derived permissions)을 사용하고 있다면 편집자나 소유자(owner)만 제안 안에서 변경할 수 있습니다.

**설명**: Task는 리뷰의 단위입니다. 예를 들어 한 브랜치에서 Employee 객체 타입에 속성 하나를 추가하고, Department 객체 타입의 표시 이름을 바꾸고, 새 링크 타입 하나를 만들었다면 제안에는 Task가 3개 생기고, 리뷰어는 각 Task를 따로 승인하거나 거절합니다.

<a id="3-request-a-review"></a><a id="request-a-review"></a>
### 3. 리뷰 요청하기 (Request a review)

브랜치에서 변경을 마친 뒤 제안에 리뷰어를 추가할 수 있습니다. 상단 바에 있는 **Open proposal details**를 선택해 [제안 화면(Proposal view)](#2-prepare-your-proposal-for-review)으로 이동합니다.

브랜치에서 나간 상태라면 **Proposals** 탭으로 가서 제안을 선택하거나, 브랜치 선택 컴포넌트를 사용해 제안 개요로 이동할 수 있습니다.

그곳의 **Reviewers** 섹션에서 리뷰어를 지정합니다.

리뷰어는 제안이 `In review` 단계가 되기 전까지는 알림을 받지 않습니다.

제안된 변경에 대한 맥락을 전달하기 위해 제안 안의 여러 Task에 댓글을 남길 수도 있습니다. **Reviews** 탭을 고른 다음 맨 오른쪽의 **Comments** 사이드바를 선택하면 Task의 **Comments** 섹션에 접근할 수 있습니다.

<a id="4-review-the-proposal"></a><a id="review-the-proposal"></a>
### 4. 제안 리뷰하기 (Review the proposal)

리뷰어는 **Reviews** 탭에서 개별 Task를 승인하거나 거절할 수 있고, 리뷰를 뒷받침하는 댓글을 추가할 수 있습니다.

변경을 승인하려면 리뷰어에게 소유자 또는 편집 권한이 있어야 합니다.

권한이 없는 사용자도 Task를 리뷰할 수는 있지만(예: 변경에 대한 의견을 전달하기 위해), 이는 Task의 승인 상태에 영향을 주지 않습니다.

제안 작성자가 편집된 모든 리소스에 대해 소유자 또는 편집자 권한을 가지고 있다면, 자신의 변경을 직접 승인할 수 있습니다.

**팁**: 모범 사례(Best practice). 편집자나 소유자는 리뷰어로 명시적으로 추가되지 않았더라도 제안을 승인할 수 있습니다. 리뷰어 목록은 누가 변경을 리뷰해야 하는지 추적하는 수단으로 사용하고, 온톨로지를 보호하는 수단으로 사용하지 않기를 권장합니다. 온톨로지는 역할과 권한을 신중하게 부여하는 방식으로 보호하십시오.

**설명**: 요점은 "리뷰어 목록에 들어 있는가"가 아니라 "해당 리소스에 편집 권한이 있는가"가 승인 가능 여부를 결정한다는 점입니다. 따라서 승인 절차를 통제하고 싶다면 리뷰어 지정이 아니라 권한 부여를 조정해야 합니다.

<a id="5-release-the-proposal"></a><a id="release-the-proposal"></a>
### 5. 제안 릴리스하기 (Release the proposal)

변경이 리뷰되고 승인되면 제안을 온톨로지에 병합할 수 있습니다. 병합에는 특별한 권한이 필요하지 않습니다. 브랜치를 편집할 수 있는 사람이라면 누구나 승인된 제안을 병합할 수 있습니다.

제안이 병합되면 사이드바에서 **In Review** 섹션에서 **Merged** 섹션으로 옮겨집니다.

제안을 병합하기 전이라면 언제든지 사이드바에서 **delete**를 선택해 제안을 닫을 수 있습니다.

제안은 메인 온톨로지 구성으로만 병합할 수 있습니다.

제안은 자동으로 되돌릴(revert) 수 없습니다. 제안을 취소하려면 그 안의 여러 변경 사항을 각각 되돌려야 합니다.

**주의**: 제안을 한 번 닫으면 다시 열 수 없습니다.

**설명**: Git의 `git revert`처럼 병합 커밋 하나를 통째로 취소하는 기능이 없다는 뜻입니다. 예를 들어 속성 추가와 링크 타입 생성이 함께 병합되었다면, 새 변경으로 그 속성을 지우고 그 링크 타입을 삭제하는 작업을 직접 해야 합니다.

> **중간 요약**: 브랜치 생성, 변경(Task 단위), 리뷰어 지정, Task별 승인 또는 거절, Main 병합의 다섯 단계로 진행합니다. 승인은 권한이 있는 사람만 할 수 있고, 병합된 제안은 자동으로 되돌릴 수 없으며 닫힌 제안은 다시 열 수 없습니다.

## 정리

- 온톨로지 브랜치(레거시)는 Main에서 갈라진 격리된 버전에서 온톨로지를 변경하고, 제안을 통해 검토 후 병합하는 기능입니다. Global Branching 환경에서는 전역 브랜치로 대체되었습니다.
- 브랜치 생성에는 프로젝트 편집자 권한이 필요하며, 브랜치는 Main에서만 만들 수 있습니다.
- 수정된 엔터티마다 Task가 생기고, 리뷰어는 Task 단위로 승인하거나 거절합니다. 승인 효력은 소유자나 편집 권한이 있는 사람에게만 있습니다.
- 승인된 제안은 브랜치를 편집할 수 있는 누구나 병합할 수 있으며, 병합은 자동으로 되돌릴 수 없고 닫힌 제안은 다시 열 수 없습니다.
