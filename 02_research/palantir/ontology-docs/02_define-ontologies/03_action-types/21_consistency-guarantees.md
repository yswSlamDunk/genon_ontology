# 일관성과 격리 (Consistency and isolation)

- 원문: https://www.palantir.com/docs/foundry/action-types/consistency-guarantees/
- 사이드바 위치: Define Ontologies > Action types > Consistency and isolation

이 페이지는 여러 액션이 동시에 실행될 때 액션 타입이 어떤 보장을 제공하는지, 그리고 용도에 맞는 격리 수준(isolation level)을 어떻게 고르는지 설명합니다. 데이터베이스 수업에서 배우는 트랜잭션, ACID, 격리 수준 개념이 온톨로지의 액션에 그대로 적용되므로, 그 개념을 액션에 연결해서 이해하는 것이 핵심입니다. 여러 사용자가 같은 객체를 동시에 수정하는 실무 환경에서 데이터가 깨지지 않게 하려면 이 내용을 알아야 합니다.

액션(action)은 하나의 트랜잭션을 통해 온톨로지에 편집(edit)을 적용합니다. 이 트랜잭션은 온톨로지에서 데이터를 읽고, 사용자가 정의한 로직을 적용하고, 하나 이상의 객체와 링크에 편집을 쓸 수 있습니다.

이 페이지는 동시 실행 중에 액션 타입이 제공하는 보장과, 특정 용도에 맞는 격리 수준을 선택하는 방법을 설명합니다.

**설명**: 트랜잭션(transaction)은 여러 개의 읽기와 쓰기를 하나의 논리적 작업 단위로 묶은 것입니다. 예를 들어 "계좌 A에서 10만 원을 빼고 계좌 B에 10만 원을 더한다"는 두 번의 쓰기가 반드시 함께 성공하거나 함께 실패해야 합니다. 액션 하나를 실행하는 것이 바로 이런 트랜잭션 하나라고 보면 됩니다.

<a id="acid-guarantees"></a>
## ACID 보장 (ACID guarantees)

액션은 데이터베이스 트랜잭션처럼 동작하며 표준 ACID 속성을 제공합니다.

* **원자성(Atomicity):** 액션이 온톨로지에 적용하는 편집은 하나의 묶음(batch)으로, 전부 적용되거나 전혀 적용되지 않습니다. 이 보장은 알림이나 웹훅 같은 액션의 다른 [부수 효과(side effect)](12_side-effects/01_side-effects-overview.md)나, 백킹 함수가 수행하는 외부 호출 같은 함수의 부수 효과에는 적용되지 않습니다.
* **일관성(Consistency):** 액션의 편집은 [값 타입 제약 조건](../02_object-and-link-types/08_value-types/06_value-type-constraints.md)과 [필수 속성](../02_object-and-link-types/03_properties/07_required-properties.md) 같은 온톨로지의 제약 조건을 만족할 때만 커밋됩니다.
* **격리성(Isolation):** 동시에 실행되는 액션들이 서로에게 어떤 영향을 주는지를 결정합니다. 액션 타입에 제공되는 격리 수준은 [아래 섹션](#isolation-levels)에서 설명합니다.
* **지속성(Durability):** 액션이 커밋되면 그 편집은 영구적으로 저장됩니다.

액션이 완료된 뒤에 시작되는 모든 액션이나 쿼리는 완료된 액션이 적용한 편집을 모두 볼 수 있습니다.
이 보장은 같은 액션 실행 도중에 수행되는 읽기에는 적용되지 않습니다.

그 편집이 보이는지 여부는 [쓰기 모드](#write-modes)에서 설명하는 액션의 쓰기 모드에 따라 달라집니다.

**설명**: 원자성의 예외에 주의해야 합니다. 액션이 객체 3개를 수정하고 이메일 알림을 보낸다고 할 때, 객체 수정 3건은 "전부 아니면 전무"로 처리되지만 이미 보낸 이메일은 되돌릴 수 없습니다. 온톨로지 바깥 시스템에 일어난 일은 트랜잭션 범위 밖이기 때문입니다.

> **중간 요약**: 액션 하나는 데이터베이스 트랜잭션 하나처럼 ACID를 보장합니다. 단, 알림이나 웹훅, 외부 호출 같은 부수 효과는 원자성 범위에 포함되지 않습니다.

<a id="how-writes-work"></a>
## 쓰기 동작 방식 (How writes work)

<a id="what-counts-as-a-write-to-a-property"></a>
### 무엇이 속성에 대한 쓰기로 간주되는가 (What counts as a write to a property)

액션이 어떤 속성(property)에 쓰는지 여부는 액션이 어떻게 구현되었는지에 따라 다릅니다.

* 로직 규칙(logic rule) 액션에서는 규칙이 [파라미터를 그 속성에 매핑](06_rules.md#values-and-parameters)할 때 속성에 쓰기가 일어납니다.
* [함수 기반 액션(function-backed action)](11_function-backed-actions/01_function-actions-overview.md)에서는 함수가 [온톨로지 편집](../04_functions/09_language-agnostic-features/01_edits-overview.md)을 통해 그 속성 값을 설정할 때 쓰기가 일어납니다.

**주의**: OSDK 액션 요청(OSDK action requests). [Ontology SDK(OSDK)](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk/#apply-action)를 통해 액션을 적용할 때, 선택 파라미터를 액션 요청에서 생략할 수 있는 것은 그 파라미터에 기본값이 설정되어 있는 경우뿐입니다.
기본값이 [객체 속성의 현재 값](07_parameters/02_parameters-default-value.md#object-property-default-values)을 사용하는 경우, 액션은 생략된 파라미터를 그 속성 값으로 채우고 그 값을 다시 속성에 씁니다.

**설명**: 마지막 문장의 의미는 이렇습니다. 파라미터 기본값이 "객체의 현재 `status` 값"으로 설정되어 있으면, 요청에서 그 파라미터를 생략해도 액션은 현재 값을 읽어서 같은 값을 `status`에 다시 씁니다. 값 자체는 변하지 않지만 "쓰기"가 발생한 것으로 처리되므로, 아래에서 설명하는 충돌 검사의 대상이 될 수 있습니다.

<a id="write-modes"></a>
### 쓰기 모드 (Write modes)

액션은 두 가지 쓰기 모드를 제공합니다.
두 모드 모두에서 액션의 편집은 액션이 실행되는 동안 모였다가 마지막에 하나의 원자적 묶음으로 온톨로지에 커밋되므로, 다른 액션이 일부만 적용된 액션을 관찰하는 일은 없습니다.
두 모드의 차이는 액션 **자신의** 읽기가 지금까지 자신이 만든 편집을 볼 수 있는지에 있습니다.

* **일괄 쓰기(Batched writes, 기본값):** 편집은 액션이 실행되는 동안 하나의 묶음으로 모였다가 마지막에 하나의 원자적 연산으로 온톨로지에 커밋됩니다. 액션 자신의 읽기는 묶음에 모인 편집을 볼 수 없습니다. 모든 읽기는 이 액션이 지금까지 모은 편집이 반영되지 않은, 온톨로지에 있는 그대로의 데이터를 반환합니다. 예를 들어 액션이 객체의 속성을 업데이트한 다음 그 객체를 다시 읽으면, 읽기는 업데이트된 값이 아니라 원래 값을 반환합니다.
* **단계적 쓰기(Staged writes):** 액션의 읽기가 자신의 편집을 볼 수 있습니다. 같은 액션 실행 안에서, 액션이 편집한 객체를 읽으면 편집된 값이 반환되고, 검색과 집계에도 편집이 반영됩니다. 단계적 쓰기는 현재 [TypeScript v2](../04_functions/10_typescript-v2/05_typescript-v2-staged-writes.md), [Python](../04_functions/11_python/06_python-staged-writes.md), [AIP Logic](https://www.palantir.com/docs/foundry/logic/staged-writes/) 함수 기반 액션 타입에서 지원됩니다.

**설명**: 구체적인 순서로 비교해 보겠습니다. `Order` 객체의 `quantity`가 5인 상태에서 액션이 (1) `quantity`를 10으로 바꾸고 (2) 같은 객체를 다시 읽는다고 합시다. 일괄 쓰기에서는 (2)의 결과가 5이고, 단계적 쓰기에서는 10입니다. 두 경우 모두 다른 사용자에게는 액션이 끝나서 커밋되기 전까지 여전히 5로 보입니다. 데이터베이스 용어로 단계적 쓰기는 "자기 쓰기 읽기(read-your-own-writes)"를 지원하는 방식입니다.

<a id="how-conflict-checks-work"></a>
### 충돌 검사 방식 (How conflict checks work)

충돌 검사를 수행하는 격리 수준에서, 온톨로지는 객체 단위로 쓰기-쓰기 충돌(write-write conflict)을 감지합니다.
두 액션이 동시에 같은 객체에 쓰면, 한 액션은 충돌 오류로 실패합니다.
이는 두 액션이 그 객체의 서로 다른 속성에 쓰는 경우에도 마찬가지입니다.

객체 타입이나 다대다(many-to-many) 링크 타입을 뒷받침하는 데이터셋을 다시 빌드(rebuild)하는 것도 충돌을 일으킬 수 있습니다.
액션 실행 사이의 충돌은 두 액션이 모두 쓰는 객체로 한정되지만, 백킹 데이터셋 재빌드로 인한 충돌은 범위가 더 넓습니다.
재빌드가 액션이 쓰는 특정 객체를 바꾸지 않더라도, 재빌드가 진행 중일 때 액션이 충돌을 만날 수 있습니다.
이런 충돌은 일시적이므로, 재빌드가 끝난 뒤 액션을 다시 시도하면 대개 성공합니다.

충돌이 감지되면 실패한 액션의 편집 전체가 폐기됩니다. 충돌이 어떻게 드러나고 재시도되는지는 [일시적 오류에 대한 재시도 모드](#retry-mode-on-transient-errors)를 참고하세요.

**설명**: "객체 단위"로 충돌을 검사한다는 점이 중요합니다. 관계형 데이터베이스로 치면 열 단위가 아니라 행 단위로 잠금이나 충돌 검사를 하는 것과 같은 수준입니다. 그래서 액션 A는 `Employee` 객체 E1의 `phone`만, 액션 B는 같은 E1의 `email`만 바꾸더라도 둘이 동시에 실행되면 하나는 실패합니다.

> **중간 요약**: 편집은 항상 마지막에 원자적으로 커밋되며, 일괄 쓰기는 자기 편집을 읽지 못하고 단계적 쓰기는 읽을 수 있습니다. 충돌은 객체 단위로 감지되며, 백킹 데이터셋 재빌드도 일시적 충돌을 일으킬 수 있습니다.

<a id="isolation-levels"></a>
## 격리 수준 (Isolation levels)

액션 타입의 *격리 수준*은 액션이 같은 데이터를 다루는 다른 액션과 함께 실행될 때 적용되는 보장을 정합니다.
격리 수준은 두 가지를 정의합니다. 하나는 액션 안의 각 읽기가 데이터의 어느 버전을 보는지이고, 다른 하나는 이후 바뀐 데이터를 바탕으로 만든 결과를 커밋하는 대신 액션을 실패시키는 동시 변경이 무엇인지입니다.
더 강한 수준은 더 많은 이상 현상(anomaly)을 막지만 충돌 시 더 많은 액션을 거부하고, 더 약한 수준은 더 자주 커밋되지만 보장이 적습니다.

액션 타입의 격리 수준은 **Ontology Manager**에서 액션 타입의 **Capabilities** 탭에서 설정합니다.
격리 수준은 생성 후에도 바꿀 수 있으며, 이후의 실행부터 적용됩니다.

**주의**: 일괄 쓰기를 사용하는 모든 새 액션 타입은 기본적으로 **스냅샷 격리(snapshot isolation)** 로 생성됩니다.
단계적 쓰기를 사용하는 액션 타입은 현재 레거시(legacy) 모드만 지원합니다.
자세한 내용은 [현재 단계적 쓰기 동작](#current-staged-writes-behavior)을 참고하세요.

![Ontology Manager의 Capabilities 탭에서 격리 수준 설정이 표시되고, 권장 옵션인 Snapshot isolation이 선택된 모습.](https://www.palantir.com/docs/resources/foundry/action-types/actions-isolation-levels.png)

액션 타입에 사용할 수 있는 수준을 아래 표에 요약했으며, 이어지는 섹션에서 자세히 설명합니다.

| 수준 | 읽기 | 충돌 검사 |
|---|---|---|
| **레거시(Legacy)** | 읽기가 하나의 시점에서 나온다는 보장이 없습니다. 같은 액션의 서로 다른 읽기가 서로 다른 상태를 볼 수 있습니다. | 이 액션이 **쓴** 객체를 다른 액션이 바꿨으면 실패합니다. |
| **스냅샷 격리(Snapshot isolation)** | 모든 읽기가 액션 시작 시점에 찍은 하나의 스냅샷을 사용합니다. | 이 액션이 **쓴** 객체를 다른 액션이 바꿨으면 실패합니다. |
| **커밋된 읽기(Read committed)** | 각 읽기는 읽는 시점에 가장 최근에 커밋된 값을 반환합니다. | 동시 변경이 있어도 편집을 허용합니다. 두 액션이 모두 설정한 속성은 마지막에 커밋한 액션의 값이 남습니다. |

**설명**: 스냅샷(snapshot)은 특정 시점의 데이터 상태를 고정해 둔 사본입니다. 스냅샷 격리에서는 액션이 10:00:00에 시작했다면, 실행 중 10:00:02에 다른 액션이 커밋한 변경은 이 액션의 읽기에 보이지 않습니다. 커밋된 읽기에서는 읽을 때마다 그 순간의 최신 커밋 값을 보므로, 같은 객체를 두 번 읽으면 결과가 다를 수 있습니다. PostgreSQL 같은 데이터베이스의 `REPEATABLE READ`, `READ COMMITTED` 격리 수준과 같은 개념입니다.

<a id="legacy"></a>
### 레거시 (Legacy)

레거시 격리 모드는 명시적 격리 수준이 도입되기 전에 만들어진 액션 타입을 위해 **Capabilities** 탭에서 계속 제공됩니다.
일괄 쓰기를 사용하는 새 액션 타입은 대신 스냅샷 격리가 기본값입니다.

**읽기:** 읽기는 대개 하나의 시점에서 나오지만 보장되지는 않습니다. 객체 저장소(object storage)에서 데이터를 가져오는 중 오류가 나면 액션이 실행되는 동안 기반 데이터가 새로 고쳐질 수 있으므로, 같은 액션 실행 중에 불러온 서로 다른 객체가 온톨로지의 서로 다른 상태를 반영할 수 있습니다.

**쓰기:** 레거시 격리는 두 쓰기 모드를 모두 지원합니다. 일괄 쓰기에서는 같은 액션 실행에서 나중에 수행한 읽기에 앞서 만든 편집이 포함되지 않습니다. 단계적 쓰기에서는 나중의 읽기에 그 편집이 포함됩니다. 자세한 내용은 [쓰기 동작 방식](#how-writes-work)과 [현재 단계적 쓰기 동작](#current-staged-writes-behavior)을 참고하세요.

**충돌 검사:** 액션이 쓰는 객체를, 그 객체를 불러온 시점과 액션이 커밋하는 시점 사이에 다른 액션이 바꾸면 액션은 충돌 오류로 실패합니다. 그러나 읽기의 일관성이 보장되지 않으므로, 액션이 *읽기만* 한 데이터에 기반한 판단은 서로 다른 시점의 데이터가 섞인 상태를 보고 내려질 수 있습니다.

레거시 격리 모드는 하위 호환성을 위해 제공됩니다.

새 액션 타입에는 [스냅샷 격리](#snapshot-isolation)를 사용하세요. 같은 충돌 검사를 하면서, 모든 읽기가 하나의 시점에서 나온다는 보장이 추가됩니다.

<a id="snapshot-isolation"></a>
### 스냅샷 격리 (Snapshot isolation)

일괄 쓰기를 사용하는 새 액션 타입의 기본 수준입니다. 단계적 쓰기를 사용하는 액션 타입의 동작은 [현재 단계적 쓰기 동작](#current-staged-writes-behavior)을 참고하세요.

**주의**: 소스는 다른 데이터를 볼 수 있음(Sources may observe different data). 로직 규칙 액션과 함수 기반 액션은 하나의 일관된 시점에서 온톨로지를 읽습니다. 함수가 [소스(source)](../04_functions/15_aliases/03_source-aliases.md)를 호출하면, 소스는 액션의 시점 기준 뷰 바깥에서 동작합니다. 소스는 온톨로지나 다른 시스템에서 읽을 수 있으며, 그 읽기는 다른 시점의 데이터를 볼 수 있습니다. 액션의 원자성과 충돌 검사는 소스가 수행하는 작업을 다루지 않습니다.

**읽기:** 액션이 직접 수행하는 모든 온톨로지 읽기는 액션이 시작될 때 찍은 하나의 일관된 시점 기준 뷰를 봅니다. 같은 객체를 두 번 읽거나 같은 검색을 두 번 실행하면, 이 액션이 실행되는 동안 다른 액션이 무엇을 커밋하든 항상 같은 데이터가 반환됩니다.

**쓰기:** 이 수준의 액션은 일괄 쓰기를 사용하므로, 같은 액션 실행에서 나중에 수행한 읽기에 앞서 만든 편집이 포함되지 않습니다.

**충돌 검사:** 액션이 쓰는 객체를, 그 객체를 불러온 시점과 액션이 커밋하는 시점 사이에 다른 액션이 바꾸면 액션은 충돌 오류로 실패합니다. 액션은 동시 변경을 덮어쓰지 않고 실패합니다. 이 수준에서는 액션이 *읽기만* 하는 객체는 충돌 실패의 원인이 되지 않습니다. 충돌 재시도에 대해서는 [일시적 오류에 대한 재시도 모드](#retry-mode-on-transient-errors)를 참고하세요.

<a id="write-skew"></a>
#### 쓰기 왜곡 (Write skew)

*쓴* 객체만 충돌 검사 대상이므로, 스냅샷 격리는 읽기-쓰기 충돌(read-write conflict)을 감지하지 **못합니다**.

두 액션이 각각 겹치는 데이터를 읽고, 그 읽기를 바탕으로 판단하고, *서로 다른* 객체에 쓰면 둘 다 커밋될 수 있습니다. 어느 한쪽이 다른 쪽의 쓰기를 봤다면 커밋하지 않았을 상황인데도 그렇습니다.

이를 *쓰기 왜곡(write skew)* 이라고 합니다.

**예시:** 당직 순번(on-call rotation)에는 항상 **최소 한 명**의 엔지니어가 당직을 서야 합니다. 엔지니어는 다른 누군가가 남아 있을 때만 순번에서 빠질 수 있으므로, 액션은 *현재 당직 엔지니어가 최소 두 명인가?* 를 확인합니다. 엔지니어 A와 B가 모두 당직 중이고, 각자 동시에 자신을 빼는 액션을 실행합니다.

* A의 액션은 자신의 스냅샷에서 순번을 읽고, 당직 엔지니어가 두 명인 것을 확인한 뒤 진행합니다. A를 빼도 B가 남기 때문입니다.
* B의 액션은 자신의 스냅샷에서 같은 상태를 읽고, 당직 엔지니어가 두 명인 것을 확인한 뒤 같은 이유로 진행합니다.
* A는 `A.onCall = false`를 쓰고, B는 `B.onCall = false`를 씁니다. 두 액션은 *서로 다른* 객체에 썼으므로 쓰기-쓰기 충돌이 없고 둘 다 커밋됩니다. 이제 순번이 비어 불변 조건(invariant)이 깨졌습니다.

깨진 불변 조건이 어느 액션이 *쓴* 단일 객체가 아니라 액션들이 *읽은* 데이터(당직 엔지니어 집합)에 걸려 있으므로, 스냅샷 격리는 이를 잡아낼 수 없습니다.

이 이상 현상을 피하려면 불변 조건을 하나의 공유 객체에 대한 쓰기로 표현하도록 워크플로를 다시 설계하세요.

예를 들어 두 액션이 모두 `onCallCount` 속성을 가진 `Rotation` 객체에 쓰도록 하면, 두 액션이 충돌하게 됩니다.

**설명**: 시간 순서로 정리하면 다음과 같습니다. 초기 상태는 A.onCall = true, B.onCall = true입니다. A의 액션과 B의 액션이 거의 동시에 시작해 각자 스냅샷에서 "당직자 2명"을 읽습니다. A의 액션은 객체 A만, B의 액션은 객체 B만 수정하므로 객체 단위 충돌 검사에 걸리지 않고 둘 다 커밋되어 당직자가 0명이 됩니다. 해결책으로 제시된 방법은 두 액션 모두 `Rotation` 객체의 `onCallCount`를 2에서 1로 줄이는 쓰기를 하게 만드는 것입니다. 그러면 두 액션이 같은 객체(`Rotation`)에 쓰므로 하나는 충돌로 실패하고, 재시도 시 `onCallCount`가 1인 것을 보고 빠지기를 거부할 수 있습니다.

<a id="read-committed"></a>
### 커밋된 읽기 (Read committed)

**커밋된 읽기(read committed)** 격리 모드는 곧 제공될 예정입니다.

**읽기:** 각 읽기는 읽기가 실행되는 순간에 가장 최근에 커밋된 값을 반환합니다. 고정된 스냅샷이 없으므로, 같은 액션에서 서로 다른 시점에 수행한 두 읽기 사이에 다른 액션이 커밋하면 두 읽기는 서로 다른 상태를 볼 수 있습니다.

**쓰기:** 이 수준의 액션은 일괄 쓰기를 사용하므로, 같은 액션 실행에서 나중에 수행한 읽기에 앞서 만든 편집이 포함되지 않습니다([쓰기 동작 방식](#how-writes-work) 참고).

**충돌 검사:** 실행 중에 다른 액션이 같은 객체를 바꿨더라도 액션의 편집이 허용됩니다. 두 액션이 모두 커밋되면 서로 다른 속성에 대한 변경은 보존됩니다. 두 액션이 같은 속성을 설정했다면 마지막에 커밋한 액션이 그 값을 결정합니다. 같은 객체에 대해 매우 많은 액션을 동시에 실행하면 가끔 소수의 충돌이 여전히 발생할 수 있습니다.

**예시:** `Ticket` 객체가 `status = "open"`, `priority = "low"`인 상태입니다. 두 액션이 동시에 실행됩니다.

* 액션 A는 `status = "in progress"`와 `priority = "medium"`을 설정합니다.
* 액션 B는 `priority = "high"`를 설정합니다.
* 액션 A가 먼저 커밋합니다. 티켓은 이제 `status = "in progress"`, `priority = "medium"`입니다.
* 액션 B가 두 번째로 커밋하면서 A가 바꾼 `priority`를 덮어씁니다. 티켓은 최종적으로 `status = "in progress"`, `priority = "high"`가 됩니다. 액션 A의 `status` 변경과 액션 B의 `priority` 변경이 모두 보존됩니다.

[스냅샷 격리](#snapshot-isolation)에서였다면, 두 액션이 같은 객체에 썼으므로 액션 B가 충돌 검사에서 실패하고 액션 A의 편집이 보존되었을 것입니다.

이 수준은 더 약한 정확성 보장을 대가로 커밋 성공률을 높입니다. 액션이 파라미터로 전달된 값처럼 이미 손에 쥐고 있는 값만 쓰고, 무엇을 쓸지 정하는 데 읽은 값에 의존하지 않을 때 적합합니다.

**경고**: 동시 편집이 덮어써질 수 있음(Concurrent edits may be overwritten). 여러 액션이 같은 속성을 동시에 설정할 수 있는 경우에는 커밋된 읽기를 신중하게 사용하세요. 두 액션이 모두 커밋되면 나중 액션이 그 속성의 이전 값을 덮어씁니다. 다른 속성에 대한 변경은 보존됩니다.

**설명**: 커밋된 읽기에서 충돌 검사가 속성 단위로 병합되는 것처럼 보이는 이유는, 각 액션이 "자신이 설정한 속성"만 덮어쓰기 때문입니다. 반면 "현재 재고를 읽고 1을 빼서 쓴다" 같은 읽기-수정-쓰기 로직에 이 수준을 쓰면, 두 액션이 모두 재고 10을 읽고 9를 쓰는 갱신 손실(lost update)이 생길 수 있습니다. 원문이 "읽은 값에 의존하지 않을 때"에만 권하는 이유가 이것입니다.

> **중간 요약**: 레거시는 읽기 시점이 보장되지 않는 하위 호환용 모드이고, 스냅샷 격리는 시작 시점의 일관된 스냅샷을 읽으며 쓴 객체의 충돌을 검사하는 기본 권장 수준입니다. 스냅샷 격리도 쓰기 왜곡은 막지 못하며, 커밋된 읽기는 충돌 대신 마지막 커밋이 이기는 방식으로 성공률을 높이지만 보장이 약합니다.

<a id="current-staged-writes-behavior"></a>
## 현재 단계적 쓰기 동작 (Current staged writes behavior)

단계적 쓰기를 사용하는 액션 타입은 현재 레거시 격리 모드만 지원합니다.

이 섹션은 단계적 쓰기가 제공하는 보장을 설명합니다.

**읽기:** 각 읽기는 읽기가 실행되는 순간에 가장 최근에 커밋된 값에 액션 자신의 단계적 편집을 더한 결과를 반환합니다. 고정된 스냅샷이 없으므로, 같은 액션에서 서로 다른 시점에 수행한 두 읽기 사이에 다른 액션이 커밋하면 두 읽기는 서로 다른 상태를 볼 수 있습니다. 그러나 액션 자신의 단계적 편집은 이후의 읽기에서 항상 보입니다.

**쓰기:** 액션은 단계적 쓰기를 사용하므로, 같은 액션 실행에서 나중에 수행한 읽기에 앞서 만든 편집이 포함됩니다. 다른 액션은 편집이 마지막에 원자적으로 커밋되기 전까지 그 편집을 볼 수 없습니다([쓰기 동작 방식](#how-writes-work) 참고).

**충돌 검사:** 액션이 쓰는 객체를, 그 객체를 불러온 시점과 액션이 커밋하는 시점 사이에 다른 액션이 바꾸면 액션은 충돌 오류로 실패합니다. 액션은 동시 변경을 덮어쓰지 않고 실패합니다. 액션이 *읽기만* 하는 객체는 충돌 실패의 원인이 되지 않습니다. 충돌 재시도에 대해서는 [일시적 오류에 대한 재시도 모드](#retry-mode-on-transient-errors)를 참고하세요.

이 동작은 단계적 쓰기의 자기 쓰기 읽기(read-your-own-writes) 기능과 쓰기-쓰기 충돌 감지를 결합하지만, 온톨로지에서의 읽기가 하나의 시점에서 나온다는 것은 보장하지 않습니다.

> **중간 요약**: 단계적 쓰기 액션은 현재 레거시 모드로만 동작하며, 자기 편집은 읽을 수 있고 쓴 객체의 충돌은 검사하지만 읽기 시점의 일관성은 보장되지 않습니다.

<a id="retry-mode-on-transient-errors"></a>
## 일시적 오류에 대한 재시도 모드 (Retry mode on transient errors)

플랫폼은 충돌 오류나 객체 저장소에서 객체를 불러오는 중의 실패 같은 일시적 오류를 만나면 액션을 자동으로 재시도할 수 있습니다. 각 재시도는 액션에 설정된 격리 수준을 사용해 액션을 처음부터 다시 실행하며, 최대 5회까지 시도합니다. 현재 값을 읽는 로직은 새 실행에서 사용할 수 있는 데이터로 편집을 다시 계산합니다. 모든 시도가 실패하면 오류가 호출자에게 반환됩니다.

기본적으로 외부 시스템 호출(웹훅 등)이 없는 액션은 재시도되고, 외부 시스템 호출이 있는 액션은 재시도되지 않습니다. 액션을 다시 실행하면 웹훅을 두 번 보내는 것처럼 부수 효과가 반복되기 때문입니다.

이 동작은 **Capabilities** 탭의 **Retry mode on transient errors** 설정으로 액션 타입별로 조정할 수 있습니다.

![Capabilities 탭에서 사용 가능한 옵션이 표시된 Retry mode on transient errors 드롭다운.](https://www.palantir.com/docs/resources/foundry/action-types/actions-retry-settings.png)

* **Only actions without external calls (기본값):** 액션 타입에 외부 시스템 호출이 없을 때만 플랫폼이 재시도합니다.
* **All actions:** 외부 호출이 있는 액션을 포함해 모든 액션을 플랫폼이 재시도합니다. 액션 타입의 외부 호출이 반복해도 안전하다고(멱등적, idempotent) 알려져 있을 때 사용합니다.
* **Disabled:** 플랫폼이 자동 재시도를 하지 않습니다. 첫 실패 때 오류가 호출자에게 반환됩니다. 호출자가 모든 충돌을 직접 관찰하고 처리하려 할 때 사용합니다.

이 설정에 따라, 다른 점에서는 똑같은 두 액션 타입이 경합 상황에서 다르게 동작할 수 있다는 점에 유의하세요. 한쪽은 충돌이 재시도로 해소되어 항상 성공하는 것처럼 보이고, 다른 쪽은 호출자에게 충돌 오류를 드러냅니다.

자동 재시도 때문에, 충돌이 잦은 액션은 결국 성공하더라도 완료까지 눈에 띄게 오래 걸릴 수 있습니다.

**설명**: 멱등성(idempotency)은 같은 요청을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질입니다. 예를 들어 "주문 #123의 상태를 shipped로 설정"하는 외부 API 호출은 두 번 보내도 결과가 같으므로 멱등적이지만, "결제 1만 원 청구"는 두 번 보내면 2만 원이 청구되므로 멱등적이지 않습니다. 기본 설정이 외부 호출이 있는 액션을 재시도하지 않는 것은 이런 중복 실행을 막기 위해서입니다.

> **중간 요약**: 일시적 오류가 나면 플랫폼이 최대 5회까지 액션을 처음부터 다시 실행할 수 있으며, 기본적으로 외부 호출이 없는 액션만 재시도합니다. 재시도 정책은 액션 타입별로 바꿀 수 있습니다.

<a id="choosing-an-isolation-level"></a>
## 격리 수준 선택하기 (Choosing an isolation level)

* 특별한 이유가 없다면 **스냅샷 격리를 사용하세요.** 스냅샷 격리는 개별 객체에 대한 읽기-수정-쓰기 로직을 포함해 대부분의 워크플로에 가장 적합한 격리 수준입니다.
* 명시적 격리 수준이 도입되기 *전에* 만들어진 액션 타입은, 대개 성립하지만 보장되지는 않는 레거시 동작 대신 실행 안의 모든 읽기가 같은 시점에서 나오도록 보장받기 위해 수준을 스냅샷 격리로 설정하세요. 다만 스냅샷 격리는 실행 내내 같은 시점 기준 뷰를 사용하므로, 실행 시간이 길고 자주 업데이트되는 데이터를 편집하려는 액션은 더 자주 재시도될 수 있습니다.
* 커밋된 읽기는 충돌 실패가 잦고, 그 수준이 허용하는 이상 현상을 이해하고 있으며, 액션의 쓰기가 데이터의 안정적인 읽기에 의존하지 않는 경우에**만** 고려하세요. 기존 액션 타입을 이 모드로 바꾸기 전에 [커밋된 읽기](#read-committed) 섹션의 경고를 검토하세요.

## 정리

- 액션 하나는 ACID를 보장하는 트랜잭션 하나이며, 편집은 마지막에 원자적으로 커밋됩니다(외부 부수 효과는 제외).
- 일괄 쓰기(기본값)는 자기 편집을 읽지 못하고, 단계적 쓰기는 읽을 수 있습니다. 단계적 쓰기는 현재 레거시 격리만 지원합니다.
- 충돌은 객체 단위 쓰기-쓰기 충돌로 감지되며, 백킹 데이터셋 재빌드도 일시적 충돌을 일으킬 수 있습니다.
- 격리 수준은 레거시, 스냅샷 격리(기본, 권장), 커밋된 읽기(예정, 마지막 커밋 우선) 세 가지이고, 스냅샷 격리도 쓰기 왜곡은 막지 못합니다.
- 일시적 오류는 최대 5회 자동 재시도되며, 외부 호출이 있는 액션은 기본적으로 재시도하지 않습니다.
