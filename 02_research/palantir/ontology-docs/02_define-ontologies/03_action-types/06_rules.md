# 규칙 (Rules)

- 원문: https://www.palantir.com/docs/foundry/action-types/rules/
- 사이드바 위치: Define Ontologies > Action types > Rules

이 페이지는 액션 타입(action type)의 핵심 로직인 규칙(rule)을 설명합니다. 사용자가 입력한 파라미터 값을 받아 실제로 객체와 링크를 만들거나 바꾸거나 지우는 부분, 또는 알림이나 웹훅 같은 다른 효과를 일으키는 부분이 바로 규칙입니다. 액션 타입을 설계할 때 "무엇을 입력받는가"가 파라미터라면 "그 입력으로 무엇을 하는가"가 규칙이므로, 어떤 규칙 종류가 있고 어떤 조합이 허용되지 않는지 알아 두어야 합니다.

**규칙(Rules)은** 파라미터를 온톨로지 편집(edit)이나 그 밖의 효과로 변환하는 액션 타입의 로직을 정의합니다. 규칙에는 크게 두 종류가 있습니다. 온톨로지를 편집하는 규칙과, Foundry에서 다른 효과를 일으키는 규칙입니다.

아래 규칙들로 무엇을 만들 수 있는지 안내형으로 소개받으려면 [다른 액션 타입 살펴보기](03_explore-action-types.md)를 참고하세요.

**설명**: 액션 타입을 함수 호출에 대응시켜 보면, 파라미터는 함수의 인자이고 규칙은 함수 본문입니다. 예를 들어 "티켓 상태 변경" 액션은 `ticket`과 `newStatus`를 인자로 받고, 규칙은 "`ticket` 객체의 `status` 속성을 `newStatus`로 수정한다"는 본문에 해당합니다. 차이점은 규칙을 코드가 아니라 Ontology Manager 화면에서 선택과 매핑으로 구성한다는 점입니다.

<a id="ontology-rules"></a>
## 온톨로지 규칙 (Ontology rules)

온톨로지 규칙은 온톨로지의 특정 요소를 변경합니다. 기존 타입의 객체와 링크를 생성, 수정, 삭제할 수 있습니다. 일대다(one-to-many) 또는 일대일(one-to-one) 링크를 생성하거나 삭제하려면 객체 규칙을 사용해 객체의 외래 키(foreign key) 속성을 수정해야 합니다.

1. **Create object(객체 생성):** 미리 정의된 타입의 객체를 생성할 때 사용합니다. 객체 타입의 기본 키(primary key)는 반드시 채워야 하는 필수 속성입니다. 추가 속성은 선택적으로 더할 수 있습니다.
2. **Modify object(s)(객체 수정):** 객체 참조 파라미터로부터 기본 키를 얻는 기존 객체를 수정할 때 사용합니다. 현재 액션 안에서 생성된 객체는 참조할 수 없습니다.
3. **Create or modify object(s)(객체 생성 또는 수정):** 객체 참조 파라미터를 기준으로 기존 객체를 수정할 때 사용합니다. 객체가 선택되지 않으면 자동 생성된 고유 ID 또는 사용자가 제출한 기본 키로 새 객체를 생성합니다.
4. **Delete object(s)(객체 삭제):** 객체 참조 파라미터로부터 기본 키를 얻는 기존 객체를 삭제할 때 사용합니다. 현재 액션 안에서 생성된 객체는 참조할 수 없습니다.
5. **Create link(s)(링크 생성):** 객체 참조 파라미터로 전달된 객체들 사이에 다대다(many-to-many) 링크를 생성할 때 사용합니다. 외래 키 링크의 경우에는 **Modify object** 규칙으로 외래 키 속성을 명시적으로 수정해야 합니다.
6. **Delete link(링크 삭제):** 객체 참조 파라미터로 전달된 객체들 사이의 다대다 링크를 삭제할 때 사용합니다. 외래 키 링크의 경우에는 **Modify object** 규칙으로 외래 키 속성을 명시적으로 수정해야 합니다.
7. **Function rule(함수 규칙):** 액션의 파라미터에서 입력을 얻는 온톨로지 편집 함수(function)를 참조할 때 사용합니다. 이 규칙이 있으면 다른 규칙은 구성할 수 없습니다. 함수 코드만으로 다른 규칙이 하는 모든 일을 처리할 수 있기 때문입니다. [함수 기반 액션 타입](11_function-backed-actions/01_function-actions-overview.md)에서 더 읽어 보세요.
8. **Create object(s) of interface(인터페이스의 객체 생성):** 특정 인터페이스를 구현하는 임의 타입의 객체를 생성할 때 사용합니다. [인터페이스에 대한 액션](09_actions-on-interfaces.md)에서 더 읽어 보세요.
9. **Modify object(s) of interface(인터페이스의 객체 수정):** 특정 인터페이스를 구현하는 타입의 객체를 수정할 때 사용합니다. [인터페이스에 대한 액션](09_actions-on-interfaces.md)에서 더 읽어 보세요.
10. **Delete object(s) of interface(인터페이스의 객체 삭제):** 특정 인터페이스를 구현하는 타입의 객체를 삭제할 때 사용합니다. [인터페이스에 대한 액션](09_actions-on-interfaces.md)에서 더 읽어 보세요.
11. **Create link(s) on object(s) of interface(인터페이스 객체에 링크 생성):** 특정 인터페이스를 구현하는 타입의 객체들 사이에 링크를 생성할 때 사용합니다. [인터페이스에 대한 액션](09_actions-on-interfaces.md)에서 더 읽어 보세요.
12. **Delete link(s) on object(s) of interface(인터페이스 객체의 링크 삭제):** 특정 인터페이스를 구현하는 타입의 객체들 사이의 링크를 삭제할 때 사용합니다. [인터페이스에 대한 액션](09_actions-on-interfaces.md)에서 더 읽어 보세요.

**설명**: 링크를 다루는 방법이 링크 종류에 따라 다른 이유는 관계형 데이터베이스의 설계와 같습니다. 일대다 관계는 보통 "다" 쪽 테이블에 외래 키 열을 두어 표현합니다. 예를 들어 `Employee` 테이블의 `department_id` 열이 `Department`를 가리키면, 직원을 다른 부서로 옮기는 일은 `UPDATE employee SET department_id = 'D2' WHERE employee_id = 'E1'`처럼 그 행의 열 값을 바꾸는 일입니다. 그래서 온톨로지에서도 **Modify object** 규칙으로 외래 키 속성을 수정합니다. 반면 다대다 관계는 별도의 조인 테이블(예: `employee_project(employee_id, project_id)`)에 행을 넣고 빼는 방식이므로 **Create link**와 **Delete link** 규칙이 따로 있습니다.

> **중간 요약**: 온톨로지 규칙은 객체와 링크를 생성, 수정, 삭제하며, 인터페이스를 구현하는 객체를 대상으로 하는 규칙도 있습니다. 다대다 링크는 링크 규칙으로, 일대일과 일대다 링크는 외래 키 속성을 수정하는 객체 규칙으로 다룹니다. 함수 규칙을 쓰면 다른 규칙은 함께 쓸 수 없습니다.

<a id="values-and-parameters"></a>
### 값과 파라미터 (Values and parameters)

링크와 객체를 생성하거나 수정할 때 규칙은 동작에 필요한 추가 값을 요구합니다. 객체를 수정할 때는 규칙이 어떤 속성을 수정할지도 정의합니다. 각 속성은 다음 여러 선택지 중 하나가 제공하는 값에 매핑됩니다(링크에 대한 규칙은 객체 참조 파라미터만 받을 수 있습니다).

* **From parameter(파라미터에서):** 속성과 같은 타입을 가진 기존 파라미터입니다. 기본적으로 규칙에 새 속성을 추가할 때마다 같은 이름의 파라미터가 자동으로 만들어지고, 속성은 그 파라미터의 값을 받도록 매핑됩니다.
* **Object parameter property(객체 파라미터의 속성):** 기존 객체 참조 파라미터의 속성입니다. 객체 파라미터 쪽 속성의 타입은 매핑되는 속성의 타입과 일치해야 합니다.
* **Static value(정적 값):** 액션 타입의 규칙 부분에만 존재하는 고정 값입니다. 이 값은 Workshop, Slate, Object Views에서 액션을 사용할 때 바꿀 수 없습니다.
* **Current User/Time(현재 사용자/시간):** 문자열과 타임스탬프 속성은 액션을 실행하는 현재 사용자나 액션 실행이 시작된 시각 같은 맥락 값을 받을 수도 있습니다. 시간 값은 실행하는 동안 고정되며, [액션 로그와 편집 이력의 커밋 타임스탬프](26_action-log.md#action-log-timestamps)와 다를 수 있습니다. **Static value**와 마찬가지로 이 값들은 액션을 제출할 때 사용자가 조작할 수 없으며, 액션 타입의 다른 부분에서 사용할 수도 없습니다.

**설명**: 예를 들어 `Ticket` 객체를 수정하는 규칙에서 `status` 속성은 "From parameter"로 사용자가 고른 값을 받고, `last_modified_by` 속성은 "Current User"로, `last_modified_at` 속성은 "Current Time"으로, `source` 속성은 "Static value"로 항상 `"manual"`을 받도록 매핑할 수 있습니다. 이 경우 사용자 입력 폼에는 `status`만 나타나고 나머지 세 값은 자동으로 채워집니다.

<a id="creating-an-object-many-to-many-link"></a>
### 객체와 다대다 링크를 함께 생성하기 (Creating an object & many-to-many link)

객체와 다대다 링크를 동시에 생성할 수도 있습니다. 다대다 링크만 생성하려면 링크 양쪽의 객체가 미리 존재해야 하지만, 하나의 액션 타입으로 두 엔터티를 모두 생성할 수 있습니다. 먼저 다대다 링크를 가진 객체 타입으로 **Create object** 규칙을 구성합니다. 그런 다음 **Add property** 아래에 있는 **Add link** 버튼을 클릭해 링크 타입을 선택하고 링크를 구성합니다.

일대다 또는 일대일 링크를 생성하려면 객체의 외래 키를 편집하기만 하면 됩니다.

<a id="invalid-combinations"></a>
### 허용되지 않는 조합 (Invalid combinations)

액션 타입에는 여러 온톨로지 규칙을 조합해 넣을 수 있습니다. 여러 규칙이 정의되어 있으면 액션 백엔드는 규칙들을 컴파일해 객체당 하나의 편집(예: **Add object**, **Modify object(s)**, **Delete object(s)**)을 생성합니다. 예를 들어 한 규칙의 결과가 어떤 속성을 "A"로 업데이트하고, 같은 액션 타입의 다른 규칙이 같은 객체의 같은 속성을 "B"로 업데이트하면, 최종 편집은 그 속성을 "B"로 업데이트하는 것 하나가 됩니다. 규칙의 순서가 최종 객체 편집에 영향을 줍니다. 그 결과 다음과 같은 객체 편집 조합은 지원되지 않습니다.

* 객체를 추가하거나 수정하기 전에 삭제할 수 없습니다.
* 객체를 추가하기 전에 수정할 수 없습니다.
* 한 번의 폼 제출에서 같은 객체를 두 번 생성할 수 없습니다.

**설명**: "객체당 하나의 편집으로 컴파일한다"는 말은, 규칙 목록을 위에서 아래로 차례로 적용한 결과를 객체별로 합쳐 최종 상태 하나만 남긴다는 뜻입니다. 규칙 1이 `T1.status = "A"`, 규칙 2가 `T1.status = "B"`라면 T1에 대해서는 `status = "B"`라는 수정 하나만 기록됩니다. 이렇게 합치는 방식이기 때문에 "삭제한 뒤 다시 수정"처럼 순서상 성립하지 않는 조합은 금지됩니다.

> **중간 요약**: 규칙의 각 속성은 파라미터, 객체 파라미터의 속성, 정적 값, 현재 사용자나 시간 중 하나에서 값을 받습니다. 여러 규칙은 객체당 편집 하나로 합쳐지므로, 삭제 후 수정, 생성 전 수정, 이중 생성 같은 조합은 허용되지 않습니다.

<a id="other-rules"></a>
## 기타 규칙 (Other rules)

[부수 효과(side effect)](12_side-effects/01_side-effects-overview.md)를 일으키는 규칙은 두 종류가 있습니다.

* [**Notification(알림)**](12_side-effects/02_notifications.md) 규칙은 액션에 대한 알림을 보낼 때 사용합니다. 파라미터를 사용해 알림 내용과 수신자를 맞춤 설정할 수 있습니다. 최종 사용자는 플랫폼 내 푸시 알림, 이메일, 또는 둘 다로 알림을 받도록 자신의 설정을 조정할 수 있습니다. 알림은 액션의 모든 편집이 적용된 뒤에 전송되지만, 알림 내용은 편집이 적용되기 전의 온톨로지 상태를 기준으로 생성됩니다.
* [**Webhooks(웹훅)**](12_side-effects/04_webhooks.md)는 액션이 적용될 때 액션이 외부 시스템에 요청을 보낼 수 있게 합니다. 액션 파라미터를 웹훅에 전달할 수 있고, 웹훅은 다시 그 파라미터를 외부 요청으로 넘길 수 있습니다. 웹훅은 편집이 적용되기 전 또는 후에 실행되도록 구성할 수 있습니다.

[빌드(build)](https://www.palantir.com/docs/foundry/data-integration/builds/)를 트리거하는 고급 규칙이 하나 더 있습니다.

* [**Schedule(스케줄)**](13_trigger-schedule-build.md) 규칙은 스케줄의 빌드를 트리거할 때 사용합니다. 액션 파라미터를 스케줄에 전달할 수 있고, 스케줄은 다시 빌드 안의 [파라미터화된 변환(parameterized transforms)](https://www.palantir.com/docs/foundry/building-pipelines/parameterization/)에 파라미터를 넘길 수 있습니다. Foundry는 빌드가 시작된 뒤에 온톨로지 편집을 적용합니다.

**설명**: 부수 효과는 온톨로지 데이터를 바꾸는 것 외에 바깥 세계에 영향을 주는 동작을 말합니다. 웹훅은 HTTP 요청을 외부 시스템(예: 사내 ERP의 REST API)으로 보내는 것이고, 알림은 사람에게 메시지를 보내는 것입니다. 빌드는 Foundry에서 데이터 파이프라인(변환 코드)을 실행해 데이터셋을 다시 계산하는 작업이며, 스케줄은 그런 빌드를 언제 어떤 범위로 돌릴지 정해 둔 설정입니다.

> **중간 요약**: 온톨로지 편집 외에도 알림 규칙과 웹훅 규칙으로 부수 효과를 일으킬 수 있고, 스케줄 규칙으로 데이터 파이프라인 빌드를 트리거할 수 있습니다.

## 정리

- 규칙은 액션 타입이 파라미터를 받아 실제로 수행하는 로직입니다.
- 온톨로지 규칙은 객체(일반 또는 인터페이스 구현 객체)와 링크를 생성, 수정, 삭제합니다. 일대일과 일대다 링크는 외래 키 속성 수정으로 다룹니다.
- 함수 규칙을 쓰면 그 규칙 하나만 둘 수 있습니다.
- 속성 값은 파라미터, 객체 파라미터의 속성, 정적 값, 현재 사용자나 시간에서 가져옵니다.
- 여러 규칙은 객체당 편집 하나로 합쳐지므로 순서상 모순되는 조합은 허용되지 않습니다.
- 알림, 웹훅, 스케줄 규칙으로 온톨로지 밖의 효과를 일으킬 수 있습니다.
