# 파라미터 구성의 성능 고려 사항 (Performance considerations)

- 원문: https://www.palantir.com/docs/foundry/action-types/parameter-performance-considerations/
- 사이드바 위치: Define Ontologies > Action types > Parameters > Performance considerations

이 페이지는 파라미터끼리 서로 참조하는 의존 관계가 액션 폼의 로딩 시간에 어떤 영향을 주는지 설명합니다. 기본값이나 드롭다운 선택지를 다른 파라미터에 기대어 정의하면 값을 순서대로 계산해야 하므로, 의존 관계를 얕게 유지하는 설계 원칙을 알아 두면 폼 응답 속도를 개선할 수 있습니다.

## 파라미터 구성의 성능 고려 사항 (Performance considerations for parameter configuration)

[기본값](02_parameters-default-value.md)이나 [다중 선택 옵션](03_parameters-filter.md)의 정의처럼 파라미터 사이에 의존 관계가 있으면 액션 폼이 로드되는 데 걸리는 시간에 영향을 줄 수 있습니다. 예를 들어 다음과 같은 액션 파라미터 구성을 생각해 보겠습니다.

1. 첫 번째 파라미터는 `from single result of object set`(객체 집합의 단일 결과에서) 기본값을 가진 `object reference`(객체 참조)입니다.
2. 두 번째 파라미터는 문자열이며, 기본값은 첫 번째 파라미터를 참조하는 `object parameter property`(객체 파라미터의 속성)입니다.
3. 세 번째 파라미터도 문자열이며 기본값은 없지만, `get options from an object set`(객체 집합에서 선택지 가져오기)을 사용하는 `multiple choice`(다중 선택) 드롭다운으로 구성되어 있습니다. 이 객체 집합 정의는 두 번째 파라미터를 참조합니다.

사용자가 이 액션의 폼을 로드하면 여러 연산이 차례로 수행되어야 합니다.

1. 먼저 첫 번째 파라미터의 기본값을 가져와야 합니다.
2. 그다음 첫 번째 파라미터 값에서 두 번째 파라미터의 기본값을 도출해야 합니다.
3. 마지막으로 두 번째 파라미터 값에서 세 번째 파라미터의 선택지를 도출해야 합니다.

액션 파라미터를 구성할 때는 의존 계층을 가능한 한 평평하게 유지하는 것이 좋습니다. 위에서 설명한 액션의 경우, 세 번째 파라미터의 객체 집합 정의에서 두 번째 파라미터 대신 첫 번째 파라미터를 참조하면 두 번째와 세 번째 파라미터에 필요한 정보를 병렬로 도출할 수 있으므로, 폼을 연 시점부터 폼이 완전히 상호 작용 가능해지는 시점까지의 전체 지연 시간이 줄어듭니다.

**설명**: 의존 관계를 그래프로 보면 원래 구성은 `P1`에서 `P2`, `P2`에서 `P3`로 이어지는 길이 3의 사슬입니다. 각 단계가 서버 조회 한 번(예: 100ms)이라면 총 약 300ms가 걸립니다. `P3`가 `P1`을 직접 참조하도록 바꾸면 `P1`이 정해진 뒤 `P2`와 `P3`를 동시에 계산할 수 있어 깊이가 2가 되고, 총 약 200ms로 줄어듭니다. 전체 지연 시간은 의존 그래프에서 가장 긴 경로의 길이에 비례하므로, 경로를 짧게 만드는 것이 핵심입니다.

## 정리

- 기본값이나 다중 선택 옵션이 다른 파라미터에 의존하면 폼 로딩 시 값을 순차적으로 계산해야 합니다.
- 의존 사슬이 길수록 폼이 완전히 사용 가능해지기까지 오래 걸립니다.
- 가능하면 여러 파라미터가 같은 상위 파라미터를 직접 참조하게 해 의존 계층을 평평하게 유지하면 병렬 계산으로 지연 시간을 줄일 수 있습니다.
