# 온톨로지 설계: 안티패턴 (Ontology design: Anti-patterns)

- 원문: https://www.palantir.com/docs/foundry/ontology/ontology-anti-patterns/
- 사이드바 위치: Define Ontologies > Ontology design: Anti-patterns

이 페이지는 온톨로지(Ontology)를 설계할 때 자주 빠지는 잘못된 설계 습관, 즉 안티패턴(anti-pattern) 8가지를 정리합니다. 각 안티패턴마다 왜 생기는지, 어떤 징후로 알아챌 수 있는지, 어떤 문제가 생기는지, 어떻게 고치는지를 같은 틀로 설명합니다. 데이터베이스 설계에서 정규화를 배우며 "이렇게 테이블을 나누면 안 된다"는 사례를 익히듯이, 온톨로지 설계에서도 피해야 할 형태를 미리 알아 두면 규모가 커진 뒤 구조를 뜯어고치는 비용을 줄일 수 있습니다.

**설명**: 안티패턴은 "처음에는 그럴듯해 보이지만 반복해서 문제를 일으키는 것으로 알려진 설계 방식"을 가리키는 소프트웨어 공학 용어입니다. 디자인 패턴이 권장하는 해법의 목록이라면, 안티패턴은 피해야 할 해법의 목록입니다.

숙련된 온톨로지 설계자도 처음에는 합리적으로 보이지만 온톨로지가 커질수록 큰 문제를 일으키는 흔한 설계 함정에 빠질 수 있습니다. 이 절에서는 반복해서 나타나는 안티패턴을 짚고, 왜 생기는지 설명하며, 이를 피하거나 해결하는 구체적인 지침을 제공합니다.

이 안티패턴들을 피하면 비즈니스 도메인을 정확하게 표현하고, 유지 보수 부담을 줄이며, 여러 부서에 걸친 강력한 워크플로를 가능하게 하는 온톨로지를 만들 수 있습니다.

| 안티패턴 | 설명 | 해결책 |
|-------------|-------------|----------|
| [시스템 사일로(System Silos)](#anti-pattern-system-silos) | 소스 시스템마다 별도의 객체 타입을 만듭니다. | 파이프라인에서 데이터를 병합하고, 통합된 객체 타입을 만듭니다. |
| [키친 싱크(The Kitchen Sink)](#anti-pattern-the-kitchen-sink) | 불필요한 기술용 열을 속성(property)으로 포함합니다. | 속성을 의도적으로 선별하고, ETL 메타데이터는 제외합니다. |
| [부서 사일로(Department Silos)](#anti-pattern-department-silos) | 부서마다 공통 엔터티의 자기 버전을 만듭니다. | 공용 객체 타입을 만들고, 부서별 데이터는 속성과 링크로 표현합니다. |
| [갓 오브젝트(The God Object)](#anti-pattern-the-god-object) | 객체 타입 하나가 서로 다른 여러 엔터티를 표현합니다. | 서로 다른 객체 타입을 만들고, 공통 특성은 인터페이스로 표현합니다. |
| [골든 해머(The Golden Hammer)](#anti-pattern-the-golden-hammer) | 문제마다 알맞은 기능을 고르지 않고 하나의 도구(예: 액션 타입, 파이프라인, 함수)에 지나치게 의존합니다. | 작업에 맞는 도구를 고릅니다. 데이터 처리에는 배치 또는 스트리밍 파이프라인, 사람의 결정에는 액션, 이벤트 기반 반응에는 오토메이션, 복잡한 실시간 로직에는 함수를 씁니다. |
| [액션 난립(Action Sprawl)](#anti-pattern-action-sprawl) | 응집된 비즈니스 작업 대신 속성 하나만 바꾸는 액션을 잔뜩 만듭니다. | 관련된 변경을 의미 있는 워크플로로 묶는 비즈니스 작업 단위로 액션을 설계합니다. |
| [타임머신(The Time Machine)](#anti-pattern-the-time-machine) | 과거 버전을 별도의 객체나 객체 타입으로 모델링합니다. | 엔터티당 객체 하나를 두고, 이력 또는 변경(amendment) 객체를 링크로 연결하며, 시계열 속성을 사용합니다. |
| [잘못된 이름(The Misnomer)](#anti-pattern-the-misnomer) | 온톨로지 요소에 모호하거나, 일반적이거나, 오해를 부르는 이름을 씁니다. | 구체적이고 설명적인 이름을 쓰고, 모호한 속성 이름은 한정어를 붙이며, 링크는 관계에 따라 이름 짓습니다. |

> **중간 요약**: 이 페이지는 8가지 온톨로지 설계 안티패턴을 다루며, 각각 원인, 예시, 문제, 해결책의 순서로 설명합니다.

<a id="anti-pattern-system-silos"></a>
## 안티패턴: 시스템 사일로 (Anti-pattern: System Silos)

시스템 사일로는 실제 세계의 엔터티 자체를 모델링하지 않고, 데이터가 들어오는 소스 시스템을 기준으로 같은 실제 엔터티에 대해 별도의 객체 타입을 만들 때 생깁니다.

**설명**: 사일로(silo)는 원래 곡물 저장탑을 뜻하며, IT에서는 서로 연결되지 않고 고립된 데이터나 조직을 가리키는 용어로 쓰입니다.

<a id="common-causes"></a>
### 흔한 원인

* 팀마다 서로 다른 소스 시스템을 소유하고 독립적으로 구축함
* 여러 소스의 데이터를 어떻게 병합해야 할지 확신이 없음
* 무엇이 필수인지 정하지 않고 시스템별 필드를 모두 보존하고 싶어 함

<a id="example"></a>
### 예시

조직의 직원 데이터가 인사(HR) 시스템, 출입 배지 시스템, 프로젝트 관리 도구 세 곳에 있습니다. `Employee` 객체 타입 하나를 만드는 대신 다음과 같이 만듭니다.

* `HR System Employee`
* `Badge System Employee`
* `Project Management Employee`

<a id="problems"></a>
### 문제

| 문제 | 영향 |
|---------|--------|
| 현실에 대한 조각난 시야 | 최종 사용자는 직원 한 명에 대한 통합된 모습을 볼 수 없고, 전체 그림을 이해하려면 여러 객체 타입을 오가야 합니다. |
| 중복된 노력 | 개념상 같은 엔터티를 위해 액션 타입, 링크 타입, 애플리케이션을 여러 번 만들어야 합니다. |
| 일관되지 않은 데이터 | 같은 직원이 객체 타입마다 서로 충돌하는 정보를 가질 수 있고, 무엇이 기준 정보(source of truth)인지 분명하지 않습니다. |
| 복잡한 유지 보수 | 비즈니스 로직을 바꾸면 시스템별 객체 타입 모두에 똑같이 반영해야 합니다. |

<a id="solution"></a>
### 해결책

실제 세계의 엔터티를 나타내는 객체 타입 하나를 만들고, 데이터 파이프라인으로 여러 소스 시스템의 정보를 하나의 통합된 백킹 데이터셋으로 병합합니다.

```
✗ Avoid                          ✓ Prefer
─────────────────────────────    ─────────────────────────────
HR System Employee               Employee
Badge System Employee         →  (backed by merged dataset
Project Management Employee      from all three systems)
```

**설명**: 왼쪽(Avoid, 피할 것)은 시스템별로 나뉜 객체 타입 세 개이고, 오른쪽(Prefer, 권장)은 세 시스템의 데이터를 병합한 데이터셋을 백킹 데이터소스(backing datasource)로 쓰는 `Employee` 객체 타입 하나입니다.

이를 구현하려면 다음과 같이 합니다.

1. 여러 시스템에 걸쳐 엔터티를 유일하게 식별하는 기본 키(primary key)를 찾습니다(예: 직원 ID).
2. 모든 소스 시스템의 데이터를 조인하는 변환(transform)을 만듭니다.
3. 값이 충돌할 때 적용할 명확한 우선순위 규칙을 정합니다(예: 직책은 HR 시스템을 기준으로 함).
4. 병합된 데이터셋을 백킹 데이터셋으로 하는 객체 타입 하나를 만듭니다.

**설명**: 구체적으로 보면, HR 테이블에 `(E001, 김민수, 선임연구원)`, 배지 테이블에 `(E001, 3층 출입 가능)`, 프로젝트 테이블에 `(E001, 프로젝트 A)` 행이 있을 때, 변환 단계에서 `employee_id`를 키로 세 테이블을 조인하면 `(E001, 김민수, 선임연구원, 3층 출입 가능, 프로젝트 A)`라는 한 행이 나옵니다. 이 행이 `Employee` 객체 하나가 됩니다. 두 시스템에 직책 값이 모두 있고 서로 다르다면 3단계의 우선순위 규칙에 따라 HR 값을 택하는 식입니다.

> **중간 요약**: 소스 시스템별로 객체 타입을 나누지 말고, 파이프라인에서 데이터를 기본 키 기준으로 병합해 실제 엔터티당 객체 타입 하나를 만듭니다.

<a id="anti-pattern-the-kitchen-sink"></a>
## 안티패턴: 키친 싱크 (Anti-pattern: The Kitchen Sink)

이 안티패턴("부엌 싱크대 빼고 다 넣기(everything but the kitchen sink)"라고도 함)은 객체 타입에 온톨로지 맥락에서는 비즈니스상 의미가 없는 외부 시스템의 불필요한 열을 포함시켜, 데이터 모델을 기술적 부산물로 어지럽힐 때 생깁니다.

**설명**: "everything but the kitchen sink"는 "있는 것을 몽땅 다"라는 뜻의 영어 관용 표현입니다. 이 안티패턴의 이름은 그 표현에서 따왔습니다.

<a id="common-causes"></a>
### 흔한 원인

* "혹시 모르니까" 사고방식(나중에 쓸모 있을지 모르는 필드를 남겨 둠)
* 어떤 필드가 의미 있는지에 대한 명확한 기준이 없음
* 선별 과정 없이 소스 시스템을 그대로 매핑함
* 열을 제외하면 데이터를 잃을까 하는 두려움

<a id="example"></a>
### 예시

CRM 시스템 연동 데이터로 `Customer` 객체 타입을 만들면서, 사용 가능한 열을 모두 포함합니다. 아래에서 (포함)은 남길 만한 열, (제외)는 빼야 할 열입니다.

* customer\_id (포함)
* customer\_name (포함)
* email (포함)
* \_crm\_extracted\_at (제외)
* \_crm\_received\_at (제외)
* \_crm\_batched\_at (제외)
* \_crm\_sequence (제외)
* \_crm\_table\_version (제외)
* \_crm\_internal\_record\_id (제외)
* last\_etl\_update\_timestamp (제외)

**설명**: 원문은 각 열 옆에 체크 표시와 X 표시를 붙여 남길 열과 뺄 열을 구분합니다. 여기서는 괄호 표기로 바꿨습니다. `_crm_extracted_at`처럼 밑줄로 시작하는 열은 데이터를 추출하고 적재한 시각, 배치 번호 같은 ETL(Extract, Transform, Load: 데이터를 꺼내 변환하고 적재하는 과정) 메타데이터입니다. 데이터 엔지니어가 파이프라인을 디버깅할 때는 쓸모가 있지만, 고객을 조회하는 업무 사용자에게는 의미가 없습니다.

<a id="problems"></a>
### 문제

| 문제 | 영향 |
|----------|--------|
| 혼란 | 최종 사용자가 비즈니스 데이터 옆에 관련 없는 기술 필드를 보게 됩니다. |
| 성능 저하 | 불필요한 속성은 데이터 규모, 연산량, 인덱스(index) 크기를 늘리고 검색을 느리게 합니다. |
| 인사이트가 가려짐 | 중요한 비즈니스 속성이 시스템 메타데이터 사이에 묻힙니다. |

<a id="solution"></a>
### 해결책

속성을 의도적으로 선별합니다. 비즈니스상 의미가 분명하고 워크플로에 유용할 열만 포함합니다.

어떤 속성을 포함할지 정할 때 다음 지침을 사용합니다.

| 포함 | 제외 |
|----------|----------|
| 비즈니스 식별자(고객 ID, 주문 번호) | 파이프라인 메타데이터 |
| 사람이 읽을 수 있는 특성(이름, 설명) | 비즈니스 의미가 없는 내부 시스템 ID |
| 비즈니스 프로세스와 관련된 날짜 | 데이터 엔지니어링에만 관련된 타임스탬프 |
| 필터링이나 액션에 필요한 상태 필드 | 파이프라인 디버깅용 감사(audit) 열 |

이를 구현하려면 다음과 같이 합니다.

1. 각 열을 검토하며 "누군가 이 값을 보거나, 검색하거나, 이것으로 필터링할 일이 있을까?"라고 묻습니다.
2. 기술 메타데이터는 디버깅을 위해 백킹 데이터셋에 남겨 두되, 속성으로 노출하지 않습니다.
3. 존재는 해야 하지만 거의 필요하지 않은 애매한 속성은 속성 가시성(visibility) 설정으로 숨깁니다.
4. 각 속성이 왜 존재하고 누가 쓰는지 문서화합니다.

**설명**: 2단계가 핵심입니다. 백킹 데이터셋의 열과 객체 타입의 속성은 일대일로 모두 대응할 필요가 없습니다. 데이터셋에는 열이 10개 있어도 객체 타입에는 그중 3개만 속성으로 매핑할 수 있으므로, 데이터를 버리지 않고도 온톨로지를 깔끔하게 유지할 수 있습니다. SQL로 보면 원본 테이블은 그대로 두고 필요한 열만 고른 뷰(view)를 사용자에게 보여 주는 것과 같은 구조입니다.

> **중간 요약**: 소스 시스템의 열을 전부 속성으로 옮기지 말고, 업무 사용자가 보거나 검색하거나 필터링할 열만 속성으로 만듭니다. 기술 메타데이터는 백킹 데이터셋에만 남깁니다.

<a id="anti-pattern-department-silos"></a>
## 안티패턴: 부서 사일로 (Anti-pattern: Department Silos)

부서 사일로는 서로 다른 부서가 같은 객체 타입의 자기 버전을 각자 만들 때 생기며, 그 결과 온톨로지가 비즈니스 현실이 아니라 조직 구조를 그대로 반영하는 조각난 형태가 됩니다.

<a id="common-causes"></a>
### 흔한 원인

* 부서 간 협업 없이 각자 고립되어 작업함
* 팀마다 자기 팀이 보는 고객의 모습이 고유하다고 믿음
* 거버넌스나 중앙의 온톨로지 설계 책임 조직이 없음
* 팀이 "자기" 데이터에 대한 자율성과 통제권을 원함

<a id="example"></a>
### 예시

여러 부서가 고객 데이터를 다뤄야 하고, 각 부서가 자기 객체 타입을 만듭니다.

* 영업팀이 `Sales Customer`를 만듦
* 고객 지원팀이 `Support Customer`를 만듦
* 재무팀이 `Billing Customer`를 만듦
* 마케팅팀이 `Marketing Contact`를 만듦

네 객체 타입 모두 같은 실제 엔터티, 즉 고객을 나타냅니다.

<a id="problems"></a>
### 문제

| 문제 | 영향 |
|---------|--------|
| 단일 기준 정보 없음 | 부서마다 같은 고객에 대해 서로 충돌하는 정보를 가집니다. |
| 부서 간 워크플로 불가능 | "영업, 지원, 청구 전반에서 이 고객과의 모든 상호작용을 보여 줘" 같은 질문에 쉽게 답할 수 없습니다. |
| 중복 개발 | 부서마다 같은 역할의 액션, 링크, 애플리케이션을 중복해서 만듭니다. |
| 거버넌스의 악몽 | 데이터 품질 문제가 늘어나고, 한 객체 타입에서 고친 내용이 다른 객체 타입에 반영되지 않습니다. |

<a id="solution"></a>
### 해결책

여러 부서가 함께 쓰는 공용 객체 타입을 만들고, 필요한 곳에서는 속성과 링크로 부서별 정보를 담습니다.

```
✗ Avoid                          ✓ Prefer
─────────────────────────────    ─────────────────────────────
Sales Customer                   Customer
Support Customer           →       ├── salesStatus (property)
Billing Customer                   ├── supportTier (property)
Marketing Contact                  ├── billingAccountId (property)
                                   └── Links to:
                                       ├── Sales Opportunities
                                       ├── Support Tickets
                                       └── Invoices
```

**설명**: 권장안에서는 `Customer` 객체 타입 하나에 부서별 특성(`salesStatus`, `supportTier`, `billingAccountId`)을 속성으로 두고, 영업 기회, 지원 티켓, 청구서처럼 부서 고유의 데이터는 별도 객체 타입으로 만든 뒤 `Customer`와 링크로 연결합니다. 관계형 데이터베이스로 보면 `customers` 테이블 하나와 `customer_id` 외래 키를 가진 `support_tickets`, `invoices` 테이블이 있는 구조입니다.

이를 구현하려면 다음과 같이 합니다.

1. 부서 경계를 넘어 존재하는 엔터티를 식별합니다.
2. 공용 객체 타입을 정의할 부서 간 작업 그룹을 구성합니다.
3. 공용 객체에 부서별 특성을 담을 때는 속성을 사용합니다.
4. 공용 객체를 부서 고유의 객체에 연결할 때는 링크 타입을 사용합니다(예: `Customer`에서 `Support Ticket`으로 가는 링크).
5. 부서마다 같은 기반 엔터티를 다른 "화면"으로 보고 싶다면 Object View나, 목적에 맞게 구성한 Workshop 및 OSDK 애플리케이션을 활용합니다.
6. 특정 속성을 특정 팀만 볼 수 있어야 한다면 제한된 뷰(restricted view)를 사용합니다.

> **중간 요약**: 부서마다 고객 객체 타입을 따로 만들지 말고, 공용 `Customer` 객체 타입 하나에 부서별 속성과 링크를 붙입니다. 화면 차이는 애플리케이션으로, 접근 제한은 제한된 뷰로 해결합니다.

***

<a id="anti-pattern-the-god-object"></a>
## 안티패턴: 갓 오브젝트 (Anti-pattern: The God Object)

갓 오브젝트 안티패턴은 객체 타입 하나가 서로 다른 여러 실제 엔터티를 표현하도록 과하게 짐을 떠안아, 비대하고 혼란스러우며 유지 보수할 수 없는 객체 타입이 될 때 생깁니다.

**설명**: "God Object"는 객체 지향 프로그래밍에서 너무 많은 일을 아는 클래스 하나(모든 기능이 몰린 거대한 클래스)를 가리키는 안티패턴 이름입니다. 온톨로지에서는 객체 타입 하나에 성격이 다른 엔터티가 몰린 경우를 가리킵니다.

<a id="common-causes"></a>
### 흔한 원인

* 피상적인 유사성에서 나온 과도한 추상화("이것들은 다 자산이다")
* 객체 타입 수를 최소화하려는 욕구
* 구축 전에 엔터티 정의를 명확히 하지 않음
* 기존 객체 타입에 사용 사례가 계속 추가되며 범위가 불어남

<a id="indicators"></a>
### 징후

* 객체 타입에 자주 null인 속성이 많음
* 속성의 의미가 다른 속성 값(예: 유형이나 범주)에 따라 바뀜
* 객체를 볼 때 "이건 어떤 종류의 `[Object]`지?"라고 묻게 됨
* 비즈니스 규칙과 검증에 객체의 "유형"에 따른 조건 분기가 광범위하게 필요함

<a id="example"></a>
### 예시

"가치 있는 모든 것"을 표현하려는 `Asset` 객체 타입을 만들었는데, 결국 다음이 모두 들어갑니다.

* 물리적 장비(트럭, 기계)
* 소프트웨어 라이선스
* 부동산
* 금융 상품
* 직원("인적 자산"으로서)

이 객체 타입은 속성이 150개가 넘고, 어느 객체를 보더라도 대부분의 속성이 null이며, value, location, status 같은 속성의 의미가 그 객체가 어떤 종류의 "자산"이냐에 따라 완전히 달라집니다.

**설명**: 예를 들어 트럭 객체의 `location`은 GPS 좌표이고, 소프트웨어 라이선스 객체의 `location`은 설치된 서버 이름이며, 부동산 객체의 `location`은 주소입니다. 같은 열에 서로 다른 의미의 값이 섞이므로 "location으로 필터링"하는 일 자체가 의미를 잃습니다. 관계형 데이터베이스에서 여러 종류의 엔터티를 테이블 하나에 몰아넣어 대부분의 칸이 NULL인 넓은 테이블이 생기는 것과 같은 문제입니다.

<a id="problems"></a>
### 문제

| 문제 | 영향 |
|---------|--------|
| 의미 혼란 | 최종 사용자가 `Asset`이 실제로 무엇을 나타내는지 이해할 수 없습니다. |
| 희소한 데이터 | 대부분의 객체에서 대부분의 속성이 null이라 데이터를 해석하기 어렵습니다. |
| 검증 불가능 | 규칙이 엔터티 유형마다 다르므로 비즈니스 규칙을 강제할 수 없습니다. |
| 나쁜 검색 경험 | `Assets`를 검색하면 서로 관련 없는 것들이 뒤섞여 나옵니다. |
| 액션 타입의 복잡도 | 액션이 성격이 전혀 다른 엔터티 유형을 복잡한 조건 로직으로 처리해야 합니다. |

<a id="solution"></a>
### 해결책

서로 다른 실제 엔터티에는 서로 다른 객체 타입을 만듭니다. 엔터티들이 공통 속성이나 동작을 실제로 공유한다면 인터페이스로 그 공통 특성을 모델링합니다.

```
✗ Avoid                          ✓ Prefer
─────────────────────────────    ─────────────────────────────
Asset                            Equipment
  - assetType                    Vehicle
  - assetSubtype                 Software License
  - value                  →     Property (Real Estate)
  - location                     Financial Instrument
  - status
  - 145 more properties...       Interface: Depreciable Asset
                                   - purchaseDate
                                   - purchaseValue
                                   - depreciationSchedule
```

**설명**: 권장안은 엔터티별 객체 타입 다섯 개(장비, 차량, 소프트웨어 라이선스, 부동산, 금융 상품)를 만들고, 감가상각 대상이라는 공통점만 `Depreciable Asset` 인터페이스(구입일, 구입 가격, 감가상각 일정)로 묶습니다. 객체 지향 언어로 보면 거대한 클래스 하나 대신 `Vehicle`, `Equipment` 같은 클래스를 따로 만들고 이들이 `DepreciableAsset` 인터페이스를 구현하게 하는 구조입니다. 이렇게 하면 "감가상각 대상 자산 전체"를 조회하는 기능은 인터페이스를 통해 유지하면서도 각 객체 타입은 자기에게 의미 있는 속성만 가집니다.

이를 구현하려면 다음과 같이 합니다.

1. 현재 그 객체 타입이 표현하는 서로 다른 실제 엔터티를 나열합니다.
2. 엔터티마다 별도의 객체 타입을 만듭니다.
3. 실제로 공유되는 속성과 동작을 식별합니다.
4. 인터페이스로 여러 객체 타입에 걸친 공통 특성을 모델링합니다.
5. 기존 객체를 알맞은 새 객체 타입으로 옮깁니다.

> **중간 요약**: 성격이 다른 엔터티를 객체 타입 하나에 몰아넣지 말고 엔터티별 객체 타입으로 나누며, 진짜 공통점만 인터페이스로 묶습니다. null이 많은 속성과 유형에 따라 의미가 바뀌는 속성이 대표적인 징후입니다.

<a id="anti-pattern-the-golden-hammer"></a>
## 안티패턴: 골든 해머 (Anti-pattern: The Golden Hammer)

골든 해머 안티패턴은 다른 접근이 더 적절한 경우에도 하나의 도구에 지나치게 의존해 모든 문제를 풀려고 할 때 생깁니다. 이 이름은 ["가진 것이 망치뿐이면 모든 것이 못으로 보인다" ↗](https://en.wikipedia.org/wiki/Law_of_the_instrument)라는 말에서 왔습니다.

이 안티패턴은 파이프라인에 더 맞는 작업에 액션 타입을 남용하거나, 이벤트 기반 오토메이션이어야 할 로직을 파이프라인으로 만들거나, 변환(transform)에서 미리 계산하는 편이 나은 계산을 함수(function)로 작성하는 형태로 나타납니다.

**설명**: 여기서 나오는 도구들을 간단히 정리하면 다음과 같습니다. 파이프라인은 데이터셋을 입력받아 정제, 조인, 집계한 데이터셋을 출력하는 데이터 처리 흐름이며, 배치(batch)는 정해진 시점에 모아서 한 번에 처리하는 방식이고 스트리밍(streaming)은 데이터가 들어오는 대로 계속 처리하는 방식입니다. 액션은 사용자가 화면에서 실행해 객체를 바꾸는 작업입니다. 오토메이션(automation)은 "객체가 생성됨" 같은 이벤트나 일정을 조건으로 정해 두면 자동으로 액션이나 알림을 실행하는 기능입니다. 함수는 요청 시점에 실행되는 코드입니다.

<a id="common-causes"></a>
### 흔한 원인

* 팀이 익숙하고 눈에 잘 띄는 도구에 과도하게 의존함
* 계산이 언제 일어날지를 최종 사용자가 "통제"하게 하고 싶어 함
* 플랫폼 전체(파이프라인, 오토메이션, 함수, 예약된 빌드 등)에 익숙하지 않음
* 전체 도구 모음을 고려하지 않고 한 계층(온톨로지 우선, 파이프라인 우선, 코드 우선)으로만 생각함

<a id="examples"></a>
### 예시

**액션 타입에 대한 과도한 의존:**

지역별 총매출을 보여 주는 대시보드용 집계 지표를 계산해야 합니다. 데이터 파이프라인으로 이 지표를 미리 계산하는 대신, 최종 사용자가 직접 실행해야 하는 `Calculate Regional Sales Totals`라는 액션 타입을 만듭니다. 결과는 액션을 통해 객체에 다시 기록됩니다.

**파이프라인에 대한 과도한 의존:**

센서 측정값이 임계치를 넘으면 파이프라인이 경보(alert) 객체를 만듭니다. 이 경보를 당번(on-call) 엔지니어에게 자동으로 배정하고 알림을 보내고 싶습니다. 새 객체에 반응하는 오토메이션을 쓰는 대신, 담당자를 결정하고 배정 결과를 백킹 데이터셋에 쓰려는 파이프라인 로직을 추가로 만들어, 운영 워크플로 로직을 데이터 통합 단계에 섞어 넣습니다.

**함수에 대한 과도한 의존:**

`fullName` = `firstName` + `lastName` 같은 간단한 속성 파생을 함수 기반 열(function-backed column)로 구현해, 파이프라인의 `concat` 식 하나면 충분한데도 실행 시점 오버헤드와 유지 보수할 코드 저장소를 추가합니다.

<a id="problems"></a>
### 문제

| 문제 | 영향 |
|---------|--------|
| 확장성 한계 | 도구마다 실행 한도가 다르므로 잘못된 도구를 쓰면 한계에 일찍 부딪힙니다. |
| 불필요한 복잡도 | 잘못된 계층에서 로직을 유지하면 움직이는 부품의 수가 늘어납니다. |
| 사용자 부담 | 플랫폼이 자동으로 처리할 수 있는 단계를 최종 사용자가 직접 수행해야 합니다. |
| 성능 문제 | 액션이나 함수를 통한 실시간 계산은 미리 계산된 파이프라인 결과보다 느립니다. 반대로 예약된 파이프라인은 이벤트 기반 반응에 쓰기에는 너무 느립니다. |
| 어려운 디버깅 | 로직이 잘못된 계층에 있으면 장애를 진단하고 해결하기 어렵습니다. |

<a id="solution"></a>
### 해결책

사용 사례에 따라 작업에 맞는 도구를 고릅니다.

| 도구 | 적합한 용도 | 적합하지 않은 용도 |
|------|----------|---------------|
| 액션 타입 | 사람의 결정, 객체 하나 또는 몇 개에 대한 사용자 주도 편집(edit), 즉시 적용되어야 하는 입력 기반 변경. | 배치 계산, 예약된 갱신, 사람이 개입하지 않는 이벤트 기반 반응. |
| 파이프라인(배치) | 배치 데이터 처리, 집계, 정제, 보강(enrichment), 일정에 따라 또는 데이터 도착 시 파생 값 미리 계산. | 개별 객체 변경에 대한 실시간 반응, 사람의 입력이 필요한 로직. |
| 파이프라인(스트리밍) | 소스 데이터가 도착하는 대로 결과가 최신 상태를 유지해야 하는 연속적이고 지연이 짧은 데이터 처리(실시간 대시보드, 실시간 상태 추적, 연속 보강). | 배치로 충분한 드문 갱신, 사람의 입력이 필요한 로직, 온톨로지 수준 이벤트에 대한 반응(오토메이션을 사용). |
| 오토메이션 | 온톨로지 변경(객체 생성, 속성 갱신, 일정 트리거)에 대한 이벤트 기반 반응, 사용자 개입 없이 액션이나 알림을 조율. | 무거운 데이터 처리, 복잡한 다중 데이터셋 조인, 사람의 판단이 필요한 로직. |
| 함수 | 여러 객체에 걸친 복잡한 실시간 계산, 검증 로직, 실시간 온톨로지 상태에 의존해 미리 계산할 수 없는 파생 값. | 파이프라인에서 계산할 수 있는 단순 파생, 대규모 데이터셋의 배치 처리. |
| 일정(Schedules) | 반복적인 파이프라인 빌드, 시간 기반 또는 이벤트 기반의 데이터 갱신 조율. | 개별 객체 수준 변경에 대한 실시간 반응. |

이 지침을 적용한 예시는 다음과 같습니다.

```
✗ Avoid                                          ✓ Prefer
──────────────────────────────────────────────   ──────────────────────────────────────────────
Action: "Calculate Regional Sales"          →    Pipeline that aggregates sales data daily
                                                 into a "Regional Sales Summary" object type.

Action: "Standardize Address Format"        →    Pipeline that cleanses addresses on ingestion.

Action: "Update Inventory Status"           →    Pipeline that sets status based on quantity
(based on quantity thresholds)                   thresholds during each sync.

Action: "Assign Risk Score"                 →    Pipeline or model that calculates risk scores
(using a formula)                                and writes to the backing dataset.

Pipeline that assigns alerts to on-call     →    Automation that triggers an "Assign Alert"
engineers by writing to the backing dataset      action when a new "Alert" object is created.

Pipeline that sends a notification when     →    Automation that monitors for the condition
an object meets a condition                      and sends a notification or triggers an action.

Batch pipeline polling every minute for     →    Streaming pipeline that continuously processes
new IoT sensor readings                          sensor data as it arrives.

Function-backed column for                  →    Pipeline that computes fullName = firstName
fullName = firstName + " " + lastName         + " " + lastName in the backing dataset.

to check for objects needing follow-up           change and triggers the follow-up immediately.
```

**설명**: 위 표의 각 줄을 한국어로 풀면 다음과 같습니다.

| 피할 것 | 권장 |
|---|---|
| 액션 "Calculate Regional Sales"(지역별 매출 계산) | 매일 매출 데이터를 집계해 "Regional Sales Summary" 객체 타입에 넣는 파이프라인 |
| 액션 "Standardize Address Format"(주소 형식 표준화) | 데이터 수집 시점에 주소를 정제하는 파이프라인 |
| 액션 "Update Inventory Status"(수량 임계치 기준 재고 상태 갱신) | 동기화할 때마다 수량 임계치에 따라 상태를 설정하는 파이프라인 |
| 액션 "Assign Risk Score"(공식으로 위험 점수 부여) | 위험 점수를 계산해 백킹 데이터셋에 쓰는 파이프라인 또는 모델 |
| 백킹 데이터셋에 기록해 당번 엔지니어에게 경보를 배정하는 파이프라인 | 새 "Alert" 객체가 생성되면 "Assign Alert" 액션을 실행하는 오토메이션 |
| 객체가 조건을 만족하면 알림을 보내는 파이프라인 | 조건을 감시하다가 알림을 보내거나 액션을 실행하는 오토메이션 |
| 새 IoT 센서 측정값을 찾으려 매분 폴링하는 배치 파이프라인 | 센서 데이터가 들어오는 대로 연속 처리하는 스트리밍 파이프라인 |
| fullName = firstName + " " + lastName 을 계산하는 함수 기반 열 | 백킹 데이터셋에서 fullName을 계산하는 파이프라인 |
| 후속 조치가 필요한 객체를 찾으려 매분 실행되는 예약 파이프라인 | 특정 객체 변경에 반응해 즉시 후속 조치를 실행하는 오토메이션 |

이를 구현하려면 다음과 같이 합니다.

1. **액션 타입을 만들기 전에** "이 작업에 사람의 판단이나 사용자 입력이 필요한가?"라고 묻습니다. 필요 없다면 파이프라인이나 오토메이션에 속할 가능성이 큽니다.
2. **파이프라인에 로직을 추가하기 전에** "이것은 데이터 변환인가, 운영 워크플로인가?"라고 묻습니다. 데이터 정제, 집계, 보강은 파이프라인에 속합니다. 작업 배정, 알림 발송, 개별 변경에 대한 반응은 오토메이션에 속합니다.
3. **함수를 작성하기 전에** "이것을 백킹 파이프라인에서 미리 계산할 수 있는가?"라고 묻습니다. 결과가 소스 데이터 열에만 의존하고 실시간 온톨로지 탐색이 필요 없다면 상류(upstream)에서 계산합니다.
4. **폴링 파이프라인(변경을 감지하려 N분마다 실행되는 파이프라인)을 만들기 전에** "오토메이션이 이 이벤트에 직접 반응할 수 있는가?"라고 묻습니다. 오토메이션은 예약 빌드의 오버헤드 없이 거의 실시간으로 온톨로지 변경에 반응합니다. 소스 시스템의 데이터를 연속 처리해야 하는 경우라면 스트리밍 파이프라인을 고려합니다.
5. **기본값처럼 배치 파이프라인을 택하기 전에** "이 데이터가 계속 최신이어야 하는가?"라고 묻습니다. 소비자가 짧은 지연의 최신성에 의존한다면 스트리밍 파이프라인이 배치 일정이라는 타협을 피하게 해 줍니다.
6. **오토메이션을 사용해** 사용자가 버튼을 누르거나 파이프라인을 폴링하지 않아도 "무언가 바뀌었다"와 "무언가 일어나야 한다" 사이를 연결합니다.

**설명**: 폴링(polling)은 변경이 있었는지 일정 간격으로 반복해서 확인하는 방식이고, 이벤트 기반(event-driven)은 변경이 일어났을 때 그 사실을 통지받아 반응하는 방식입니다. 매분 도는 파이프라인은 변경이 없어도 매번 빌드 비용을 쓰고 최대 1분의 지연이 생기지만, 이벤트 기반 오토메이션은 변경이 있을 때만 실행됩니다.

> **중간 요약**: 액션은 사람의 판단, 파이프라인은 데이터 변환, 오토메이션은 이벤트 반응, 함수는 미리 계산할 수 없는 실시간 로직에 씁니다. 도구를 고르기 전에 표의 질문을 던져 잘못된 계층에 로직을 넣지 않도록 합니다.

<a id="anti-pattern-action-sprawl"></a>
## 안티패턴: 액션 난립 (Anti-pattern: Action Sprawl)

액션 난립은 의미 있는 비즈니스 작업을 표현하는 응집된 액션을 설계하지 않고, 각각 속성 하나만 바꾸는 좁은 범위의 액션 타입을 많이 만들 때 생깁니다.

<a id="common-causes"></a>
### 흔한 원인

* 액션을 비즈니스 작업이 아니라 데이터베이스 열 갱신으로 생각함
* 전체 사용자 경험을 고려하지 않고 액션을 하나씩 덧붙여 만듦
* 액션 하나가 여러 속성 변경을 묶을 수 있다는 점을 잘 모름
* 전통적인 애플리케이션 개발의 CRUD 작업을 그대로 흉내 냄

**설명**: CRUD는 Create, Read, Update, Delete의 약자로, 데이터를 생성, 조회, 수정, 삭제하는 기본 작업을 말합니다. "각 열마다 UPDATE 문 하나"처럼 데이터 조작 단위로 액션을 만들면 이 안티패턴에 빠집니다.

<a id="indicators"></a>
### 징후

* 객체 타입 하나에 액션 타입이 10개 넘게 있음
* 항상 연달아 실행되는 액션이 여러 개 있음
* 액션 이름이 `Set [Property]`나 `Update [Property]`처럼 읽힘
* 최종 사용자가 작업 하나를 끝내는 데 단계가 너무 많다고 불평함

<a id="example"></a>
### 예시

`Employee` 객체 타입에 대해 의미 있는 비즈니스 액션을 만드는 대신 다음을 만듭니다.

* `Update Employee First Name`
* `Update Employee Last Name`
* `Update Employee Email`
* `Update Employee Phone`
* `Update Employee Department`
* `Update Employee Manager`
* ...그리고 속성 하나짜리 액션 20개 더

<a id="problems"></a>
### 문제

| 문제 | 영향 |
|---------|--------|
| 감당하기 어려운 사용 경험 | 최종 사용자가 길고 어수선한 액션 목록을 마주하고 알맞은 액션을 찾는 데 애를 먹습니다. |
| 조각난 워크플로 | 단순한 갱신조차 비즈니스 작업 하나를 끝내려면 액션을 여러 번 제출해야 합니다. |
| 응집된 비즈니스 표현 부재 | 액션이 실제 세계의 프로세스와 대응하지 않아 온톨로지가 직관적이지 않습니다. |
| 조각난 감사 추적 | 변경 이력이 작은 액션 여러 개에 흩어져 무엇이 왜 일어났는지 이해하기 어렵습니다. |

<a id="solution"></a>
### 해결책

액션 타입을 데이터베이스 갱신이 아니라 비즈니스 작업을 중심으로 설계합니다. 관련된 변경을 의미 있는 워크플로로 묶는 액션을 만듭니다.

```
✗ Avoid                                    ✓ Prefer
────────────────────────────────────────   ────────────────────────────────────────
Update Employee First Name                 Update Employee Contact Information
Update Employee Last Name            →       - firstName
Update Employee Email                        - lastName
Update Employee Phone                        - email
                                             - phone

Update Employee Department                 Transfer Employee to New Department
Update Employee Manager              →       - newDepartment
Update Employee Location                     - newManager
                                             - newLocation
                                             - effectiveDate

Create Employee Record                     Onboard New Employee
Set Employee Start Date              →       - All required fields for a new hire
Assign Employee Badge                        - Triggers downstream workflows
Assign Employee Equipment                    (badge assignment, equipment request)
```

**설명**: 권장안의 세 액션은 각각 "연락처 정보 갱신"(이름, 성, 이메일, 전화), "다른 부서로 전보"(새 부서, 새 관리자, 새 근무지, 발효일), "신규 직원 온보딩"(신규 입사자에게 필요한 모든 필드를 받고, 배지 배정과 장비 요청 같은 후속 워크플로를 실행)입니다. 전보처럼 실제로 함께 바뀌는 값을 한 액션의 파라미터로 묶으면, 한 번의 제출로 업무 하나가 끝나고 감사 이력에도 "전보" 한 건으로 남습니다.

이를 구현하려면 다음과 같이 합니다.

1. 객체 데이터를 바꾸는 실제 비즈니스 프로세스를 정리합니다.
2. 관련된 속성 변경을, 그 프로세스를 나타내는 단일 액션으로 묶습니다.
3. 응집된 액션 안에서 선택 입력 필드를 허용하려면 액션 파라미터를 사용합니다.
4. 액션 이름은 비즈니스 작업을 따라 짓습니다: `Transfer Employee`, `Approve Purchase Order`, `Escalate Support Ticket`.
5. 액션 규칙과 검증 로직으로 액션 안에서 비즈니스 제약을 강제합니다.

> **중간 요약**: 속성 하나마다 액션을 만들지 말고, 전보, 온보딩처럼 실제 업무 단위로 관련 변경을 묶은 액션을 만듭니다.

<a id="anti-pattern-the-time-machine"></a>
## 안티패턴: 타임머신 (Anti-pattern: The Time Machine)

타임머신 안티패턴은 시계열 데이터, 스냅숏, 적절한 버전 관리 전략을 쓰지 않고 엔터티의 과거 버전을 별도의 객체나 객체 타입으로 모델링할 때 생깁니다.

<a id="common-causes"></a>
### 흔한 원인

* 모든 변경의 완전한 이력을 보존하고 싶어 함
* 온톨로지에서 시간에 따른 데이터를 모델링하는 방법을 잘못 이해함
* 파일 버전 관리식 사고(v1, v2, v3)를 객체 설계에 적용함
* 시계열 속성이나 링크된 이력 패턴을 모름

<a id="indicators"></a>
### 징후

* 객체 타입 안에 서로 다른 시점의 같은 실제 엔터티를 나타내는 객체가 여러 개 있음
* 사본을 구분하려고 `version`, `revision`, `isCurrent` 같은 속성이 존재함
* 객체 수가 엔터티 수가 아니라 변경 횟수에 비례해 늘어남
* 최종 사용자가 어떤 객체를 참조하거나 링크해야 할지 헷갈려 함

<a id="example"></a>
### 예시

`Contract`(계약)의 변경을 추적하려고 다음을 만듭니다.

* 같은 객체 타입 안에 `Contract v1`, `Contract v2`, `Contract v3`를 별도 객체로 둠
* 더 나쁜 경우: 연도별로 `Contract 2023`, `Contract 2024`, `Contract 2025`를 별도 객체 타입으로 둠

각 "버전"은 속성 값만 조금씩 다른 계약 전체의 사본이고, 다른 객체(예: `Vendor`나 `Department`)로 가는 링크도 모든 버전에 중복됩니다.

<a id="problems"></a>
### 문제

| 문제 | 영향 |
|---------|--------|
| 객체 수 폭증 | 변경할 때마다 새 객체가 생겨 중복 데이터로 온톨로지가 빠르게 부풉니다. |
| 모호한 현재 상태 | 어느 버전이 "현재" 또는 기준이 되는 버전인지 알아내기 어렵습니다. |
| 모호한 링크 | 계약으로 가는 링크가 불분명해집니다. `Vendor`나 `Department`는 어느 버전에 링크되어야 할까요? |
| 복잡한 보고 | 여러 기간에 걸친 보고에 오류가 나기 쉬운 필터링과 중복 제거 로직이 필요합니다. |

<a id="solution"></a>
### 해결책

엔터티당 객체 하나를 두고 현재 상태를 속성으로 담습니다. 과거 변경은 별도의 링크된 객체 타입에 저장하거나, 편집 이력(edits history)을 활성화하거나, 시계열 속성을 활용합니다.

```
✗ Avoid                                    ✓ Prefer
────────────────────────────────────────   ────────────────────────────────────────
Contract v1 (object)                       Contract (single object per contract)
Contract v2 (object)                 →       - currentValue
Contract v3 (object)                         - currentStatus
                                             - effectiveDate
— OR —                                       - Links to:
                                               └── Contract Amendments
Contract 2023 (object type)                        - amendmentDate
Contract 2024 (object type)                        - previousValue
Contract 2025 (object type)                        - newValue
                                                   - changeReason
```

**설명**: 권장안에서는 계약 하나당 `Contract` 객체 하나만 두고 현재 금액, 현재 상태, 발효일을 속성으로 가집니다. 변경 이력은 `Contract Amendments`(계약 변경) 객체 타입에 한 건씩 쌓으며, 각 변경 객체는 변경일, 이전 값, 새 값, 변경 사유를 담고 계약에 링크됩니다. 예를 들어 계약 C-17의 금액이 두 번 바뀌었다면 `Contract` 객체는 여전히 1개이고 `Contract Amendment` 객체가 2개 생깁니다. 데이터베이스 설계에서 현재 값 테이블과 변경 이력 테이블을 나누고 이력 테이블이 외래 키로 원본 행을 가리키게 하는 방식과 같습니다.

이를 구현하려면 다음과 같이 합니다.

1. 실제 엔터티당 객체 하나를 두고, 현재 상태를 반영하는 속성을 둡니다.
2. 과거 변경을 담을 별도의 링크된 객체 타입(예: `Contract Amendment`나 `Contract History`)을 만듭니다.
3. 자주 바뀌고 시간에 따른 추적이 필요한 값에는 시계열 속성을 활용합니다.
4. 감사 추적을 위해 전체 이력이 필요하다면 백킹 데이터셋이나 편집 이력으로 보관합니다.

> **중간 요약**: 버전마다 객체를 복제하지 말고, 엔터티당 객체 하나에 현재 상태를 두고 이력은 링크된 변경 객체, 시계열 속성, 편집 이력으로 관리합니다.

***

<a id="anti-pattern-the-misnomer"></a>
## 안티패턴: 잘못된 이름 (Anti-pattern: The Misnomer)

잘못된 이름 안티패턴은 객체 타입, 속성, 링크 타입에 의미를 분명히 전달하지 못하는 모호하거나, 일반적이거나, 오해를 부르는 이름을 써서 온톨로지 전반에 혼란과 오해를 일으킬 때 생깁니다.

<a id="common-causes"></a>
### 흔한 원인

* 나에게는 통하지만 다른 사람에게는 통하지 않는 약칭을 씀
* 소스 시스템의 열 이름을 다듬지 않고 그대로 가져옴
* 명확성보다 간결함을 선호함
* 명명 규칙이나 거버넌스 표준이 없음
* 맥락만 보면 의미가 당연히 드러날 것이라고 가정함

<a id="indicators"></a>
### 징후

* 최종 사용자가 "이 속성은 무슨 뜻이지?"나 "이건 어떤 종류의 `[Object]`지?"라고 자주 물음
* 같은 이름이 서로 다른 여러 개념을 가리킬 수 있음
* 속성 이름이 `value`, `type`, `status`, `date`, `name` 같은 한정어 없는 일반 단어 하나임
* 링크 타입이 관계의 성격을 밝히지 않고 "related to(관련됨)" 같은 일반 레이블을 씀

<a id="example"></a>
### 예시

다음과 같이 모호한 이름의 온톨로지 요소를 만듭니다.

* 객체 타입: `Item`(어떤 품목? 제품? 주문 품목(line item)? 재고 품목?)
* 속성: `value`(금액? 수량? 점수? 평점?)
* 속성: `type`(무엇의 유형? 유효한 값은 무엇?)
* 속성: `date`(생성일? 수정일? 마감일? 발효일?)
* 링크 타입: `Item`에서 `Related Item`으로(어떻게 관련되는가? 부모와 자식? 대체품? 액세서리?)

이런 이름을 마주친 최종 사용자는 의미를 추측하거나, 데이터가 실제로 무엇을 나타내는지 알기 위해 문서를 뒤져야 합니다.

<a id="problems"></a>
### 문제

| 문제 | 영향 |
|---------|--------|
| 오해 | 최종 사용자가 추가 맥락 없이는 온톨로지를 이해할 수 없어 잘못된 분석과 결정을 내립니다. |
| 가파른 학습 곡선 | 새 팀원이 모호한 이름의 실제 의미를 익히는 데 상당한 시간을 써야 합니다. |
| 문서 의존 | 문서가 보조 수단이 아니라 필수가 되고, 금세 낡습니다. |
| 팀 간 혼란 | 팀마다 같은 모호한 이름을 다르게 해석해 사용 방식이 일관되지 않습니다. |

<a id="solution"></a>
### 해결책

모든 온톨로지 요소에 구체적이고 설명적인 이름을 씁니다. 이름은 그 자체로 의미를 설명해서, 누구든 추가 맥락 없이 의미를 이해할 수 있어야 합니다.

```
✗ Avoid                                    ✓ Prefer
────────────────────────────────────────   ────────────────────────────────────────
Object type: Item                    →     Object type: Product
                                           Object type: Sales Order Line Item
                                           Object type: Warehouse Inventory Record

Property: value                      →     Property: monetaryValue
                                           Property: quantityOnHand
                                           Property: riskScore

Property: type                       →     Property: productCategory
                                           Property: serviceTier

Property: date                       →     Property: orderPlacedDate
                                           Property: contractEffectiveDate

Link: Item → Related Item            →     Link: Product → Purchasing Customer
                                           Link: Employee → Supervisor
                                           Link: Equipment → Manufacturing Facility
```

**설명**: 모호한 이름 하나를 상황에 따라 구체적인 이름 여러 개로 바꾸는 예입니다. 예를 들어 `value`는 무엇의 값인지에 따라 `monetaryValue`(금액), `quantityOnHand`(보유 수량), `riskScore`(위험 점수)가 됩니다. 링크도 "관련 품목"이 아니라 `Purchasing Customer`(구매 고객), `Supervisor`(상급자), `Manufacturing Facility`(제조 시설)처럼 관계의 의미를 이름에 담습니다. 프로그래밍에서 변수 이름을 `x`, `data` 대신 `orderTotalAmount`처럼 짓는 것과 같은 원칙입니다.

이를 구현하려면 다음과 같이 합니다.

1. 구축 전에 명명 규칙을 정하고 거버넌스 검토로 이를 강제합니다.
2. 구체적이고 설명적인 이름을 씁니다: `Product`, `Sales Order Line Item`, `Warehouse Inventory Record`.
3. 모호한 속성에는 한정어를 붙입니다: `monetaryValue`, `quantityOnHand`, `riskScore`.
4. 링크는 관계를 설명하도록 이름 짓습니다: `Purchasing Customers`, `Manufacturing Facility`, `Supervisor`.
5. 모든 온톨로지 요소에 의미와 유효한 값을 설명하는 설명(description)을 추가합니다.
6. 최종 사용자와 함께 이름을 검토해 직관적이고 모호하지 않은지 확인합니다.

> **중간 요약**: `value`, `type`, `date`, `Item` 같은 일반 이름 대신 의미가 드러나는 구체적인 이름을 쓰고, 링크는 관계의 성격으로 이름 짓습니다.

<a id="building-a-successful-ontology"></a>
## 성공적인 온톨로지 만들기 (Building a successful Ontology)

이 가이드에서 설명한 안티패턴은 흔하지만 피할 수 있습니다. 근본적인 모범 사례(시스템이 아니라 현실을 모델링하기, 속성을 의도적으로 선별하기, 팀 간에 협업하기, 작업마다 알맞은 도구 고르기)에 집중하면 조직의 필요에 맞춰 확장되는 온톨로지를 만들 수 있습니다.

효과적인 온톨로지 설계는 반복적이라는 점을 기억하십시오. 명확한 엔터티 정의에서 시작하고, 이해관계자를 일찍 참여시키며, 무엇이 효과가 있는지 배워 가며 모델을 다듬습니다. 어려움에 부딪히면 이 가이드의 원칙을 다시 살펴 안티패턴이 나타나고 있지 않은지 확인하고, 바꾸기 어려워지기 전에 방향을 바로잡습니다. 개선 조치가 사람과 에이전트가 온톨로지를 더 쉽게 쓰도록 만들었는지 확인하려면 [실제 비즈니스 질문을 인수 테스트로](09_ontology-design-validation.md#sourcing-real-business-questions) 사용합니다.

## 정리

- 시스템 사일로와 부서 사일로는 같은 실제 엔터티를 소스 시스템이나 부서 기준으로 쪼갠 것이며, 공용 객체 타입 하나에 데이터를 병합하고 부서별 정보는 속성과 링크로 붙여 해결합니다.
- 키친 싱크는 기술 메타데이터 열까지 속성으로 노출한 것이며, 업무에 의미 있는 열만 속성으로 선별해 해결합니다.
- 갓 오브젝트는 성격이 다른 엔터티를 하나로 묶은 것이며, 엔터티별 객체 타입과 인터페이스로 해결합니다.
- 골든 해머와 액션 난립은 도구와 액션을 잘못된 단위로 쓰는 문제이며, 작업 성격에 맞는 도구를 고르고 비즈니스 작업 단위로 액션을 설계해 해결합니다.
- 타임머신은 버전을 객체로 복제한 것이고 잘못된 이름은 모호한 명명이며, 각각 링크된 이력 객체와 구체적인 이름으로 해결합니다.
