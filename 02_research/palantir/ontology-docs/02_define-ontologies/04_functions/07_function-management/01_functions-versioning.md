# 함수 버전 관리 (Function versioning)

- 원문: https://www.palantir.com/docs/foundry/functions/functions-versioning/
- 사이드바 위치: Define Ontologies > Functions > Function management > Function versioning

이 페이지는 함수(function)를 게시할 때 버전 번호를 어떻게 정해야 하는지 설명합니다. 함수는 Workshop 모듈, 액션, 다른 함수 등 여러 곳에서 버전을 지정해 사용되므로, 버전 번호가 "기존 사용자가 그대로 써도 안전한 변경인가"를 정확히 알려 주어야 합니다. 이 기준으로 시맨틱 버저닝(Semantic Versioning)과 Foundry가 제공하는 하위 호환성 검사를 다룹니다.

이 문서는 함수에 사용되는 버전 관리 체계를 설명합니다. 함수 릴리스의 버전은 게시자가 직접 정하며, 한 번 만들어지면 변경할 수 없습니다(immutable). 적절한 버전을 붙이는 것은 함수 사용자(consumer)에게 안정적이고 신뢰할 수 있는 경험을 제공하는 데 매우 중요합니다.

<a id="backward-compatible-changes-vs-breaking-changes"></a>
## 하위 호환 변경과 호환성을 깨는 변경 (Backward compatible changes vs. breaking changes)

함수의 버전 관리 체계는 하위 호환 변경과 호환성을 깨는 변경을 구분합니다. *하위 호환 변경(backward compatible change)* 은 함수의 기존 사용자를 방해하지 않는 변경입니다. 하위 호환이 아닌 변경은 *하위 비호환(backward incompatible)* 변경 또는 *호환성을 깨는(breaking)* 변경이라고 부릅니다.

하위 호환 변경의 예는 다음과 같습니다.

* 함수 시그니처에 선택적(optional) 입력을 추가하는 것.
* 기대 동작을 바꾸지 않고 함수의 성능을 최적화하는 것.
* 기대 동작을 바꾸지 않고 함수의 버그를 고치는 것.

호환성을 깨는 변경의 예는 다음과 같습니다.

* 함수 시그니처에 필수(required) 입력을 추가하는 것.
* 함수 시그니처의 출력 타입을 정수에서 문자열로 바꾸는 것.
* 함수를 삭제하는 것.

기존 버전에 대한 변경이 하위 호환인지 판단할 때는, 그 변경이 기존 버전 사용자를 방해하거나 사용자가 명시적으로 신경 써야 하는 일을 만드는지 스스로 물어보세요.

함수를 어떤 방식으로 사용하도록 기대할지 정하는 최종 책임은 여러분에게 있다는 점을 기억하세요.

**설명**: 시그니처(signature)는 함수의 이름, 입력 파라미터의 이름과 타입, 출력 타입을 합친 것입니다. 예를 들어 `getAge(name: string): number`를 쓰는 Workshop 모듈이 있다고 합시다. 여기에 필수 입력 `birthYear`를 추가하면 기존 모듈은 `birthYear`를 넘기지 않으므로 호출이 실패합니다. 반면 선택적 입력을 추가하면 기존 호출은 그대로 동작합니다. 이 차이가 하위 호환 여부를 가릅니다.

> **중간 요약**: 기존 사용자가 아무것도 바꾸지 않아도 계속 동작하면 하위 호환 변경이고, 필수 입력 추가, 출력 타입 변경, 함수 삭제처럼 사용자 쪽 수정이 필요하면 호환성을 깨는 변경입니다.

<a id="the-semantic-versioning-system"></a>
## 시맨틱 버저닝 체계 (The semantic versioning system)

함수는 [Semantic Versioning ↗](https://semver.org/) 체계에 따라 버전이 매겨집니다.

시맨틱 버저닝에서 버전은 `X.Y.Z` 형식을 가지며, `X`, `Y`, `Z`는 각각 메이저(major), 마이너(minor), 패치(patch) 버전이라고 부르는 0 이상의 정수입니다(예: `1.2.3`). 패치 버전 바로 뒤에 하이픈을 붙이고 영숫자로 이루어진 프리릴리스(prerelease) 식별자를 덧붙일 수도 있습니다(예: `1.2.3-rc1`).

이 페이지는 시맨틱 버저닝을 간단히 요약합니다. 명세를 따르는 것은 다른 애플리케이션에서 안정적으로 사용할 수 있는 함수를 게시하는 데 중요하므로, [전체 명세 ↗](https://semver.org/)를 읽어 보기를 권장합니다.

<a id="choosing-a-release-version"></a>
### 릴리스 버전 고르기 (Choosing a release version)

함수의 새 버전을 게시할 때는 시맨틱 버저닝 명세의 다음 사항을 고려합니다.

* 메이저 버전 `0`(`0.y.z`)은 초기 개발용입니다. 초기 개발 중에는 함수가 언제든 바뀔 수 있으며, 사용자는 함수를 안정적인 것으로 간주해서는 안 됩니다.
* 하위 비호환 변경을 하면 메이저 버전을 올려야 합니다.
* 하위 호환 방식으로 기능을 추가하면 마이너 버전을 올려야 합니다.
* 하위 호환 버그 수정을 하면 패치 버전을 올려야 합니다.
* 프리릴리스 버전은 그 버전이 불안정하며, 연결된 일반 버전이 나타내는 호환성 요구 사항을 만족하지 않을 수 있음을 뜻합니다.

**설명**: 현재 버전이 `1.4.2`라고 할 때, 버그 수정이면 `1.4.3`, 선택적 입력을 추가하는 기능 확장이면 `1.5.0`, 필수 입력 추가처럼 호환성을 깨는 변경이면 `2.0.0`을 게시합니다. 마이너를 올리면 패치는 0으로, 메이저를 올리면 마이너와 패치를 0으로 되돌리는 것이 명세의 규칙입니다.

<a id="backward-compatibility-checks"></a>
### 하위 호환성 검사 (Backward compatibility checks)

새 버전을 게시하기 전에 함수에 대해 하위 호환성 검사가 수행됩니다. 특히 다음과 같은 호환성을 깨는 변경이 있으면 경고를 받습니다.

* 함수를 없애는 것. Python 또는 TypeScript 함수 코드 저장소에서 함수를 삭제하는 경우도 포함됩니다.
* 함수 시그니처에서 입력을 없애는 것(선택적 입력이라도 해당됩니다).
* 함수 시그니처에서 입력의 순서를 바꾸는 것.
* 함수 시그니처에 필수 입력을 추가하는 것.
* 잘못된 입력 타입 변경(예: 정수에서 문자열로). 숫자 입력 타입을 넓히는 것(예: 정수에서 부동소수점으로)도 경고를 냅니다.
* 잘못된 출력 타입 변경(예: 문자열에서 선택적 문자열로).

이 검사가 어떤 이유로든 실패하면 메이저 버전을 릴리스하는 것이 권장됩니다. 단, 아직 초기 개발 단계(즉, 메이저 버전이 `0`)라면 해당되지 않습니다.

**주의**: Palantir의 기본 제공 검사가 모든 종류의 호환성을 깨는 변경을 잡아내지는 않습니다. 예를 들어 내부 구현에서 비롯된 호환성을 깨는 변경은 감지되지 않을 수 있습니다. 이 검사를 통과했다는 사실만으로 마이너나 패치 버전을 릴리스하는 것은 안전하지 않습니다.

**설명**: 출력 타입을 "문자열"에서 "선택적 문자열"로 바꾸는 것이 왜 문제인지 보겠습니다. 기존 사용자는 결과가 항상 문자열이라고 가정하고 있었는데, 이제 결과가 비어 있을(null) 수 있으므로 null 처리 코드가 없는 사용자는 오류를 겪을 수 있습니다. 입력은 반대 방향으로 작동합니다. 입력이 "더 많은 값을 받도록" 바뀌는 것은 대체로 기존 호출을 깨지 않지만, 출력이 "더 많은 종류의 값을 내놓도록" 바뀌면 받는 쪽이 깨질 수 있습니다.

<a id="caveat-custom-types"></a>
#### 주의 사항: 커스텀 타입 (Caveat: Custom types)

현재 함수 내부의 데이터 타입 표현에는 커스텀 타입(custom type) 필드의 선택성(optionality)에 대한 정보가 충분하지 않습니다. 그 결과, 커스텀 타입 입력과 출력에 대해서는 선택적 필드(예: TypeScript의 `quantity?: Integer` 또는 Python의 `quantity: Integer = 0`)를 포함해 어떤 필드든 추가하거나 제거하면 하위 호환성 검사가 경고를 낼 수 있습니다.

앞으로는 출력 커스텀 타입에서 선택적 필드를 제거하거나 입력 커스텀 타입에 선택적 필드를 추가할 때 경고가 나오지 않도록 변경 작업을 진행하고 있습니다.

**주의**: 입력 커스텀 타입에서 선택적 필드를 제거하면 여전히 경고를 받습니다. 사용자가 넘겨준 필드를 무시하는 것은 일반적으로 나쁜 관행입니다. 사용자는 자신이 넘긴 필드가 함수의 동작을 결정한다고 기대할 가능성이 높기 때문입니다.

**설명**: 커스텀 타입은 함수의 입력이나 출력으로 쓰려고 직접 정의한 구조(TypeScript의 인터페이스, Python의 데이터 클래스 등)입니다. 예를 들어 `{ name: string; quantity?: Integer }` 형태의 입력 타입에서 `quantity?`의 물음표가 "선택적 필드"를 뜻합니다.

<a id="restrict-stable-version-tags"></a>
### 안정 버전 태그 제한 (Restrict stable version tags)

안정적인 시맨틱 버전 릴리스(프리릴리스가 아닌 버전)는, 다운스트림 운영(production) 애플리케이션이 버전 범위(예: `>=1.2.3 <2.0.0`)로 함수를 참조하도록 구성되어 있으면 즉시 사용될 수 있습니다. 그러므로 새 안정 버전으로 릴리스하기 전에 코드 변경 사항을 검토하고 테스트하는 것이 중요합니다.

보호된 브랜치(protected branch)에 대한 저장소 설정에서 [토글을 활성화](https://www.palantir.com/docs/foundry/code-repositories/branch-settings/#restrict-stable-version-tags)하면, 함수의 안정 버전 릴리스에 제한을 강제할 수 있습니다.

**설명**: 버전 범위 `>=1.2.3 <2.0.0`은 "1.2.3 이상이면서 2.0.0 미만인 버전 중 가장 최신 것을 쓴다"는 뜻입니다. 이렇게 설정된 애플리케이션은 누군가 `1.3.0`을 게시하는 순간 별도 조치 없이 `1.3.0`을 쓰기 시작합니다. 그래서 검토되지 않은 코드가 안정 버전으로 나가면 바로 운영 환경에 영향을 줍니다.

> **중간 요약**: 함수 버전은 `X.Y.Z` 시맨틱 버저닝을 따르며, 호환성을 깨면 메이저, 기능 추가는 마이너, 버그 수정은 패치를 올립니다. Foundry가 게시 전에 호환성 검사를 해 주지만 완전하지 않으며, 버전 범위로 참조하는 운영 앱은 새 안정 버전을 즉시 쓰므로 저장소 설정으로 안정 버전 태그를 제한할 수 있습니다.

<a id="frequently-asked-questions"></a>
## 자주 묻는 질문 (Frequently asked questions)

<a id="choosing-release-versions-in-the-0yz-initial-development-phase"></a>
### 0.y.z 초기 개발 단계에서 릴리스 버전 고르기 (Choosing release versions in the 0.y.z initial development phase)

호환성을 깨는 변경은 마이너 릴리스로, 하위 호환 변경은 패치 릴리스로 내는 것이 일반적인 관행입니다. Node/NPM 생태계처럼 여러 개발 영역의 사용자가 이를 전제로 삼고 있으며, 이는 [캐럿 범위(caret range) ↗](https://docs.npmjs.com/cli/v6/using-npm/semver#caret-ranges-123-025-004)가 널리 쓰이는 데서 드러납니다.

**설명**: NPM의 캐럿 범위 `^0.2.5`는 `>=0.2.5 <0.3.0`을 뜻합니다. 즉 메이저가 0일 때는 마이너가 바뀌면 호환성이 깨진다고 보고 자동 업데이트 대상에서 제외합니다. 이 관행에 맞추면 `0.y.z` 단계에서도 사용자가 안전하게 버전 범위를 쓸 수 있습니다.

<a id="accidentally-releasing-a-backward-incompatible-change-as-a-patch-or-minor-version"></a>
### 실수로 하위 비호환 변경을 패치나 마이너 버전으로 릴리스한 경우 (Accidentally releasing a backward incompatible change as a patch or minor version)

호환성을 깨는 변경을 릴리스했다는 것을 깨닫는 즉시, 문제를 바로잡고 새 마이너 버전으로 하위 호환성을 복원해야 합니다.

다음 예를 생각해 봅시다.

1. 문자열 입력 하나를 받는 `myFunction`이라는 함수가 버전 `1.0.0`으로 있습니다.
2. `myFunction`에 새 필수 입력을 추가하고, 실수로 이 변경을 마이너 버전 릴리스 `1.1.0`으로 냈습니다.

이를 바로잡으려면 시그니처의 호환성을 깨는 변경을 되돌리고(즉, `1.1.0`에서 추가한 필수 입력을 제거하고) 이 변경을 버전 `1.2.0`으로 릴리스합니다.

**설명**: 이미 게시된 버전은 변경할 수 없으므로 `1.1.0`을 고쳐 쓰는 대신 그 위에 `1.2.0`을 새로 냅니다. 버전 범위 `>=1.0.0 <2.0.0`을 쓰던 사용자는 `1.2.0`을 자동으로 받아 다시 정상 동작하게 됩니다. 필수 입력이 정말 필요하다면 그 변경은 별도로 `2.0.0`으로 내야 합니다.

<a id="checking-backward-compatibility-when-a-release-fails-or-has-not-yet-been-published"></a>
### 릴리스가 실패했거나 아직 게시되지 않았을 때 하위 호환성 확인하기 (Checking backward compatibility when a release fails or has not yet been published)

TypeScript나 Python 함수의 경우 게시가 실패하거나 몇 분 정도 걸릴 수 있습니다. 두 경우 모두 기본 제공 하위 호환성 검사를 실행할 수 없습니다. 새 릴리스를 만들기 전에 이 검사 결과를 보고 싶다면 다음 방법이 있습니다.

* 마지막 릴리스가 실패했다면 "custom tag" 옵션을 사용해 마지막으로 성공한 태그와 비교합니다.
* 마지막 릴리스가 아직 게시되지 않았다면 게시가 끝날 때까지 기다립니다.

> **중간 요약**: `0.y.z` 단계에서는 호환성을 깨는 변경을 마이너로, 나머지를 패치로 냅니다. 호환성을 깨는 변경을 실수로 낸 경우 되돌린 뒤 새 마이너 버전으로 다시 냅니다. 이전 릴리스가 실패했거나 진행 중이면 custom tag로 비교하거나 게시 완료를 기다립니다.

## 정리

- 함수 버전은 게시자가 정하며 한 번 게시되면 바꿀 수 없습니다.
- 버전은 시맨틱 버저닝 `X.Y.Z`를 따르며, 호환성을 깨는 변경은 메이저, 하위 호환 기능 추가는 마이너, 하위 호환 버그 수정은 패치를 올립니다. `0.y.z`는 초기 개발 단계입니다.
- Foundry는 게시 전에 함수 삭제, 입력 제거와 순서 변경, 필수 입력 추가, 타입 변경 등을 검사해 경고하지만, 모든 호환성 문제를 잡아내지는 못합니다.
- 커스텀 타입은 선택적 필드 변경에도 경고가 날 수 있습니다.
- 버전 범위로 참조하는 운영 앱은 새 안정 버전을 즉시 쓰므로, 저장소 설정으로 안정 버전 태그를 제한할 수 있습니다.
