# 필수 통제 속성 (Mandatory control properties)

- 원문: https://www.palantir.com/docs/foundry/object-link-types/mandatory-control-properties/
- 사이드바 위치: Define Ontologies > Object and link types > Properties > Mandatory control properties

이 페이지는 객체 단위로 세밀한 접근 제어를 걸 수 있는 필수 통제 속성(mandatory control property)을 설명합니다. 설정 절차, 세 가지 통제 유형(마킹, 조직, 분류), 데이터소스 단위로 권한이 적용되는 방식, 검증 규칙, 액션과 Marketplace에서의 사용법을 다룹니다. 데이터베이스로 치면 행 단위 보안(row-level security)을 객체 속성 값으로 설정하는 기능입니다.

필수 통제 속성은 객체에 저장된 데이터에 대해 세분화된 접근 제어를 가능하게 하는 객체 타입 속성입니다. 필수 통제 속성을 사용하면 어떤 객체에서 같은 데이터소스에 있는 다른 모든 속성에 대한 접근을 제한할 수 있으며, 그 속성들은 필수 통제(mandatory control)를 충족하는 사용자만 볼 수 있게 됩니다.

**참고:** 필수 통제 속성은 **Object Storage v2에서만 사용할 수 있습니다**.

**설명**: 일반적인 권한(permission)은 "이 데이터셋 전체를 볼 수 있는가"처럼 리소스 단위로 판단합니다. 필수 통제 속성은 행마다 다른 접근 조건을 붙입니다. 예를 들어 `Case` 객체 3개가 다음과 같다고 합시다.

| case_id | summary | access_marking |
|---|---|---|
| C1 | 일반 민원 | `[]` |
| C2 | 개인정보 포함 | `["PII"]` |
| C3 | 내부 감사 | `["PII", "AUDIT"]` |

`access_marking`이 필수 통제 속성이면, `PII` 마킹이 없는 사용자는 C1만 볼 수 있고, `PII`와 `AUDIT`을 모두 가진 사용자는 세 객체를 모두 볼 수 있습니다. SQL의 행 단위 보안 정책 `WHERE user_markings ⊇ row.access_marking`과 같은 조건입니다.

<a id="how-to-use-mandatory-control-properties"></a>
## 필수 통제 속성 사용 방법 (How to use mandatory control properties)

1. 먼저 마킹 기반 제한 뷰(marking-backed restricted view, RV)를 만듭니다. [마킹 기반 제한 뷰 만들기](https://www.palantir.com/docs/foundry/security/restricted-views/#create-marking-backed-restricted-views)에 대해 더 알아보세요.
2. Ontology Manager로 이동합니다.
3. 속성 접근을 제한하려는 객체 타입을 선택한 뒤, 필수 통제 속성으로 설정할 속성을 만들거나 선택합니다.
4. 속성 사이드바에서 그 속성이 제한 뷰의 해당 **마킹 열(marking column)에** 매핑되어 있는지 확인합니다.
5. 속성 타입의 기본 타입(base type)을 **Mandatory Control**로 설정합니다.
   1. 기본적으로 필수 통제 속성은 접근 제한을 위해 **마킹(markings)과**/또는 **조직(organizations)을** 지원합니다.
   2. CBAC가 활성화되어 있다면 **분류(classification)** 기반 필수 통제를 선택하는 옵션이 생깁니다.
6. 데이터소스에서 **Allowed markings**(허용 마킹)와/또는 **Allowed organizations**(허용 조직)를 선택합니다. 분류의 경우 **Max classification**(최대 분류)을 선택합니다.
7. 객체 타입에 데이터소스가 여러 개라면, 나머지 각 데이터소스에도 필수 통제 속성을 하나씩 선택해 그 속성들도 보호합니다.
8. 온톨로지에 변경 사항을 저장하고 재인덱싱이 완료될 때까지 기다립니다.

**설명**: 제한 뷰(restricted view)는 데이터셋 위에 행 단위 접근 정책을 얹은 뷰입니다. 마킹 열은 각 행에 붙은 마킹 목록을 담은 열입니다. 필수 통제 속성은 이 마킹 열을 객체 속성으로 가져와 객체 단위 접근 제어에 쓰는 것입니다.

> **중간 요약**: 마킹 기반 제한 뷰를 만들고, 그 마킹 열에 매핑한 속성의 기본 타입을 Mandatory Control로 설정한 뒤, 데이터소스마다 허용 마킹, 허용 조직 또는 최대 분류를 지정하고 저장합니다.

<a id="types-of-mandatory-control-properties"></a>
## 필수 통제 속성의 유형 (Types of mandatory control properties)

속성에 설정할 수 있는 필수 통제에는 세 가지 유형이 있습니다.

* [마킹(Markings)](#markings)
* [조직(Organizations)](#organizations)
* [분류(Classifications)](#classifications)

<a id="markings"></a>
### 마킹 (Markings)

마킹은 데이터에 접근하려면 사용자가 특정 마킹을 가지고 있어야 하도록 요구해 접근을 제한하는 필수 통제입니다. 리소스에 마킹이 여러 개 있으면, 사용자는 그 모두를 가지고 있어야 리소스에 접근할 수 있습니다. [마킹](https://www.palantir.com/docs/foundry/security/markings/)에 대해 더 알아보세요.

마킹을 사용하려면 허용 마킹 집합을 제공해야 합니다. 데이터소스의 모든 필수 통제 속성에는 이 집합에 속한 마킹만 허용됩니다.

<a id="organizations"></a>
### 조직 (Organizations)

조직은 사용자 그룹과 리소스 사이에 엄격한 격리(silo)를 강제하는 접근 요건입니다. 모든 사용자는 단 하나의 조직의 *구성원(member)이지만*, 여러 조직의 *게스트 구성원(guest member)이* 될 수 있습니다. 조직이 표시된 데이터에 접근하려면 사용자가 그 조직의 구성원이어야 합니다. 리소스에 조직이 여러 개 있으면, 사용자는 리소스에 적용된 조직 중 최소 하나의 구성원이어야 합니다. [조직](https://www.palantir.com/docs/foundry/security/orgs-and-spaces/#organizations)에 대해 더 알아보세요.

조직을 사용하려면 허용 조직 집합을 제공해야 합니다. 데이터소스의 모든 필수 통제 속성에는 이 집합에 속한 조직만 허용됩니다.

마킹과 조직은 같은 필수 통제 속성에서 함께 사용할 수 있습니다. 이 경우 사용자는 리소스에 접근하기 위해 모든 마킹을 충족하고 조직 중 최소 하나를 충족해야 합니다.

**설명**: 마킹은 AND 조건, 조직은 OR 조건입니다. 어떤 행의 값이 마킹 `["PII", "HR"]`, 조직 `["OrgA", "OrgB"]`라면 접근 조건은 `(PII 보유 AND HR 보유) AND (OrgA 구성원 OR OrgB 구성원)`입니다.

<a id="classifications"></a>
### 분류 (Classifications)

분류 마킹(classification marking)은 민감한 정부 정보를 보호하는 데 쓰이는 필수 통제입니다. 정보의 민감도가 계층적으로 정의되는 경우에 민감한 정보에 대한 접근을 제한하는 데 사용됩니다. 모든 사용자는 자신의 분류 등급과 같거나 그보다 낮은 등급으로 분류된 데이터에만 접근할 수 있습니다.

CBAC 마킹은 등록 환경(enrollment)에 CBAC가 활성화되어 있을 때만 설정할 수 있습니다. [CBAC(분류 기반 접근 제어, classification based access controls)](https://www.palantir.com/docs/foundry/security/classification-based-access-controls/)에 대해 더 알아보세요.

분류를 사용하려면 최대 분류(max classification)를 제공해야 합니다. 데이터소스의 모든 분류 기반 필수 통제 속성에는 이 최대 분류를 충족하는 마킹만 허용됩니다.

분류는 같은 필수 통제 속성에서 마킹이나 조직과 함께 사용할 수 없습니다.

**설명**: 계층적 분류는 등급에 순서가 있는 체계입니다. 예를 들어 등급이 낮은 순으로 "공개 < 대외비 < 비밀"이라면, "비밀" 등급 사용자는 세 등급의 데이터를 모두 볼 수 있고 "대외비" 사용자는 "공개"와 "대외비"만 볼 수 있습니다. 마킹이 "필요한 꼬리표를 모두 가졌는가"를 보는 반면, 분류는 "등급의 크기 비교"로 판단합니다.

> **중간 요약**: 필수 통제는 마킹(모두 보유해야 함), 조직(하나 이상 구성원이어야 함), 분류(사용자 등급 이하만 접근) 세 유형이 있습니다. 마킹과 조직은 함께 쓸 수 있지만 분류는 다른 유형과 섞을 수 없습니다.

<a id="datasource-level-permissioning"></a>
## 데이터소스 수준의 권한 부여 (Datasource-level permissioning)

필수 통제 속성은 같은 데이터소스에 있는 다른 모든 속성을 보호합니다. 데이터소스가 하나인 객체 타입에서는, 사용자가 필수 통제 속성의 값을 충족할 때만 객체를 볼 수 있다는 뜻입니다.

하지만 여러 데이터소스가 뒷받침하는 객체 타입(multi-datasource-backed object type, MDO)에서는 데이터소스마다 자체 필수 통제 속성을 가질 수 있습니다. 특정 데이터소스의 필수 통제는 그 데이터소스가 뒷받침하는 속성만 보호합니다.

따라서 사용자가 한 객체의 속성 중 일부만 볼 권한을 가질 수도 있습니다. 이 경우 사용자는 권한이 있는 데이터소스에서 매핑된 속성만 볼 수 있습니다. 나머지 속성은 사용자에게 객체 인스턴스를 표시할 때 null로 나타납니다.

필수 통제 속성을 효과적으로 사용하려면, 같은 필수 통제를 공유해야 하는 속성만 같은 데이터소스에 들어가도록 백킹 데이터소스를 구성해야 합니다.

**설명**: 예를 들어 `Employee` 객체 타입이 데이터소스 A(`name`, `department`, 통제 없음)와 데이터소스 B(`salary`, `ssn`, 통제 마킹 `["HR"]`)로 구성되어 있다면, `HR` 마킹이 없는 사용자에게는 같은 직원 객체가 `name`과 `department`만 채워지고 `salary`, `ssn`은 null인 상태로 보입니다. 그래서 민감도가 같은 속성끼리 데이터소스를 나누어 설계해야 합니다.

> **중간 요약**: 필수 통제는 같은 데이터소스의 속성에만 적용되므로, 데이터소스가 여러 개인 객체에서는 사용자마다 볼 수 있는 속성이 다르고 권한 없는 속성은 null로 보입니다.

<a id="validations"></a>
## 검증 (Validations)

필수 통제 속성에는 다음 검증이 적용됩니다.

* 필수 통제 속성은 **제한 뷰(restricted view)의** **마킹 열(marking column)에** 매핑되어야 합니다. 필수 통제는 객체 타입을 제한 뷰로 뒷받침함으로써 강제됩니다. 이 제한 뷰에는 사용자가 행을 보려면 매핑된 열의 마킹을 충족해야 한다는 정책이 있습니다. 자세한 내용은 [제한 뷰(Restricted Views)](https://www.palantir.com/docs/foundry/security/restricted-views/)를 참고하세요.
* **필수 통제 속성은 필수(required)여야 합니다.** 이렇게 하면 필수 통제 속성이 있는 객체가 데이터소스에 존재할 때 필수 통제가 반드시 정의되어 있으므로 데이터 일관성과 무결성을 유지하는 데 도움이 됩니다. 모든 필수 통제 속성은 null이면 안 됩니다. 다만 마킹과 조직 값은 빈 배열로 설정할 수 있습니다. 이 경우 모든 사용자가 마킹 요건을 충족하므로 해당 행을 볼 수 있습니다. [필수 속성](07_required-properties.md)에 대해 더 알아보세요.
  * 이미 편집 내용이 있는, 백킹 데이터소스 없는 객체 타입에 필수 통제 속성을 추가하려는 경우, 필수 통제 속성은 비어 있을 수 없으므로 속성을 바로 만들 수 없습니다. 이를 우회하려면 다음과 같이 합니다.
    1. null을 허용하는 문자열 배열 속성을 추가합니다.
    2. [액션](../../03_action-types/01_overview.md)을 사용해 그 값을 채워 넣습니다(backfill).
    3. 속성의 기본 타입을 **Mandatory Control**로 바꿉니다.
* 필수 통제 속성을 포함하는 모든 데이터소스는 그 속성에 어떤 값을 넣을 수 있는지에 대한 제약 조건을 정의해야 합니다. 이 제약 조건은 분류 기반 필수 통제의 경우 최대 분류, 그 외에는 허용 마킹과/또는 허용 조직 집합의 형태를 띱니다. 필수 통제 속성에 대한 모든 편집과 백킹 데이터셋에서 가져온 값은 데이터소스에 설정된 제약 조건을 따라야 합니다.
  * 이 제약 조건은 객체 저장소 수준에서 강제됩니다. 따라서 Ontology Manager에서 이 제약 조건을 위반하는 객체 타입을 저장할 수는 있더라도, 데이터셋의 기존 값이 제약 조건을 충족하지 않거나 데이터셋 값이 필수 통제에 유효하지 않은 값을 포함하도록 업데이트되면 객체 타입 인덱싱이 실패합니다. 또한 필수 통제 속성에 유효하지 않은 값을 설정하려는 모든 편집은 거부되며 액션 제출이 실패합니다.
  * 이 허용 마킹, 허용 조직, 최대 분류는 이 객체 타입에서 머티리얼라이즈된(materialized) 모든 내보내기 데이터셋에 마킹을 붙이는 데 사용됩니다. 이렇게 하면 객체 타입의 모든 행을 볼 수 있는 사용자만 머티리얼라이즈된 데이터셋을 볼 수 있습니다.

필수 통제 속성은 기본적으로 `Hidden`(숨김)으로 설정됩니다. 필수 통제 속성은 다른 필드의 마킹으로 쓰이기 위한 것이므로, 보통 Object View나 표에 표시할 필요가 없기 때문입니다. 그러나 필요하다면 필수 통제 속성의 가시성을 켤 수 있습니다.

**설명**: 머티리얼라이제이션(materialization)은 객체 타입의 현재 상태(편집 반영 포함)를 다시 데이터셋으로 내보내는 것입니다. 내보낸 데이터셋에는 행별 통제가 없으므로, 허용 마킹 전체를 데이터셋 전체에 붙여서 "모든 행을 볼 자격이 있는 사람"만 보도록 막는 것입니다. 허용 마킹이 `{PII, HR}`라면 내보낸 데이터셋에는 `PII`와 `HR`이 모두 붙습니다.

> **중간 요약**: 필수 통제 속성은 제한 뷰의 마킹 열에 매핑되어야 하고, 필수 속성이어야 하며(빈 배열은 허용), 데이터소스마다 허용 값 제약이 있어 위반 시 인덱싱이나 액션이 실패합니다. 머티리얼라이즈된 데이터셋에는 이 제약 값이 마킹으로 붙고, 속성 자체는 기본적으로 숨겨집니다.

<a id="mandatory-controls-in-actions"></a>
## 액션에서의 필수 통제 (Mandatory controls in actions)

액션 타입에 필수 통제 파라미터를 추가할 수 있습니다. 이 파라미터는 마킹 파라미터일 수도 있고, CBAC가 활성화되어 있다면 분류 파라미터일 수도 있습니다. 조직 파라미터는 현재 지원되지 않습니다.

필수 통제 파라미터는 주로 액션이 만드는 객체에 필수 통제 속성을 설정할 때 사용됩니다. 이 경우 제공된 값은 속성의 허용 값을 따라야 합니다. 유효하지 않은 값이 제공되면 액션 제출이 실패합니다.

분류 기반 필수 통제 파라미터의 경우, 파라미터 수준에서 최대 분류를 추가할 수도 있습니다. 이는 액션 타입 검증이므로, 제공된 값이 최대 분류를 충족하지 않으면 액션 제출 자체를 막습니다. 이는 액션 제출은 허용하지만 완료에 실패하게 되는 데이터소스 검증에 의존하는 것과 대비됩니다.

액션으로 만든 객체는 백킹 데이터소스에서 파생된 객체와 마찬가지로, 필수 통제 속성에 제공된 값으로 보호됩니다.

> **중간 요약**: 액션 타입에는 마킹 또는 분류 필수 통제 파라미터를 둘 수 있으며(조직은 미지원), 파라미터 수준의 최대 분류를 설정하면 잘못된 값을 제출 단계에서 미리 막을 수 있습니다.

<a id="marketplace-usage"></a>
## Marketplace 사용 (Marketplace usage)

필수 통제 속성이 있는 객체 타입과 필수 통제 파라미터가 있는 액션 타입은 Marketplace를 통해 패키징하고 설치할 수 있습니다.

필수 통제 속성이 있는 객체 타입을 패키징할 때, 허용 마킹이나 최대 분류는 해당 제품의 설치 입력(installation input)으로 선언됩니다.

마찬가지로, 최대 분류가 설정된 분류 기반 필수 통제 파라미터가 있는 액션 타입을 패키징하면, 최대 분류가 설치 입력으로 선언됩니다.

제품을 설치할 때는 각 필수 통제 속성에 대해 허용 마킹이나 최대 분류를 선택하라는 요청을 받습니다. 선택한 값은 설치 시 필수 통제 속성의 허용 마킹이나 최대 분류로 설정됩니다.

<img src="https://www.palantir.com/docs/resources/foundry/object-link-types/marking-inputs-install.png" alt="Marketplace 설치 중 필수 통제 입력을 선택하는 모습" width="800" />

같은 값을 가진 필수 통제 속성이나 파라미터를 여러 개 패키징하면 필수 통제 입력은 하나만 선언됩니다.

**설명**: 마킹은 설치 환경마다 다른 값(다른 조직의 다른 마킹)을 쓰기 때문에, 패키지에 특정 마킹을 고정해 넣을 수 없습니다. 그래서 설치하는 쪽이 자기 환경의 마킹을 고르도록 "설치 입력"으로 남겨 두는 것입니다. 함수의 매개변수를 호출 시점에 넘겨받는 것과 같은 구조입니다.

> **중간 요약**: Marketplace로 패키징하면 허용 마킹과 최대 분류가 설치 입력이 되어, 설치 시 설치 환경의 값을 선택하게 됩니다.

## 정리

- 필수 통제 속성은 마킹 기반 제한 뷰의 마킹 열에 매핑해, 같은 데이터소스의 속성에 객체 단위 접근 제어를 거는 Object Storage v2 전용 기능입니다.
- 통제 유형은 마킹(모두 필요), 조직(하나 이상), 분류(등급 비교) 세 가지이며, 분류는 다른 유형과 함께 쓸 수 없습니다.
- 필수 통제 속성은 필수 속성이어야 하고, 데이터소스별 허용 값 제약을 위반하면 인덱싱이나 액션이 실패합니다.
- 데이터소스가 여러 개이면 데이터소스별로 통제가 적용되어, 권한 없는 속성은 null로 보입니다.
- 액션에는 마킹 또는 분류 파라미터를 둘 수 있고, Marketplace 패키징 시 허용 값은 설치 입력이 됩니다.
