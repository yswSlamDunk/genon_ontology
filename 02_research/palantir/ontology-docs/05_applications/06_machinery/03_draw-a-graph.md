# Machinery 프로세스 그리기 (Draw a graph)

- 원문: https://www.palantir.com/docs/foundry/machinery/draw-a-graph/
- 사이드바 위치: Applications > Machinery > Draw a graph

이 페이지는 Machinery 애플리케이션에서 상태(state)와 전이(transition)를 직접 그려 프로세스 모델을 만드는 방법을 다룹니다. 프로세스 모델은 데이터에서 자동으로 뽑아낼 수도 있지만, 머릿속에 있는 업무 흐름을 그림으로 옮기거나 기존 모델을 고칠 때는 수동 그리기 도구가 필요합니다. 프로세스 컨테이너, 상태와 액션 사이의 간선 의미, 자동 레이아웃, 여러 객체 타입을 다루는 방법을 차례로 설명합니다.

Machinery 애플리케이션으로 프로세스 모델을 만드는 방법은 두 가지입니다. [프로세스 마이닝(process mining)](05_process-mining.md)으로 과거 관측 기록에서 프로세스 모델을 자동으로 도출하거나, 상태와 전이를 직접 그려서 프로세스를 수동으로 정의할 수 있습니다.

모델링하고 그래픽으로 시각화하고 싶은 실제(물리적) 프로세스가 머릿속에 있을 때, 또는 기존 프로세스 모델을 수정하고 보강해야 할 때 수동 프로세스 그리기 도구를 사용하면 좋습니다.

Machinery 리소스의 빈 캔버스에서 수동 프로세스 그리기의 첫 단계는 프로세스 컨테이너(process container)를 만드는 것입니다. 컨테이너는 특정 유형의 엔터티와 그 상태들을 나타내는 데 사용됩니다. 예를 들면 `Claim`(보험 청구)이 있습니다. 서로 상호작용하는 엔터티가 여러 개라면 프로세스 컨테이너를 더 추가할 수 있으며, 나란히 두거나 다른 컨테이너 안에 중첩해 둘 수 있습니다.

![빈 캔버스에 새 프로세스를 그리는 모습.](https://www.palantir.com/docs/resources/foundry/machinery/drawing-1.png)

편집을 더 편하게 하려면 전체 화면(fullscreen) 옵션을 선택해 프로세스 컨테이너에 초점을 맞출 수 있습니다. 그러면 해당 프로세스 컨테이너와 그 하위 요소가 캔버스 전체를 채웁니다. 전체 화면 초점 모드에서 되돌아가려면 **Navigation** 패널에서 보기를 바꾸면 됩니다.

모든 그리기 동작은 프로세스 컨테이너의 액션을 통해 사용할 수 있고, 프로세스에 초점이 맞춰져 있을 때는 메인 툴바에서도 사용할 수 있습니다.

![프로세스 메인 툴바.](https://www.palantir.com/docs/resources/foundry/machinery/drawing-2.png)

**설명**: 여기서 "프로세스"는 하나의 엔터티가 시간에 따라 거쳐 가는 상태들의 흐름을 말합니다. 예를 들어 `Claim` 객체 하나는 "접수됨", "심사 중", "승인됨" 또는 "거절됨" 같은 상태를 차례로 지납니다. 컴퓨터공학에서 배우는 상태 기계(state machine, 유한 상태 오토마타)와 같은 구조로, 노드는 상태이고 간선은 상태 전이입니다. 프로세스 컨테이너는 "어떤 객체 타입의 상태 기계인가"를 묶어 두는 상자라고 보면 됩니다.

> **중간 요약**: Machinery에서는 프로세스 마이닝으로 모델을 자동 생성하거나 직접 그릴 수 있습니다. 직접 그릴 때는 먼저 엔터티 유형(예: `Claim`)을 나타내는 프로세스 컨테이너를 만들고, 필요하면 여러 컨테이너를 나란히 또는 중첩해 둡니다.

<a id="adding-states-actions-and-automations"></a>
## 상태, 액션, 자동화 추가하기 (Adding states, actions, and automations)

프로세스를 구성하는 일반적인 방식은 초기 상태에서 시작해 이후 상태들을 그리고, 그다음 그 사이에 액션과 자동화(automation)를 추가하는 것입니다.

<img src="https://www.palantir.com/docs/resources/foundry/machinery/state-action-automation.png" width="250" alt="캔버스에 상태, 액션, 자동화를 추가합니다." />

또는 액션들의 순서부터 먼저 만들고 상태는 나중에 채워 넣을 수도 있습니다.

상태 사이의 간선(edge)은 상태 전이를 나타냅니다. 액션이나 자동화를 상태에 연결할 때 간선은 다음 의미를 따릅니다.

* **Input States(입력 상태):** 액션 실행 전에 객체가 가질 수 있도록 허용된 상태입니다. Foundry 액션의 경우 [제출 조건(submission criteria)](../../02_define-ontologies/03_action-types/08_submission-criteria.md)을 통해 이를 강제할 수 있습니다. 기존 제출 조건은 액션 노드의 **Details** 패널에서 확인할 수 있습니다.

* **Output States(출력 상태):** 액션 실행 후 나올 수 있는 결과 상태입니다. 예를 들어 *엔터티 추출(extract entities)* 액션은 *추출 성공(extraction succeeded)* 또는 *추출 실패(extraction failed)로* 끝날 수 있습니다. 출력 상태는 강제할 수 없습니다. 다만 Machinery에서 액션 로직을 검토해 출력 상태를 수동으로 검증할 수는 있습니다.

* **Automations(자동화):** 입력 상태 중 하나에 도달하면 자동으로 실행되는 액션을 나타냅니다. 자동화는 알림(notification)을 보낼 수도 있는데, 이는 어떤 상태의 *부수 효과(side effect)를* 나타냅니다.

노드와 간선은 해당 요소를 선택한 뒤 휴지통 아이콘을 누르거나 키보드의 백스페이스 키를 눌러 삭제할 수 있습니다.

[프로세스 온톨로지](04_connect-data.md)를 선택하고 나면, 상태 이름은 객체 타입의 `state` 속성(property) 값을 나타냅니다. Machinery에서 상태 이름을 바꿔도 데이터의 값은 바뀌지 않습니다. 또한 그래프의 요소에 실제 액션이나 자동화를 연결할 수 있습니다. 이렇게 하면 프로세스 모델을 점차 프로세스 구현으로 바꿔 나갈 수 있습니다.

**설명**: 입력 상태와 출력 상태의 차이는 "검사할 수 있는가"에 있습니다. 액션을 실행하기 전에는 대상 객체의 현재 `state` 값을 읽을 수 있으므로, 제출 조건으로 "`state`가 `submitted`일 때만 실행 가능"처럼 규칙을 걸 수 있습니다. 반면 액션이 실행된 뒤 어떤 값이 써질지는 액션 내부 로직이 정하므로, Machinery 그래프에 그려 둔 출력 상태는 설계 의도를 기록한 것일 뿐 시스템이 막아 주지는 않습니다. 예를 들어 `state` 열에 `submitted`, `in_review`, `approved` 값이 들어 있는 Claim 테이블이 있다면, 그래프의 상태 노드 세 개가 이 세 값에 대응합니다.

> **중간 요약**: 상태를 먼저 그리고 그 사이에 액션과 자동화를 넣는 것이 일반적입니다. 입력 상태는 제출 조건으로 강제할 수 있지만 출력 상태는 강제되지 않으며, 상태 이름은 객체 타입의 `state` 속성 값에 대응하되 이름을 바꿔도 실제 데이터는 바뀌지 않습니다.

<a id="auto-layout-feature"></a>
## 자동 레이아웃 기능 (Auto-layout feature)

Machinery의 **auto-layout**(자동 레이아웃) 기능은 기본으로 켜져 있습니다. 노드를 추가하거나 연결하면 노드 위치가 자동으로 정해져, 그래프가 왼쪽에서 오른쪽으로 흐르는 프로세스 흐름으로 정돈된 상태를 유지합니다.

<img src="https://www.palantir.com/docs/resources/foundry/machinery/auto-layout.png" alt="자동 레이아웃 옵션." width="200" />

같은 "층(layer)"에 있는 노드들의 세로 순서는 노드를 위아래로 끌어서 조정할 수 있습니다.

프로세스에 루프가 있다면, 아무 노드나 왼쪽으로 끌어서 어떤 노드를 먼저 배치할지 정할 수 있습니다. 나머지 레이아웃은 그에 맞춰 조정됩니다.

자동 레이아웃 결과가 만족스럽지 않다면 이 기능을 끌 수도 있습니다. 기능을 끄면 그래프에서 노드를 자유롭게 옮길 수 있습니다.

수동 레이아웃 모드에서는 왼쪽 아래 컨트롤 바에 있는 일회성 레이아웃(one-time layout) 옵션으로 그래프를 다시 정리하면 도움이 될 수 있습니다.

**설명**: "층"은 그래프를 왼쪽에서 오른쪽으로 배치할 때 같은 세로줄에 놓이는 노드 묶음을 뜻합니다. 방향 그래프를 층별로 배치하는 알고리즘(계층형 그래프 그리기)은 사이클이 없을 때 위상 정렬 순서로 층을 정하는데, 루프가 있으면 시작점을 정할 수 없어서 사용자가 어떤 노드를 앞에 둘지 지정하도록 한 것입니다.

> **중간 요약**: 자동 레이아웃은 기본으로 켜져 있어 그래프를 왼쪽에서 오른쪽 흐름으로 정리합니다. 끌어서 순서를 조정할 수 있고, 기능을 끄면 자유 배치가 가능하며 이때는 일회성 레이아웃으로 한 번씩 정리할 수 있습니다.

<a id="multiple-object-types"></a>
## 여러 객체 타입 (Multiple object types)

실제 프로세스 중 많은 경우는 여러 엔터티가 관여합니다. 이런 경우 프로세스 컨테이너로 각 엔터티를 표현하고 그 상태와 액션을 연결할 수 있습니다. 예를 들어 한 컨테이너에 있는 액션이 다른 엔터티의 상태에 영향을 줄 수 있으며, 그 경우 해당 상태들에 출력으로 연결됩니다. 액션은 그 액션이 입력으로 받는 객체의 컨테이너 안에 두는 것을 권장합니다.

**설명**: 예를 들어 `Claim` 컨테이너와 `Payment` 컨테이너가 있다고 합시다. "청구 승인" 액션은 `Claim` 객체를 입력으로 받아 `Claim`의 상태를 `approved`로 바꾸면서 동시에 `Payment` 객체를 `pending` 상태로 만들 수 있습니다. 이 액션은 입력이 `Claim`이므로 `Claim` 컨테이너 안에 두고, `Payment`의 `pending` 상태로 출력 간선을 그립니다.

## 정리

- Machinery 프로세스 모델은 프로세스 마이닝으로 자동 생성하거나, 상태와 전이를 직접 그려 만듭니다.
- 직접 그릴 때는 엔터티 유형을 나타내는 프로세스 컨테이너를 만들고, 그 안에 상태, 액션, 자동화를 배치합니다.
- 입력 상태는 제출 조건으로 강제할 수 있지만 출력 상태는 강제되지 않습니다. 상태 이름은 `state` 속성 값에 대응하며, 이름 변경이 데이터를 바꾸지는 않습니다.
- 자동 레이아웃이 기본으로 켜져 있고, 끄면 노드를 자유롭게 배치할 수 있습니다.
- 여러 엔터티가 얽힌 프로세스는 컨테이너를 여러 개 두고, 액션은 입력 객체의 컨테이너에 둡니다.
