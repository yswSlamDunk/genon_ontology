# Machinery 핵심 개념 (Core concepts)

- 원문: https://www.palantir.com/docs/foundry/machinery/core-concepts/
- 사이드바 위치: Applications > Machinery > Core concepts

이 페이지는 Machinery를 쓰기 전에 알아야 할 개념인 프로세스(process), 상태(state), 액션과 자동화(action and automation), 프로세스 로그(process log)를 정의합니다. 각 개념이 온톨로지의 객체 타입, 속성, 액션 타입, 값 타입과 어떻게 대응하는지가 핵심입니다.

Machinery 애플리케이션을 사용하기 전에 다음 개념들을 살펴보기를 권장합니다.

<a id="process"></a>
## 프로세스 (Process)

현실 세계의 프로세스에서는 문서, 장비, 개인 같은 엔터티가 시간에 따라 [상태](#state)를 옮겨 갑니다. 이런 프로세스 객체(process object) 중 다수는 서로 링크되어, 하나의 프로세스에 관여하는 여러 엔터티를 표현할 수 있습니다. Machinery에서는 상태와 액션을 담는 프로세스 컨테이너(process container)를 통해 이런 프로세스를 모델링할 수 있습니다. 프로세스 컨테이너는 서로 링크될 수 있고 중첩될 수도 있습니다.

프로세스 안의 엔터티, 즉 "프로세스 객체"는 온톨로지의 객체 타입(예: *Claim*, *Flight*, *Employee*)으로 표현할 수 있습니다. 이 객체 타입에는 객체의 상태를 나타내는 문자열 타입 속성(property)이 있어야 합니다.

<a id="state"></a>
## 상태 (State)

상태는 객체의 현재 조건을 나타냅니다. 예를 들어 소포라면 *in progress*(배송 중)나 *delivered*(배송 완료)가 상태입니다. 가능한 상태는 열거 가능(enumerable)해야 합니다. 예를 들어 `Name` 속성은 가능한 이름이 무한히 많으므로 상태로 적합하지 않습니다.

상태 전이(state transition)는 상태 노드 사이의 엣지로 표시됩니다.

모든 객체는 어느 시점에서든 가능한 상태 중 **하나에** 있어야 합니다. 그렇지 않은 상황은 프로세스 계층(process hierarchy)으로 모델링해야 합니다. 예를 들어 직원은 *new-hire*(신규 입사) 또는 *onboarded*(온보딩 완료) 상태이면서, 동시에 *paid*(급여 지급됨) 또는 *awaiting payment*(지급 대기) 상태일 수 있습니다. 이런 경우는 별도의 프로세스로 나누고, 상위(parent) 프로세스가 직원이 *payable*(지급 가능) 상태인지를 추적하도록 해야 합니다.

온톨로지 안에서 상태는 `State` 속성의 문자열 값으로 표현됩니다. 이 값은 Machinery의 상태 ID와 같습니다. 그래프에 표시되는 상태 라벨을 바꾸려면 표시 이름(display name)을 덮어쓸 수 있습니다.

Machinery의 상태 ID는 데이터의 상태 값과 같습니다. 오타나 불일치를 피하려면 상태 속성을 열거형(enumeration) [값 타입(value type)](../../02_define-ontologies/02_object-and-link-types/08_value-types/01_value-types-overview.md)으로 뒷받침할 수 있습니다. 그러면 온톨로지의 데이터가 미리 정의된 값 집합 중 하나만 가질 수 있도록 보장됩니다. Machinery는 이 설정을 감지해 프로세스 상태를 동기화된 상태로 유지합니다.

**설명**: Machinery의 상태 모델은 유한 상태 기계(finite state machine)와 같은 구조입니다. 상태 집합이 유한하고, 객체는 한 시점에 정확히 하나의 상태에 있으며, 전이가 상태 사이의 엣지로 정의됩니다. Claim 테이블로 보면 다음과 같습니다.

| claim_id | State |
|---|---|
| C1 | `submitted` |
| C2 | `under_review` |
| C3 | `approved` |

`State` 열의 값은 `submitted`, `under_review`, `approved`, `rejected` 같은 정해진 목록 안에서만 나와야 합니다. 열거형 값 타입을 쓰는 것은 SQL에서 `CHECK (state IN ('submitted', 'under_review', 'approved', 'rejected'))` 제약을 거는 것에 해당하며, `aproved` 같은 오타가 데이터에 들어가는 것을 막습니다. 직원 예시처럼 두 상태 축(입사 진행과 급여 지급)이 독립적으로 움직이면, 한 열에 두 축을 섞지 않고 프로세스를 둘로 나누는 이유가 여기에 있습니다.

> **중간 요약**: 프로세스 객체는 상태를 나타내는 문자열 속성을 가진 객체 타입이며, 상태는 유한하게 열거 가능해야 하고 객체는 한 시점에 정확히 하나의 상태에 있어야 합니다. 동시에 여러 상태 축이 필요하면 프로세스 계층으로 나누고, 열거형 값 타입으로 상태 값의 오타를 막을 수 있습니다.

<a id="action-and-automations"></a>
## 액션과 자동화 (Action and automations)

액션은 상태 전이의 원인입니다. 플랫폼 안에서 일어나는 상태 변경은 [액션](../../02_define-ontologies/03_action-types/01_overview.md)으로 정의됩니다. 이 액션들을 Machinery 그래프로 가져와(import) 프로세스에서 어떤 역할을 하는지 지정할 수 있습니다.

<a id="process-log"></a>
## 프로세스 로그 (Process log)

프로세스는 본질적으로 엔터티가 시간에 따라 변화를 겪는 것입니다. 객체가 거치는 경로의 패턴이나 한 상태에 머문 평균 시간 같은 지표를 파악하려면 변경의 시간 차원을 기록하는 것이 필수입니다. Machinery는 외부 데이터 소스에서 왔든 Foundry 액션에서 왔든 객체에 대한 모든 변경을 추적하는 `Log` 객체 타입을 유지함으로써 이를 수행합니다.

이 객체 타입은 다른 객체 타입처럼 볼 수 있지만, 로그 객체 타입은 Machinery가 자동으로 관리하므로 직접 액션을 정의해서는 안 됩니다.

각 로그 객체 타입은 하나의 객체 타입 속성 하나의 변경을 추적합니다. 각 프로세스는 자기만의 프로세스 로그를 가질 수 있습니다.

플랫폼 밖에서 일어나는 프로세스의 경우, 어떤 객체가 언제 어떤 상태로 들어갔는지 추적하는 변경 로그(changelog) 형식의 데이터셋을 제공해야 합니다. Machinery는 이전 상태, 상태 사이의 소요 시간, 객체가 지금까지 거친 경로처럼 분석과 모니터링에 필요한 파생 값을 계산합니다.

**설명**: 앞의 Claim 테이블은 "현재" 상태만 보여 줍니다. 경로와 소요 시간을 알려면 변경 이력이 필요하며, 변경 로그 형식은 다음과 같이 변경 하나당 행 하나를 갖습니다.

| claim_id | state | timestamp |
|---|---|---|
| C1 | `submitted` | 2024-03-01 09:00 |
| C1 | `under_review` | 2024-03-02 14:00 |
| C1 | `approved` | 2024-03-05 10:00 |

Machinery가 계산하는 파생 값은 이 행들을 객체별로 시간순 정렬해 얻을 수 있습니다. 예를 들어 세 번째 행의 이전 상태는 `under_review`이고, `under_review`에 머문 시간은 3월 2일 14:00부터 3월 5일 10:00까지이며, C1의 경로는 `submitted`, `under_review`, `approved` 순입니다. SQL의 윈도 함수 `LAG(state) OVER (PARTITION BY claim_id ORDER BY timestamp)`로 이전 상태를 구하는 것과 같은 계산입니다.

> **중간 요약**: 상태 전이는 액션으로 일어나며, Machinery는 모든 변경을 `Log` 객체 타입에 자동 기록합니다. 플랫폼 밖 프로세스는 객체, 상태, 시각을 담은 변경 로그 데이터셋을 제공하면 Machinery가 이전 상태, 소요 시간, 경로를 계산합니다.

## 정리

- 프로세스는 상태와 액션을 담는 프로세스 컨테이너로 모델링하며, 컨테이너는 서로 링크되거나 중첩될 수 있습니다.
- 프로세스 객체는 상태를 나타내는 문자열 속성을 가진 객체 타입이고, 상태 값은 열거 가능해야 하며 열거형 값 타입으로 고정할 수 있습니다.
- 객체는 한 시점에 하나의 상태에만 있어야 하며, 독립된 상태 축은 프로세스 계층으로 나눕니다.
- 상태 전이는 액션이 일으키고, 변경 이력은 Machinery가 관리하는 `Log` 객체 타입이나 외부 변경 로그 데이터셋으로 기록됩니다.
